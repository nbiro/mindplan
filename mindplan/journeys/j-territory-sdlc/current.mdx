# Plan software

## Purpose

Domain capability: plan and execute software work through a GitOps MindPlan territory — orientation, compiler-gated mutation, diagrams, prescribed packages, and framework docs. Agents never invent tickets outside this graph.

## Overview

Humans and coding agents share one living plan under `mindplan/`. Work starts with `orient_for_work` / `find_related_nodes`, reads territory via `get_node_context`, checks blast radius before substantial Foundation/Interaction implementation, and mutates only through MCP tools. Mermaid/DOT views keep the architecture visible; `ship` and Bug resolution are gated by compiler rules and external review.

Journey state is **computed** from member Interactions (never set manually). Assembler(s) are derived from member Interactions’ `depends_on` (today: `f-mcp-runtime` via the SDLC Interactions).

## Linked Interactions

- `i-orient-plan` — orient on the plan (read tools)
- `i-steer-plan` — change the plan (write tools)
- `i-export-map` — see the map (Mermaid/DOT + map.md)
- `f-test-harness` — smoke / view / search regression
- `f-territory-store` — prescribe `src/foundations` and `src/interactions` packages
- `f-framework-docs` — SPEC, playbooks, skills, README (shared with Adopt MindPlan)

Deprecated historical suffixes (`i-orient-plan-v2`, `i-export-map-v2`, `f-framework-docs-v3`, …) are not active members of the living capability.

## What “healthy” means

- Agents can orient, mutate, and export without bypassing MCP or `.cursorignore`
- Active Interaction territories describe full repo contracts (Territory Completeness)
- Foundations that SDLC Interactions depend on are shipped and stable unless intentionally evolving
