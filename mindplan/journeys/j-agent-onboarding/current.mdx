# Adopt MindPlan

## Purpose

Domain capability: adopt MindPlan in a consumer project and wire it into coding agents — init (prescribed or layout-free), playbooks, per-agent MCP guides, public package install path, and shared framework documentation.

## Overview

A consumer runs `mindplan-mcp init` (or installs from npm once published) and gets territory layout, an always-on playbook (`AGENTS.md` / `mindplan/agent/playbook.md`), the define-entities skill, `.cursorignore`, and integration guides for major agent hosts. Brownfield repos can opt into layout-free mode (`--layout free`) so they keep their existing `src/` layout while still using the MindPlan graph and lifecycle. Framework docs (SPEC, README, roles, Territory Completeness) are shared with Plan software so consumers and this repo speak the same language.

Journey state is **computed** from member Interactions. Assembler for init/runtime paths: `f-mcp-runtime` (via Interaction `depends_on`).

## Linked Interactions

- `i-init-project` — scaffold `mindplan/` + agent assets + `mindplan/config.json`
- `i-init-project` — brownfield opt-out of prescribed `src/foundations|interactions` packages
- `f-framework-docs` — per-agent MCP setup guides
- `i-npm-publish` — first claim + publish script + consumer install docs (also belongs to Ship to npm / `j-npm-publish`)
- `f-framework-docs` — README / SPEC / playbook / skills (shared with Plan software)

Deprecated historical suffixes (`i-init-project-v2`, `f-framework-docs-v3`, …) are not active members of the living capability.

## What “healthy” means

- A new repo can init and connect an agent to MindPlan MCP without hand-copying internals
- An existing repo can adopt MindPlan without restructuring application code into prescribed packages
- Playbook and SPEC stay aligned with Territory Completeness and Foundation roles
- npm publish (when shipped) makes install a one-liner for consumers
