# Dirty-src paths are repo-relative when the project is in a subfolder

## Summary

`collectDirtySrcPaths` in `src/interactions/i-check-integrity/check.ts` reads `git status --porcelain -uall` and `git diff --name-only <base>...HEAD`. Both print paths relative to the repository top. Claims and the source universe are relative to the project root, so when the project sits below the top (`MINDPLAN_ROOT=packages/app`), no changed path matches a claim. `check --base` (dirty-src) and `check --merge=strict` then pass whatever changed. `newFilesSinceBase` in `f-source-index/git.ts` already passes `--relative` and gets this right.

## Repro Steps

1. A git repository with the MindPlan project in `sub/`, a node claiming `src/x.ts`, and the node `in-progress`
2. Change `sub/src/x.ts` on a branch
3. `check --merge=strict --base main` from `sub/` passes; git reported `sub/src/x.ts`, which no claim covers

## Expected / Actual

**Expected:** changed paths are relative to the project root, and paths outside it are ignored.

**Actual:** paths carry the folder prefix, nothing matches, and both checks silently pass.

## Fix Checklist

- [x] Root cause identified — note: collectDirtySrcPaths used git status --porcelain and git diff --name-only, both repo-top relative, while claims are project-root relative
- [x] Fix implemented — note: git status -- . with the repoPrefix stripped, and git diff --relative; paths outside the project are left out
- [x] Regression test added — note: merge-gate.test.mjs builds a project in <repo>/sub and checks collectDirtySrcPaths and check --merge=strict; it fails on the previous code
