# Fan-out signal

## Purpose

Infra — flags a planned node that has to know every feature of a kind. In a real project a planned "delete a site" action depended on nodes in four other unbuilt changes (billing, site analytics, the AI builder, site teams), because erasing a site had to clean up after each of them, so every new feature that stores per-site data would have had to edit its plan too. Every `depends_on` edge was individually correct and the hotspot signal only looks at shipped nodes, so nothing flagged it. This Foundation counts how many other unshipped changes a pre-ship node reaches through `depends_on` and, past a threshold, words a warning that suggests the fix: invert the design so the features meet a contract on a shared Foundation (a schema convention, or a lifecycle record they react to), enforced by a node rule and a test, and the node depends on none of them. It is its own Foundation, not another open–closed signal in `f-compiler-rules`, so this feature leaves that hotspot closed. It is graph facts only, and it only ever warns.

## Shared Substrate Spec

Intended files: `src/foundations/f-fan-out/` (`fan-out.ts`, `index.ts`).

- `fanOut(graph, node)` → `{ count, changes }` or `null`:
  - `null` unless the node is a Foundation, Interaction, or Interface that has never shipped (no `shipped_at`) and is not retired (`isInactiveNode`, `f-domain-model`)
  - Reads the node's `depends_on` targets. A target counts when it exists, is not retired, has never shipped (no `shipped_at`), and has a change id (`activeChange`, `f-domain-model`) that differs from the node's own `activeChange`. Targets in the node's own change, shipped targets, retired targets, and targets with no change id never count
  - `changes` are the distinct counted change ids in the order their first target appears in `depends_on`; `count` is their number (0 when none)
- `fanOutFor(graph, node, settings)` → `{ node_id, count, changes }` or `null` — the warning case: `fanOut` has `count` at least `settings.warn_at` (`FanOutSettings`, `f-source-index`), and the node is not kept whole (`keepsWhole`, `f-compiler-rules`: an active decision with `keep_whole: true`, the same switch the hotspot signal honours)
- `fanOutWarning(f)` → the warning text (the check prefixes `Warning: `):
  `fan-out: <id> depends on <N> other changes (<a>, <b>, …). It may need to know every feature of a kind. Consider inverting: put a contract on a Foundation those changes meet (a schema convention, or a record they react to), enforce it with a node rule and a test, and drop these depends_on edges.`
- `fanOuts(graph, settings)` → every `fanOutFor` result, highest `count` first, then by id, for the check
- Never throws on a missing target and never Blocks anything

Depends on: `f-domain-model`, `f-source-index`, `f-compiler-rules`.

- **Open revisions (0.18.0).** Fan-out still counts pre-ship nodes only; reading a node's change uses the live change, so open revisions on shipped targets do not count

## Acceptance Criteria

- A pre-ship node whose `depends_on` targets sit in 3 other unshipped changes yields a `fan-out:` warning naming the count and the change ids; 2 yields none
- Targets in the node's own change, shipped targets, retired targets, and targets with no change id do not count
- A shipped node and a Capability or Bug yield `null` from `fanOut`
- An active `keep_whole: true` decision on the node silences `fanOutFor`; superseding it brings the warning back
- `warn_at` from `fanOutSettings` changes the threshold (e.g. 2 warns on 2 changes)
- The warning text matches the wording above
- Verified via `npm test` (`src/foundations/f-test-harness/fan-out.test.mjs`)
