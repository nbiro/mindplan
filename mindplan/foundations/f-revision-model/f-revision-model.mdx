# Revision model

## Purpose

The pure rules every reader and writer of a shipped node's open revisions shares, kept out of the hotspot `f-domain-model` and `f-compiler-rules`. A shipped node can hold several open revisions at once, one per change id, so features that touch one hub node no longer queue behind each other's ship. A revision stores edges, claims, and test links as deltas against live, and remembers the hash of each live section it started from, so shipping one revision rebases the others like git.

## Shared Substrate Spec

Intended files: `src/foundations/f-revision-model/` (`revision.ts`, `rebase.ts`, `index.ts`).

- **Types** (defined in `f-domain-model/types.ts`, imported here; this Foundation adds only functions): `EdgeDelta { add: string[]; remove: string[] }`; `RevisionConflict` (`{ kind: "section", section }`, `{ kind: "scalar", field: "title" | "description" | "role" }`, `{ kind: "claim", path, owner }`); `Revision { change, change_ref?, state, opened_at, updated_at, title, description, role?, edges: Partial<Record<edge type, EdgeDelta>>, implements: EdgeDelta, tests: EdgeDelta, attributed?, split_into?, decisions?, base: { scalars, sections }, conflicts }`. A shipped node's `open_revisions?: Revision[]` holds one per change; pre-ship nodes keep their live `change` and have none
- `applyDelta(live, delta)`, `diffDelta(live, snapshot)`: deltas round-trip (`applyDelta(live, diffDelta(live, s))` equals `s` as a set, sorted)
- `openChanges(node)`, `revisionFor(node, change)`
- `resolveRevisionChange(node, change?)`: the given change (Blocked when the node has no revision of it), else the only open revision, else `null` (live) when none is open; several open and no `change` is `Blocked: "<id>" has open revisions "<a>", "<b>"; pass change.`
- `withRevision(node, change)`: a node-shaped view of live ⊕ that revision, with today's `next` view field filled from it, so gate code that reads `node.next` judges live plus that revision only
- `graphUnder(graph, change)`: the graph with every node that has a revision of `change` replaced by `withRevision`; every other node stays live (other changes' revisions are invisible)
- `splitSections(body)`, `sectionHashes(body)`: level-2 sections plus a `_preamble` entry; `## Rules` and `## Decisions` excluded; hashes are the first 8 hex characters of sha1 of the section text with line endings normalized
- `rebase(liveOld, liveNew, revision, revisionBody)` → `{ revision, body }`: per section and per scalar, untouched by the revision → take new live; touched only by the revision → keep; both touched with equal text → keep; otherwise keep the revision's text and add a conflict; every base hash moves to new live. An `add` already in new live and a `remove` no longer in live drop silently; an `implements` add now claimed live by another node becomes a claim conflict
- No module-level state; every function is pure over its arguments

Depends on: `f-domain-model`.

## Decisions

### d-revisions-per-change-folder

- Decision: A shipped node holds one open revision per change id, each in its own folder <node>/revisions/<change>/ with its <id>.mdx, attachments/, and decisions/; ship or discard deletes the folder.
- Alternatives:
  - Flat <id>.next.<change>.mdx files beside live (crowds the node folder and needs a parallel naming scheme for attachments)
  - Keep one next slot and queue features (the SkyLoom session reopened f-static-build six times in sequence)
- Why: The user chose the folder layout: two branches working on different changes of one node never touch the same path, so git merges them cleanly.
- Change: multi-revisions
- Date: 2026-11-02

### d-revision-deltas-and-section-rebase

- Decision: A revision stores edges, claims, and test links as add/remove deltas against live and records a hash of each live scalar and level-2 section at open; shipping one revision rebases its siblings per section (untouched carries live, both-edited becomes a conflict resolved by resolve_conflict before in-review).
- Alternatives:
  - Full snapshots per revision (the second ship silently reverts the first one's edges and claims)
  - Line-level three-way merge (needs stored base text and a merge engine; section granularity matches how territory is edited)
- Why: Deltas commute when they touch different targets, and a section hash is enough to tell untouched from edited without keeping base text.
- Consequences: Two revisions that edit the same section always conflict, even when the edits do not overlap.
- Change: multi-revisions
- Date: 2026-11-02

### d-gates-judge-live-plus-one-revision

- Decision: Gates judge a revision against graphUnder(graph, change): live plus that change's revisions only; other changes' open revisions are invisible to it.
- Alternatives:
  - Judge against live plus every open revision (one unfinished change would block or unblock another)
- Why: Each change must be shippable on its own; the rebase after a ship re-runs the gates against the new live.
- Change: multi-revisions
- Date: 2026-11-02
