# Graph search

## Purpose

Infra — orientation ranking and 1-hop neighborhood expansion for `find_related_nodes` / `orient_for_work`, plus the pure graph queries that say whose rules apply to a node and whose work a node's rules reach. Keeps retired nodes out of default ranking so agents focus on the live architecture. Rules flow only toward the work that needs them: up `belongs_to`, along `depends_on`, and from affected nodes into Bugs — never downward and never across siblings, otherwise a Journey's local rule would constrain unrelated Interactions. Finished work does not count: a resolved Bug must not pad the list of whose work a Foundation's rules reach. Decisions reach a node along exactly the same walk, so an agent about to reshape an Interaction sees why its Foundation's contract looks the way it does before it simplifies it back; one walk serves both, so rules and decisions can never disagree about who inherits from whom. Whether a decision is superseded is computed here from the decisions of active nodes, never stored.

## Shared Substrate Spec

Package: `src/foundations/f-graph-search/`

- `search.ts` — `tokenize` / `scoreNode` / `rankNodes` (token scoring: the keyword fallback, pure); `expandNeighborhood`; `findRelatedNodes` (focus + linked summaries; takes `matches` already ranked by `searchNodes`, else ranks by tokens); default/max find limits (`DEFAULT_FIND_LIMIT` / `MAX_FIND_LIMIT`); excludes `deprecated`/`cancelled` nodes and closed Bugs from ranking by default (aligned with map export policy)
- **Hybrid search** (`search.ts`, over `f-search-index`):
  - `searchDocs(graph, readBody?)` — one `SearchDoc` per node: the open next slot's title and description while a revision is open, area (Journey titles through `belongs_to`; an Interface's through the Interactions it exposes; a Bug's through the Interactions it affects), entry points (titles of the Interfaces exposing it), section headings from `sectionHeadings(body)` (scaffold headings and any heading shared by more than 8% of nodes left out; memoized by id, slot, `updated_at`, and the reader's optional `stamp`, the file's size and mtime, so a body edited outside MCP is re-read), claimed paths, edges, and the retired flag
  - `searchNodes(graph, query, { type?, limit?, root, readBody?, embedder? })` → `RankedMatch[]` — the type filter applies first and retired nodes never rank; keyword half = `SearchIndex.keyword` (FTS5 bm25, with the type filter in SQL), or `rankNodes` when there is no index, no FTS5, or the query throws (another server rebuilding the file); semantic half = cosine top 50 within `SEMANTIC_WINDOW` (0.12) of the best hit once the model is ready; a cache or model problem never fails the search
  - `fuseRankings(lists, { docs, exact?, paths? })` — reciprocal rank fusion (`Σ 1/(RRF_K + rank)`, `RRF_K` = 60, `FUSION_DEPTH` = 50 per half), then `GRAPH_BOOST` (one rank step at the top) once for each already-found node one `belongs_to` / `depends_on` / `exposes` / `mounts` link from a top-3 node (top-3 nodes linked to each other included), then path matches (a single-word query with a slash or a file extension, matched against claims: exact, directory prefix, or glob) above every fused score, and an exact id above everything
  - `score` is the fused score, comparable only within one reply; each `RankedMatch` from `searchNodes` also carries `area` (the doc's Journey titles), which `rankNodes` leaves out
  - `refreshSearchIndex(graph, root, readBody?)` (after a write) and `warmSearchIndex(root, loadGraph, readBody?)` (server start) — never throw, never block a call
- `scoreNode` (the token fallback) scores alias hits like title hits
- `searchDocs` fills `aliases` from the node's `aliases` list: they go into the FTS5 `aliases` column (weight 8) and the embedded text (`Aliases: …`)
- Ranking covers all node types including Interaction and Interface (no Interaction-specific branches — ranking is type-agnostic aside from retired filters and the type filter)
- `expandNeighborhood` walks all incident edge types including `exposes` and `leads_to`
- Tests/fixtures must cover Interaction/Interface nodes and `exposes`/`leads_to` neighborhoods once the domain model ships those types
- `rules.ts` — `resolveNodeRules(graph, nodeId): RuleEntry[]` over **live** edges (proposed `next` edges are ignored):
  1. the node's own rules (`via: self`, distance 0)
  2. rules of nodes reached by following `belongs_to` upward (`via: belongs_to`), ascending distance
  3. rules of nodes reached by the transitive closure of `depends_on` (`via: depends_on`), ascending distance
  4. for a Bug only: every node it `affects`, plus everything that node would itself resolve (own, `belongs_to`, `depends_on`), all with `via: affects` and distance offset by 1
  - Not inherited: `exposes` / `leads_to` neighbors, siblings, and anything downward (a Journey gets no Interaction rules; a Foundation gets no dependent's rules; an Interface gets no exposed Interaction's rules)
  - A node reached twice keeps its smallest distance; nodes with empty rules and inactive nodes (`isInactiveNode`: `cancelled`, `deprecated`, closed Bugs) are omitted; ties order by node id
- `rulesAudience(graph, nodeId): RulesImpactEntry[]` — exactly the other active nodes whose `resolveNodeRules` includes an entry from `nodeId`, with the `via` and `distance` of that entry; empty when `nodeId` has no rules
- `rulesImpact(graph, node)` → `{ has_rules, inherited_by }`: the one builder of the `rules_impact` payload used by `get_blast_radius` and `patch_node_rules`
- All three are pure and read `node.rules` already loaded in the graph; no file I/O. The node index is built once per call, not once per node
- **Shared inheritance walk.** `inheritanceSources(graph, nodeId)` → `{ node, via, distance }[]`: the walk above without the rules filter (same order, live edges only, smallest distance kept, inactive nodes skipped except the focus itself). `resolveNodeRules` is that walk filtered to nodes with rules, so its results do not change
- `decisions.ts` — pure, over `activeDecisions` already loaded in the graph:
  - `supersessionIndex(graph)` — decision id → id of the decision that supersedes it, built from every active node's decisions (only a cancelled node's decisions supersede nothing; a deprecated node's replacement still stands, or retiring it would bring back the design it replaced). A decision is `superseded` (with `superseded_by`) when the index has it, else `active`
  - `resolveNodeDecisions(graph, nodeId, { include_superseded? })` → `DecisionEntry[]` over `inheritanceSources`: each source node's decisions in recorded order, labeled with `node_id`, `node_type`, `via`, `distance`, and `status`; superseded entries left out unless asked for
  - `listDecisions(graph, { node_id?, change?, include_superseded? })` → `DecisionEntry[]`: one node's own decisions, every decision recorded under a change, or every decision in the graph. Change and whole-graph listings skip inactive nodes; the filters combine
  - `nodeDecisions(graph, node, opts, index?)` (one node's own decisions with status), `slotDecisions(graph, node, slot, opts?)` (one file's entries, for node context; superseded entries left out unless `include_superseded`), and `decisionIds(graph)` (every id in live and next files plus every id a `supersedes` still names, so an id freed by a discarded revision is not reused while a decision points at it)
  - `findDecision(graph, id)` — the node holding a decision id in its live or open next file. Ids are unique across the graph
  - `generateDecisionId(graph, text)` — `d-` plus a slug of the decision's first words, with a numeric suffix when taken

Depends on: `f-domain-model`, `f-search-index`.

## Acceptance Criteria

- Query ranking returns a focus plus 1-hop neighborhood summaries
- Retired nodes (`deprecated`, `cancelled`, closed Bugs) are excluded from default orientation ranking
- Limits respect DEFAULT_FIND_LIMIT / MAX_FIND_LIMIT
- Queries matching Interaction/Interface titles return them as focus candidates
- 1-hop neighborhoods include `exposes` and `leads_to` neighbors
- An Interaction resolves its own, its Journey's, and its Foundations' (transitive) rules, each labeled with its source node
- A Journey resolves only its own; a Foundation resolves its own and its Foundation dependencies'; sibling Interactions never see each other's rules
- A Bug resolves the full resolution of every node it `affects`
- `rulesAudience` of a Foundation lists its transitive dependents; of a Journey lists its Interactions; both agree with `resolveNodeRules`
- Resolved and wontfix Bugs appear in no audience and contribute no rules
- An Interaction resolves its own, its Journey's, and its Foundations' (transitive) decisions, each labeled with its source node; a Bug resolves the decisions of the nodes it affects; siblings never see each other's
- A decision named in another active node's `supersedes` is `superseded` and left out unless `include_superseded`; once the superseding decision is gone (its revision discarded) it is active again
- A decision superseded only by a cancelled node's decision stays active; one superseded by a deprecated node's decision stays superseded
- `listDecisions` by change returns the decisions of every node recorded under that change id
- `resolveNodeRules` and `rulesAudience` results are unchanged by the shared walk
- `searchNodes` ranks an exact id first and the claim owner of a file path first; the graph boost breaks an exact tie toward the node linked to the top 3 and never reorders a clear winner
- On the search test set (`search-eval.json`), keyword-only and hybrid ranking stay at or above the committed floor (`search-eval.metrics.json`) and hybrid beats the token baseline on top-1, top-5, and MRR; "contact form quote request" ranks `i-send-enquiry` first in the site-builder fixture
- A node with an open next is found by its next wording
- Verified via `npm test` (`search.test.mjs`, `search-index.test.mjs`, `search-eval.test.mjs`)

## Decisions

### d-supersede-reach-follows-inheritance

- Decision: A decision may supersede one held by the node itself or by any node it inherits decisions from, Journeys included.
- Alternatives:
  - Only the node and its Foundations, as the brief words it (a Journey decision that orient_for_work shows could not be replaced from the work that outgrew it)
- Why: Whatever reaches the agent through orient_for_work should be replaceable by that agent.
- Change: decision-records
- Date: 2026-10-20

### d-hybrid-rrf-ranking

- Decision: Ranking is hybrid: keyword (FTS5 bm25, or token scoring as the fallback) and semantic (cosine) top lists merged with reciprocal rank fusion, score = sum of 1/(60 + rank), then a small bonus for nodes one link from the top 3; an exact id is always first.
- Alternatives:
  - Semantic only (exact ids and rare words rank worse than with keywords)
  - A weighted sum of raw bm25 and cosine scores (the two scales differ per query and need retuning per graph)
- Why: Rank fusion needs no score calibration between the two halves and keeps each half's strengths; the graph boost lifts the Interaction behind a matched Journey or Foundation without reordering a clear winner.
- Consequences: score in RankedMatch is the fused score, comparable only within one reply.
- Change: semantic-search
- Date: 2026-10-25
