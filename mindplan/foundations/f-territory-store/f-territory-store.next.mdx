# Territory store

## Purpose

Infra — persist territory through the store only; keep a shipped next file as a state-only twin (`mirror`). Sync the twin on every live write; restore on ship/discard; delete on unship/retire. Own `writeProjectBrief` for `mindplan/project.md` and, for every node, the `## Rules` section of its `<id>.mdx`. That section has one writer (`writeNodeRules`); body writes can neither read it as prose nor clobber it, otherwise a territory rewrite would silently erase rules. Because the heading is the storage format, a `## Rules` section that already existed becomes that node's rules, so the contract names that adoption instead of leaving it to surprise a consumer. Small body fixes (one section, one phrase) are first-class writes so an agent does not resend a whole body to change a line. The store also owns each node's `## Decisions` section: decision records written only by `appendDecision`, one entry per decision and never rewritten, so the reasoning trail cannot be edited away by a body rewrite. Unlike rules, decisions are slot-bound: while a shipped node evolves they are recorded on its next file, they ship with the revision, and a discarded revision takes its decisions with it. Recording a decision never resets readiness: it explains the contract, it does not change it. A shipped node's live `change` scalar also serves as its neighbor label, written by one helper that keeps the mirror twin in step. The live `added_claims` list marks claims added in place; the store drops each entry once the body names it, so the marker clears itself through ordinary territory writes. Loading the graph goes through the graph cache (`f-graph-cache`): the store lists the node folders and owns the parser, so a load parses only folders the cache cannot vouch for and returns what a full parse would.

## Shared Substrate Spec

Intended files: `src/foundations/f-territory-store/`

- Discover: `mirror` does not set `node.next`; pipeline states do
- `writeMirrorTwin` / `syncMirrorAfterLiveWrite` / `deleteNextSlotFiles` / `mirrorDriftReason`
- Every live writer that re-syncs the twin returns its path (`patchFrontmatter`, `addEdgeToFrontmatter` / `removeEdgesFromFrontmatter` / `writeImplementsFrontmatter` as `{ readinessReset, twin }`, `patchNodeTerritory`'s `twin`, and the `paths` of `writeNodeRules` / `appendDecision`), so the tool that called it can list the twin in `changed_files`
- `openNextSlot` flips mirror→draft (creates twin from live when missing); does not reset checkboxes
- `discardNextSlot` / `promoteNextSlot` restore the mirror twin (do not delete the next file)
- Reject writes aimed at a mirror file
- A whole-body write converts the new body to the file's own line endings, so CRLF territory stays CRLF
- `writeProjectBrief` for MCP `patch_project_description` and `patch_project_rules`
- **`mounts` edge field.** `mounts` is a frontmatter edge array like `exposes`: parsed, written, removed by `unlink`, copied by `open_next`, promoted on ship, and a pipeline node with an open evolution writes it to the next slot
- **Section and replace patches.** `patchNodeTerritory` also takes `section: { heading, text }` and `replace: { find, with, all? }`
  - `replaceSectionInBody(body, heading, text)` rewrites the lines under one level-2 heading (heading line and other sections untouched, line endings kept; a `## ` line inside a fenced code block is code, not a heading); a missing heading is Blocked and lists the sections
  - `replaceTextInBody(body, find, with, all?)` replaces one exact piece; Blocked when `find` is not found or matches more than once without `all`
  - Neither may touch `## Rules`: a `## Rules` heading as the section or inside the new text is Blocked, naming `patch_node_rules`
- **Node rules section.** A node's rules are the `## Rules` section of its territory body: from a line that is exactly `## Rules` to the next level-1 or level-2 heading or end of file. At most one such section per file
  - `splitNodeRules(body)` → `{ body, rules }` — `body` has the section removed, `rules` is its trimmed text (empty string when absent)
  - `joinNodeRules(body, rules)` — inserts the section immediately before `## Attachments` when present, else appends it; an empty `rules` adds no section (no empty heading)
  - `writeNodeRules(node, rules)` — the only writer of the section. Writes the live `<id>.mdx` and, when an evolution is open, the same text into `<id>.next.mdx`; re-syncs the mirror twin when no evolution is open. Does not touch frontmatter, state, or edges. Blocked on an inactive node (`isInactiveNode`: retired or a closed Bug) or on rules containing a level-1/2 heading line. Returns the slots and repo-relative paths written
  - Discover reads `node.rules` from the live `<id>.mdx` via `splitNodeRules`
  - Body writes (`patch_node_territory`, `open_next` seeding, promote) keep the rules text unchanged; a body that itself contains a `## Rules` heading is rejected with `Blocked:` naming `patch_node_rules`. Promote keeps the live file's rules
  - Territory reads for tools split the body from the rules with `splitNodeRules` (`get_node_context` returns the body without the section plus `rules` separately)
  - **Adoption.** A `## Rules` section already in a body is read as that node's rules on the next load; nothing migrates it and nothing warns. SPEC §6.1.1 documents this so authors rename such a heading first
  - **Fences.** Parsing is line-based and ignores code fences; a heading-like line inside a fence counts as a heading (documented in SPEC §6.1.1)
- Checkbox counting and label comparison ignore the Rules and Decisions sections, so neither affects Minimum Territory Shape, Atomic Op counting, or mirror-twin equality (the twin is a byte copy, sections included)
- **Decisions section.** A node's decisions are the `## Decisions` section of a territory file (live or open next): from a line that is exactly `## Decisions` to the next level-1/2 heading or end of file; at most one per file. Each entry is a `### <id>` heading (`DECISION_ID_PATTERN`) followed by `- Decision: …`, `- Alternatives:` with one indented `  - …` line per alternative, `- Why: …`, and optional `- Consequences: …`, `- Supersedes: <id>`, `- Change: <id>`, `- Date: YYYY-MM-DD`. Values are single lines. Lines that are not part of an entry are kept as written and not parsed
  - `splitNodeDecisions(text)` → `{ body, section }`; `joinNodeDecisions(body, section)` inserts it before `## Rules` when present, else before `## Attachments`, else at the end, so a file reads Decisions, Rules, Attachments; `parseDecisions(section)` → `DecisionRecord[]`; `formatDecisionEntry(record)`; `withoutOwnedSections(text)` is the body without the Rules and Decisions sections, the one helper that node context, stale text, and checkbox counting read
  - `appendDecision(node, record)` — the only writer. Appends one entry to the active slot (the open next file while a shipped node evolves, else the live file, then re-syncs the mirror twin) and keeps the file's line endings. Frontmatter, state, and readiness are untouched. Blocked on an inactive node. Returns the slot and the paths written
  - Discover sets `node.decisions` from the live file and `node.next.decisions` from an open next file
  - Body writes (`patch_node_territory` body, section, replace, toggles) keep the section unchanged; a body, section text, or replacement containing a `## Decisions` heading, or `section: "## Decisions"`, is Blocked naming `record_decision`. `open_next` copies the section with the body (and writes `opened_at` on the next file; promote and discard drop it), promote ships the next file's section, discard drops what the revision recorded
  - **Adoption.** A `## Decisions` heading already in a body becomes the decisions section on the next load; only its `### d-…` entries are parsed. SPEC documents this
- **Checkbox toggles.** `toggleCheckboxesInBody` returns `{ body, toggled }`. A `contains` that matches more than one checkbox line is Blocked with the matching lines unless the toggle passes `all: true`; zero matches stay Blocked. `note` ticks the line and appends ` — note: <text>`; `not_applicable` ticks it and appends ` — n/a: <reason>`; unticking strips an annotation and re-toggling replaces it, so the item's own wording never changes
- **Readiness demotion.** `demoteReadySlot(node, slot)` sends a `ready` slot to `draft`. The contract writers call it after writing and return whether they did: `patchNodeTerritory` (any field but `change` / `change_ref`, as `readinessReset`), `writeImplementsFrontmatter` (only when the list changes), `addEdgeToFrontmatter`, and `removeEdgesFromFrontmatter`. `validateChangeInput` is the one change-id validator
- **Annotated completion.** `countCheckboxesInText` counts an `— n/a:` line with an empty reason as unchecked; `checkboxLabels` strips annotations
- **Change frontmatter.** `change` / `change_ref` scalars are read from the live file and the open next file; `writeChangeFrontmatter(node, { change, change_ref }, slot)` sets or clears them (empty string clears) without touching state or `updated_at`; `patchNodeTerritory` takes them as patch fields (validated slug / one-line ref); `create_node`, `open_next`, and first ship call the writer; `promoteNextSlot` drops them because it rebuilds the live frontmatter
- **Stale live labels.** While a shipped node has an open next, its live label is absent or names the revision's own change. `writeChangeFrontmatter` on the next slot ends with `dropStaleLiveLabel(node)`, which clears a live label that differs from the next slot's change, and returns the cleared id (`undefined` otherwise); `patchNodeTerritory` on the next slot does the same after a `change` write and returns it as `replaced_change`. `open_next`, `patch_node_territory`, and `set_implementation_files` report it, so `discard_next` can only restore a label of the revision's own change
- **Neighbor label.** `writeNeighborLabel(node, change)` sets (or with `""` clears) the live `change` scalar of a shipped node with no open next and re-syncs its mirror twin. It returns `{ twin, replaced? }`: `twin` is null when the label already had that value, `replaced` is the previous id when a different one was set. A node that fails `isNeighborNode` (`f-domain-model`; a retired node included) is Blocked
- **In-place claim marker.** `added_claims` is a frontmatter list parsed like `implements` (`parseFrontmatter`, `node.added_claims`, `nodeToRecord`). `writeImplementsFrontmatter(node, files, slot, addedInPlace?)` on the live slot merges `addedInPlace` into the stored list and keeps, sorted and deduped, only the entries the list still keeps (`claimListKeeps`: verbatim, or under a non-glob directory entry) that the body (owned sections excluded) does not yet name as a whole path (`namesPath`: `pkg/a.ts` is not named by `pkg/a.tsx`, `pkg/a/` not by `pkg/a/b.ts`); an empty list removes the field. A live `patchNodeTerritory` write prunes the entries its new body names. `clearAddedClaims(node)` removes the list and leaves the twin re-sync to its caller. `promoteNextSlot` rebuilds the live frontmatter and drops it
- **Deleted next-slot files.** `deleteNextSlotFiles` lists every file it deletes under `next-attachments/` (e.g. `.gitkeep`) as well as the folder
- **Search body reader.** `territoryBodyReader()` is `readMarkdown` plus a `stamp(node, slot)`: the graph cache's `contentKey` for a node a load returned (no file access), else the slot file's size and mtime. `f-graph-search` keys its heading memo on it, so a body edited outside MCP is re-read
- **Cached load.** `discoverNodes()` lists every node folder (`{ id, type, abs, rel }`) and hands `parseNodeFolder` (the live file, the optional next slot, the same Blocked errors) to `graphCacheFor(projectRoot(), parserVersion()).load`, where `parserVersion()` is the package version plus a hash of the built `store.js`, `types.js`, `claims.js`, and `cache.js`, so a rebuild that changes the parser without a version bump drops the old build's records; with the cache off it parses every folder. Records come back as copies the caller may mutate, sorted by id. A legacy duplicate is still removed by the parse that first sees it
- **Legacy removal log.** `restoreRemovedLegacyFiles(entries)` puts drained entries back at the head of the log, so an async tool result reports the legacy files its own graph load removed (`if-mcp-tools`)
- **Linked tests.** `tests` is a frontmatter list parsed like `implements` (`parseFrontmatter`, `node.tests`, `nodeToRecord`) and, like `added_claims`, kept verbatim by frontmatter rewriters that do not know it. `writeTestsFrontmatter(node, entries)` is its only writer: it validates each entry as a claim path (`validateClaimPath`: no `..`, no absolute path, nothing under `mindplan/`), dedupes and sorts, writes the same list to the live `<id>.mdx` and, while a revision is open, to `<id>.next.mdx`, re-syncs the mirror twin when none is open, and returns `{ paths, changed }`. An empty list removes the field. It never touches state, `updated_at`, or readiness. Blocked on a Journey, a Bug, or a retired node. `openNextSlot` copies the list with the live file, and `promoteNextSlot` writes the next file's list (equal to live) into the rebuilt live frontmatter

Depends on: `f-domain-model`, `f-source-index`.

### Project version stamp (`version.ts`)

- `mindplan/version.json` records which package last migrated the tree: `{ "package": "<semver>", "graph": <GRAPH_VERSION> }`. Only `init` writes it (`writeProjectVersion`).
- `packageVersion()` reads `version` from this package's own `package.json` by walking up from the module (works from `dist/` and from a consumer's `node_modules`); `f-mcp-runtime` reports the same value on `initialize`.
- `projectVersionStatus()` compares the stamp with the running package and graph format and never throws. Status: `current`, `missing` (no stamp), `invalid` (unreadable stamp), `behind` (stamp older than the package, or older graph format), `ahead` (stamp newer than the package, or newer graph format). Every status but `current` carries one `warning` sentence naming the fix: `behind` / `missing` / `invalid` → run `mindplan-mcp init` with the installed version; `ahead` → upgrade `mindplan-mcp`.
- Versions compare as SemVer `major.minor.patch`; a pre-release sorts before its release.

- **Aliases.** `aliases` is a frontmatter list parsed like `tests` and kept verbatim by rewriters that do not know it; each entry is written as a JSON string (free text: spaces, colons, other scripts) and decoded on parse. `normalizeAliases(id, entries)` trims, collapses whitespace, drops empties, deduplicates ignoring case, and Blocks an entry over `MAX_ALIAS_CHARS` (60) or more than `MAX_ALIASES` (20). `writeAliasesFrontmatter(node, entries)` is the only writer: any node type, not a retired or closed one; the same list on live and an open next, mirror twin re-synced, state / `updated_at` / readiness untouched; an empty list removes the field. `promoteNextSlot` writes the next file's list into the rebuilt live frontmatter; `nodeToRecord` carries it
- **Literal replacements.** Every frontmatter write that splices free text (aliases, tests, title, description, `change_ref`) passes a replacer function to `String.replace`, so a `$` in the text is written as is and never read as a replacement pattern

## Acceptance Criteria

- Standing twin after first ship; open_next is a state flip
- Live MCP writes keep the twin true when no evolution is open, and the writer hands back the twin path it re-synced
- Ship/discard restore mirror; retire/unship delete it
- `writeNodeRules` then a `patch_node_territory` body write leaves the rules text unchanged
- A body containing `## Rules` is rejected; an empty rules string removes the section
- With an open evolution, rules written to live are also in the next file, and promote keeps exactly one Rules section
- Rules checkboxes (`- [ ]`) inside the section are not counted as Atomic Ops
- CRLF territory stays CRLF through a rules write and a body write
- Writing rules to a retired node or a closed Bug is Blocked
- A `mounts` edge round-trips through link, unlink, open_next, and ship
- A section patch changes only that section; a replace changes exactly one occurrence; the Rules section cannot be patched through either
- Verified via `npm test`
- A `contains` matching two checkbox lines is Blocked and the Blocked text lists both lines; with `all: true` both toggle
- A note or not-applicable reason is appended to the line without rewording it; unticking removes it
- `change` / `change_ref` round-trip through the live and next files and are gone after ship
- `appendDecision` then a `patch_node_territory` body write leaves the decisions section unchanged; a body containing `## Decisions` is Blocked
- On a shipped node with an open evolution the entry lands in `<id>.next.mdx` only; promote keeps it in `<id>.mdx` and discard drops it
- On a shipped node with no open evolution the entry lands in `<id>.mdx` and the mirror twin still passes `check`
- Recording on a `ready` revision does not reset readiness
- A file with both sections keeps the order Decisions, Rules, Attachments, and CRLF territory stays CRLF
- A parsed entry round-trips through `formatDecisionEntry`; an alternative that reads like a checkbox is not counted as one
- `writeNeighborLabel` on a shipped node with no open next writes the live `change` and the twin and reports the replaced id; on a node with an open next, or one not shipped, it is Blocked
- An `added_claims` entry stays through claim writes until the body names it; a body patch that names it removes it, and removing the last entry removes the field
- `deleteNextSlotFiles` lists `next-attachments/.gitkeep`
- Moving an open revision's change id off its inherited live label clears the live label and returns the cleared id
- A body naming only a longer path keeps the `added_claims` entry; naming the exact path (even before a period) removes it
- `writeTestsFrontmatter` writes the list to live and an open next, re-syncs the twin when no revision is open, and leaves a `ready` revision ready
- The `tests` list survives `open_next`, body, claim, edge, and change writes, and ship; an empty list removes the field

- Aliases round-trip JSON-quoted, survive other territory writes and promotion, and `[]` removes them
- `loadGraph` returns the same graph with the cache on, off, and in a second process; a Blocked territory file stays Blocked on every load

## Decisions

### d-decisions-slot-bound

- Decision: Decisions belong to a slot: a revision records them on its next file and they ship or are discarded with it.
- Alternatives:
  - Write them to live and next like node rules (a discarded revision would leave its reasoning on the live node)
- Why: A decision explains one revision's design; if the revision never ships, neither does its reasoning.
- Change: decision-records
- Date: 2026-10-20

### d-decisions-keep-readiness

- Decision: Recording a decision never resets a ready revision to draft.
- Alternatives:
  - Treat it as a contract write (every reason written down after review would undo the review)
- Why: A decision explains the contract; it does not change it, and the gate asks for one late in the pipeline.
- Change: decision-records
- Date: 2026-10-20

### d-writers-return-twin-path

- Decision: Each store writer that re-syncs a mirror twin returns the twin path it wrote, and the tool handler adds it to changed_files.
- Alternatives:
  - Collect re-synced twins in a store-level log that the MCP wrapper drains into every result, as it does for removed legacy files
  - Have handlers infer the twin from node state (shipped, no open evolution) instead of the store reporting it
- Why: The store already reports what it wrote (writeMirrorTwin, writeNodeRules, appendDecision); a return value keeps the report beside the write and in the types, with no module state a failed call could leak into the next result, and inferring from state can list a twin no write touched.
- Consequences: A new live writer must hand its twin path to its caller; twins.test.mjs diffs every write against disk so a missed twin fails npm test.
- Date: 2026-10-20

### d-frontmatter-body-separator

- Decision: Territory writes keep the newline after the closing frontmatter fence as they found it; a whole-body write puts one blank line above a body that starts with text and keeps the blank lines a body already starts with; promote keeps the next file's layout and line endings.
- Alternatives:
  - Normalize every write to exactly one blank line (each unrelated patch would silently rewrite a file's layout, and the clean-up would spread across unrelated diffs)
  - Write a whole body right after the fence, verbatim (a body that starts with its heading would lose the blank line every scaffolded file has)
- Why: A patch should change only what it names, and a whole-body write should match the scaffold layout without discarding blank lines the caller sent; existing runs are collapsed once, on purpose, not as a side effect.
- Consequences: Files with long runs keep them until a whole-body write collapses them; get_node_context bodies round-trip byte for byte.
- Date: 2026-10-20

### d-version-stamp-file

- Decision: The package version that last migrated a project lives in its own file, mindplan/version.json ({ package, graph }), written only by init; a mismatch with the running package warns (get_project, run_check) and never Blocks.
- Alternatives:
  - A field in mindplan/config.json (config is user-edited through patch_config, so a stamp there could be changed without running the migrations it claims)
  - A stamp per agent file, e.g. a version line in playbook.md (does not cover graph-format migrations and makes the copies differ from the templates)
  - Block every tool on a mismatch (one stale stamp after an npm update would stop all planning until init runs)
- Why: Init is the only step that both refreshes the package-owned agent files and runs graph migrations, so the stamp must change only when init runs; projects now upgrade the package through npm, and a warning tells the agent to rerun init without stopping work.
- Consequences: A release that changes the playbook, skills, or graph format is picked up by a project only after it reruns init; a future graph-format bump can turn the ahead/behind graph case into a Block.
- Change: project-version-stamp
- Date: 2026-10-23
