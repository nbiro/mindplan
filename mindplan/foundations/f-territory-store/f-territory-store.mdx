# Territory store

## Purpose

Infra — persist territory through the store only. A shipped node is one file, `<id>.mdx`; `open_next` writes `<id>.next.mdx` from it, and ship, discard, unship, and retire delete the next file again, so a live write never has a second copy to keep in step and every PR shows one copy of a change. Own `writeProjectBrief` for `mindplan/project.md` and, for every node, the `## Rules` section of its `<id>.mdx`. That section has one writer (`writeNodeRules`); body writes can neither read it as prose nor clobber it, otherwise a territory rewrite would silently erase rules. Because the heading is the storage format, a `## Rules` section that already existed becomes that node's rules, so the contract names that adoption instead of leaving it to surprise a consumer. Small body fixes (one section, one phrase) are first-class writes so an agent does not resend a whole body to change a line. The store also owns each node's `## Decisions` section: decision records written only by `appendDecision`, one entry per decision and never rewritten, so the reasoning trail cannot be edited away by a body rewrite. Unlike rules, decisions are slot-bound: while a shipped node evolves they are recorded on its next file, they ship with the revision, and a discarded revision takes its decisions with it. Recording a decision never resets readiness: it explains the contract, it does not change it. The live `added_claims` list marks claims added in place; the store drops each entry once the body names it, so the marker clears itself through ordinary territory writes. Loading the graph goes through the graph cache (`f-graph-cache`): the store lists the node folders and owns the parser, so a load parses only folders the cache cannot vouch for and returns what a full parse would.

## Shared Substrate Spec

Intended files: `src/foundations/f-territory-store/`

- **No standing twin.** A shipped node has only `<id>.mdx` until `open_next`; every live write touches the live file alone. A next file exists only while a revision is open
  - Discover: a next file in a pipeline state sets `node.next`. A `state: mirror` file left by a release before 0.8.0 is not a revision and does not set it; `isLegacyMirror(node)` names one and `removeLegacyMirror(node)` deletes it and its empty `next-attachments/` (`upgrade_project`); a next-slot write on such a node is Blocked naming `upgrade_project`
  - `openNextSlot` writes `<id>.next.mdx` from the live file (state `draft`, `updated_at` / `opened_at` now, optional title and description; a leftover mirror file is replaced) and gives the revision a fresh Atomic Ops list (below)
  - `promoteNextSlot` writes the live file from the next file, copies `next-attachments/` into `attachments/`, then deletes the next file and `next-attachments/`; `discardNextSlot` deletes them; `deleteNextSlotFiles` lists every path it deletes (the next file, each file under `next-attachments/`, the folder) and is also used by unship and retire
  - A next-slot write on a node with no open revision is Blocked (call `open_next` first)
  - Writers report what they wrote (`writeNodeRules` / `appendDecision` `paths`, `deleteNextSlotFiles`); a live write never touches a second file
- **Atomic Ops live in unshipped slots only.** A node shows its current state; the shipped ledger is history and git keeps it. `ATOMIC_OPS_HEADINGS` is `Atomic Ops` for every pipeline type plus `Checklist` for a Foundation; Bugs are untouched (`Fix Checklist`)
  - `defaultAtomicOps(type)` returns the scaffold's default checklist lines; `scaffoldTerritory` and `openNextSlot` both use it
  - `withoutAtomicOps(body, type)` removes every Atomic Ops section (heading to the next level-1/2 heading, fence-aware like `replaceSectionInBody`) and keeps the file's line endings; Rules, Decisions, and every other section stay
  - `withFreshAtomicOps(body, type)` replaces the content of the first Atomic Ops section with the defaults and drops any further one; with none it inserts `## Atomic Ops` before the first of `## Decisions`, `## Rules`, `## Attachments`, else at the end
  - `promoteNextSlot` writes the promoted body through `withoutAtomicOps`; `stripLiveAtomicOps(node)` does the same to the live file of a node shipped in place (first ship, init) and returns whether it changed it; `freshLiveAtomicOps(node)` writes the live file through `withFreshAtomicOps` for a node taken back before ship (`force_unship`), so it has a ledger again for its next ship
  - `openNextSlot` writes the next file's body through `withFreshAtomicOps`, so a revision can never ship on the ticks of the release before it (the Completion Check sees its own open items)
- **Section read.** `readSectionFromBody(body, heading)` returns the text under one level-2 heading (same heading matching as `replaceSectionInBody`, through the exported `normalizeHeadingName` that readers use to echo the heading; a missing heading is Blocked and lists the sections)
- A whole-body write converts the new body to the file's own line endings, so CRLF territory stays CRLF
- `writeProjectBrief` for MCP `patch_project_description` and `patch_project_rules`
- **`mounts` edge field.** `mounts` is a frontmatter edge array like `exposes`: parsed, written, removed by `unlink`, copied by `open_next`, promoted on ship, and a pipeline node with an open evolution writes it to the next slot
- **Section and replace patches.** `patchNodeTerritory` also takes `section: { heading, text }` and `replace: { find, with, all? }`
  - `replaceSectionInBody(body, heading, text)` rewrites the lines under one level-2 heading (heading line and other sections untouched, line endings kept; a `## ` line inside a fenced code block is code, not a heading); a missing heading is Blocked and lists the sections
  - `replaceTextInBody(body, find, with, all?)` replaces one exact piece; Blocked when `find` is not found or matches more than once without `all`
  - Neither may touch `## Rules`: a `## Rules` heading as the section or inside the new text is Blocked, naming `patch_node_rules`
- **Node rules section.** A node's rules are the `## Rules` section of its territory body: from a line that is exactly `## Rules` to the next level-1 or level-2 heading or end of file. At most one such section per file
  - `splitNodeRules(body)` → `{ body, rules }` — `body` has the section removed, `rules` is its trimmed text (empty string when absent)
  - `joinNodeRules(body, rules)` — inserts the section immediately before `## Attachments` when present, else appends it; an empty `rules` adds no section (no empty heading)
  - `writeNodeRules(node, rules)` — the only writer of the section. Writes the live `<id>.mdx` and, when an evolution is open, the same text into `<id>.next.mdx`. Does not touch frontmatter, state, or edges. Blocked on an inactive node (`isInactiveNode`: retired or a closed Bug) or on rules containing a level-1/2 heading line. Returns the slots and repo-relative paths written
  - Discover reads `node.rules` from the live `<id>.mdx` via `splitNodeRules`
  - Body writes (`patch_node_territory`, `open_next` seeding, promote) keep the rules text unchanged; a body that itself contains a `## Rules` heading is rejected with `Blocked:` naming `patch_node_rules`. Promote keeps the live file's rules
  - Territory reads for tools split the body from the rules with `splitNodeRules` (`get_node_context` returns the body without the section plus `rules` separately)
  - **Adoption.** A `## Rules` section already in a body is read as that node's rules on the next load; nothing migrates it and nothing warns. SPEC §6.1.1 documents this so authors rename such a heading first
  - **Fences.** Parsing is line-based and ignores code fences; a heading-like line inside a fence counts as a heading (documented in SPEC §6.1.1)
- Checkbox counting and label comparison ignore the Rules and Decisions sections, so neither affects Minimum Territory Shape or Atomic Op counting
- **Decisions section.** A node's decisions are the `## Decisions` section of a territory file (live or open next): from a line that is exactly `## Decisions` to the next level-1/2 heading or end of file; at most one per file. Each entry is a `### <id>` heading (`DECISION_ID_PATTERN`) followed by `- Decision: …`, `- Alternatives:` with one indented `  - …` line per alternative, `- Why: …`, and optional `- Consequences: …`, `- Supersedes: <id>`, `- Change: <id>`, `- Date: YYYY-MM-DD`. Values are single lines. Lines that are not part of an entry are kept as written and not parsed
  - `splitNodeDecisions(text)` → `{ body, section }`; `joinNodeDecisions(body, section)` inserts it before `## Rules` when present, else before `## Attachments`, else at the end, so a file reads Decisions, Rules, Attachments; `parseDecisions(section)` → `DecisionRecord[]`; `formatDecisionEntry(record)`; `withoutOwnedSections(text)` is the body without the Rules and Decisions sections, the one helper that node context, stale text, and checkbox counting read
  - `appendDecision(node, record)` — the only writer. Appends one entry to the active slot (the open next file while a shipped node evolves, else the live file) and keeps the file's line endings. Frontmatter, state, and readiness are untouched. Blocked on an inactive node. Returns the slot and the paths written
  - Discover sets `node.decisions` from the live file and `node.next.decisions` from an open next file
  - Body writes (`patch_node_territory` body, section, replace, toggles) keep the section unchanged; a body, section text, or replacement containing a `## Decisions` heading, or `section: "## Decisions"`, is Blocked naming `record_decision`. `open_next` copies the section with the body (and writes `opened_at` on the next file; promote drops it), promote ships the next file's section, discard drops what the revision recorded
  - **Adoption.** A `## Decisions` heading already in a body becomes the decisions section on the next load; only its `### d-…` entries are parsed. SPEC documents this
- **Checkbox toggles.** `toggleCheckboxesInBody` returns `{ body, toggled }`. A `contains` that matches more than one checkbox line is Blocked with the matching lines unless the toggle passes `all: true`; zero matches stay Blocked. `note` ticks the line and appends ` — note: <text>`; `not_applicable` ticks it and appends ` — n/a: <reason>`; unticking strips an annotation and re-toggling replaces it, so the item's own wording never changes
- **Readiness demotion.** `demoteReadySlot(node, slot)` sends a `ready` slot to `draft`. The contract writers call it after writing and return whether they did: `patchNodeTerritory` (any field but `change` / `change_ref`, as `readinessReset`), `writeImplementsFrontmatter` (only when the list changes), `addEdgeToFrontmatter`, and `removeEdgesFromFrontmatter`. `validateChangeInput` is the one change-id validator
- **Annotated completion.** `countCheckboxesInText` counts an `— n/a:` line with an empty reason as unchecked; `checkboxLabels` strips annotations
- **Change frontmatter.** `change` / `change_ref` scalars are read from the live file and the open next file; `writeChangeFrontmatter(node, { change, change_ref }, slot)` sets or clears them (empty string clears) without touching state or `updated_at`; `patchNodeTerritory` takes them as patch fields (validated slug / one-line ref); `create_node`, `open_next`, and first ship call the writer; `promoteNextSlot` drops them because it rebuilds the live frontmatter
- **No labels.** The store writes a `change` scalar only on a slot that holds a revision (the next file, or the live file before first ship); it has no label writer and no live-label cleanup. Migration level 2 strips a leftover live scalar with `writeChangeFrontmatter(node, { change: "", change_ref: "" }, "current")`
- **In-place claim marker.** `added_claims` is a frontmatter list parsed like `implements` (`parseFrontmatter`, `node.added_claims`, `nodeToRecord`). `writeImplementsFrontmatter(node, files, slot, addedInPlace?)` on the live slot merges `addedInPlace` into the stored list and keeps, sorted and deduped, only the entries the list still keeps (`claimListKeeps`: verbatim, or under a non-glob directory entry) that the body (owned sections excluded) does not yet name as a whole path (`namesPath`: `pkg/a.ts` is not named by `pkg/a.tsx`, `pkg/a/` not by `pkg/a/b.ts`); an empty list removes the field. A live `patchNodeTerritory` write prunes the entries its new body names. `clearAddedClaims(node)` removes the list. `promoteNextSlot` rebuilds the live frontmatter and drops it
- **Search body reader.** `territoryBodyReader()` is `readMarkdown` plus a `stamp(node, slot)`: the graph cache's `contentKey` for a node a load returned (no file access), else the slot file's size and mtime. `f-graph-search` keys its heading memo on it, so a body edited outside MCP is re-read
- **Cached load.** `discoverNodes()` lists every node folder (`{ id, type, abs, rel }`) and hands `parseNodeFolder` (the live file, the optional next slot, the same Blocked errors) to `graphCacheFor(projectRoot(), parserVersion()).load`, where `parserVersion()` is the package version plus a hash of the built `store.js`, `types.js`, `claims.js`, and `cache.js`, so a rebuild that changes the parser without a version bump drops the old build's records; with the cache off it parses every folder. Records come back as copies the caller may mutate, sorted by id. A legacy duplicate is still removed by the parse that first sees it
- **Legacy removal log.** `restoreRemovedLegacyFiles(entries)` puts drained entries back at the head of the log, so an async tool result reports the legacy files its own graph load removed (`if-mcp-tools`)
- **Linked tests.** `tests` is a frontmatter list parsed like `implements` (`parseFrontmatter`, `node.tests`, `nodeToRecord`) and, like `added_claims`, kept verbatim by frontmatter rewriters that do not know it. `writeTestsFrontmatter(node, entries)` is its only writer: it validates each entry as a claim path (`validateClaimPath`: no `..`, no absolute path, nothing under `mindplan/`), dedupes and sorts, writes the same list to the live `<id>.mdx` and, while a revision is open, to `<id>.next.mdx`, and returns `{ paths, changed }`. An empty list removes the field. It never touches state, `updated_at`, or readiness. Blocked on a Capability, a Bug, or a retired node. `openNextSlot` copies the list with the live file, and `promoteNextSlot` writes the next file's list (equal to live) into the rebuilt live frontmatter

### Project version stamp (`version.ts`)

- `mindplan/version.json` records which package last set up or upgraded the tree and the migration level it reached: `{ "package": "<semver>", "graph": <GRAPH_VERSION>, "migrations": <level> }`. `readProjectVersion()` returns `null` when the file is missing, `"invalid"` when it cannot be parsed or lacks a semver `package` and an integer `graph`, and reads an absent or non-integer `migrations` as `0` (stamps written by init). `writeProjectVersion(version)` writes all three fields; only `stampGraph` (`f-graph-migrations`) calls it.
- `packageRoot()` is the directory of this package's own `package.json`, found by walking up from the module (works from `dist/` and from a consumer's `node_modules`); setup and upgrade read their templates from it. `packageVersion()` reads `version` from that file; `f-mcp-runtime` reports the same value on `initialize`.
- Comparing the stamp with the server (and the Block) belongs to `graphStatus` / `versionGate` in `f-graph-migrations`; this file only reads and writes the stamp.
- `compareVersions(a, b)` compares SemVer `major.minor.patch`; a pre-release sorts before its release.

- **Aliases.** `aliases` is a frontmatter list parsed like `tests` and kept verbatim by rewriters that do not know it; each entry is written as a JSON string (free text: spaces, colons, other scripts) and decoded on parse. `normalizeAliases(id, entries)` trims, collapses whitespace, drops empties, deduplicates ignoring case, and Blocks an entry over `MAX_ALIAS_CHARS` (60) or more than `MAX_ALIASES` (20). `writeAliasesFrontmatter(node, entries)` is the only writer: any node type, not a retired or closed one; the same list on live and an open next, state / `updated_at` / readiness untouched; an empty list removes the field. `promoteNextSlot` writes the next file's list into the rebuilt live frontmatter; `nodeToRecord` carries it
- **One blank line below the frontmatter.** Every write of a node file (`writeMarkdown`, `open_next`, and each frontmatter rewriter) goes through `writeTerritoryFile`, which applies `oneBlankLineBelowFrontmatter`: exactly one blank line between the closing fence and the body, none above an empty body, in the file's own line endings. `splitContext` puts the newline after the fence and every blank line below it in `separator`, so `body` starts at its first text and `get_node_context` never returns leading blank lines. Runs of blank lines left by releases before 0.2.0 collapse on the node's next write
- **Literal replacements.** Every frontmatter write that splices free text (aliases, tests, title, description, `change_ref`) passes a replacer function to `String.replace`, so a `$` in the text is written as is and never read as a replacement pattern
- **Lock-tolerant I/O.** Every read, write, copy, and removal of a file under `mindplan/` in `store.ts`, `project.ts`, and `version.ts` goes through the `f-source-index/io.ts` wrappers (`readFileRetry`, `writeFileRetry`, `copyFileRetry`, `unlinkRetry`; `fs.rmSync` with `RM_MAX_RETRIES` for `next-attachments/`), so a lock another process holds for a moment is waited out (decision `d-plan-io-retry-in-source-index`, Bug `bug-windows-transient-file-lock`).

- **Planned edges.** The live file holds `planned:` as a named list, one `<change> <edge_type> <target>` item each, kept verbatim by every frontmatter rewriter. `writePlannedEdges(node, entries)` replaces it (removed when empty), keeping any item it cannot parse verbatim. `openNextSlot` never copies `planned:` (nor `attributed:`) into the next file; the handler applies the entries of the revision's change to the next slot's edges and leaves them on live. `promoteNextSlot` keeps the live entries of every other change and drops those of the change that shipped. A discard leaves them, so they apply again when the change reopens the node
- **Attributed files.** `attributed:` is a named list on the slot that holds the revision (`<id>.next.mdx`, or `<id>.mdx` before first ship); `writeAttributedFrontmatter(node, files, slot)` replaces it and reports a readiness reset like a claim write. Promotion does not carry it, and a first ship clears it from the live file (`clearAttributed`): once shipped, the file is simply part of its owner's folder

- **Revision count at ship.** First ship writes `revisions: <previous + 1>` (`1` for a node that never shipped) on the live file with `writeRevisionFields(node, { revisions, split_at?, split_into? })`. `promoteNextSlot(node, state, shippedAt, { splitInto? })` writes `revisions: <live + 1>` (live absent counts as 1) and keeps the live `split_at` / `split_into`; with `splitInto` (the parts this revision split out, found by the steer handler) it sets `split_at` to the new count and adds the ids to `split_into`. Each ship also writes `churn` (`nextChurn(previous, previousShippedAt, shippedAt, halfLifeDays)`: the previous value decayed over the days between the two ships, plus 1; 0 when the ship records a split), rounded to three decimals. `open_next` copies the fields into the next file like any frontmatter; only a ship changes them. `force_unship` keeps `revisions` and the split record, and writes `churn` decayed to the unship with `churn_at` (the time it is as of, since `shipped_at` goes away); the next ship decays from `churn_at` and drops it. `writeRevisionFields` takes `churn_at` (a time, or null to remove it).
- **Declared splits.** `writeNextSplitInto(node, ids)` writes the open next file's `split_into` as the live list plus `ids` (the live file is untouched until the revision ships); `NextSlot.split_into` reads it back.
- **`keep_whole` in decision records.** `record_decision` writes a `keep_whole: true` line in the record when given; the parser reads it back, and a record without it has none.

- **Type folders.** One folder per type under `mindplan/`: `capabilities/`, `foundations/`, `interactions/`, `interfaces/`, `bugs/`. A node's type comes from its folder. The store never reads `journeys/`; only migration level 3 (`f-graph-migrations`) knows it. A live file whose type is `Journey` (a folder moved by hand) is `Blocked:` naming `upgrade_project`, which rewrites it

- **Open revisions (0.18.0).** A shipped node's open revisions live in `revisions/<change>/<id>.mdx` with `attachments/` and `decisions/` beside it; the loader parses every folder into `open_revisions` and never sets `next`. Revision frontmatter is flat: scalars, `<edge>_add` / `<edge>_remove`, `implements_add` / `implements_remove`, `tests_add` / `tests_remove`, `attributed`, `split_into`, `base` (`title=…`, `section:<heading>=…`), and `conflicts`. `revisions.ts` holds `openRevision`, `discardRevision`, `shipRevision` (writes live ⊕ revision, moves its decision files, deletes the folder, then rebases every sibling with `rebase`), `writeRevisionDelta`, `writeRevisionBody`, and `resolveConflict`. `TerritorySlot` becomes `{ kind: "live" } | { kind: "revision", change }`; the old `<id>.next.mdx` reader moves to the migration
- **Decision files.** `decisions-store.ts`: `readDecisionFiles(dir)`, `appendDecisionFile(dir, record)` (one `<decision-id>.md` per decision, never rewritten), `moveDecisions(from, to)`; the `## Decisions` body section is no longer written
- **Derived map.** Writes no longer list `mindplan/map.md` in `changed_files`

## Graph root per call

`projectRoot()`, `mindplanRoot()`, the brief and version-stamp paths read the root of the current tool call (an `AsyncLocalStorage` scope the MCP mount opens from the call's `root` argument), else `MINDPLAN_ROOT`, else the working directory. Nothing writes `process.env.MINDPLAN_ROOT` at runtime. The legacy-file queue (`removedLegacyFiles`) is kept per root. One server can therefore write the graph of the main checkout and of any git worktree in the same session.

## Acceptance Criteria

- A Capability loads from `mindplan/capabilities/<id>/<id>.mdx` and is written there; a folder under `mindplan/journeys/` is not loaded

- After first ship a node has no next file; `open_next` writes one from live with a fresh Atomic Ops list, and ship and discard delete it with `next-attachments/`
- A shipped node's live file has no Atomic Ops section after first ship and after promotion; Rules, Decisions, and Attachments survive; `open_next` gives the next file one `## Atomic Ops` section of unticked defaults (a Foundation's `## Checklist` is replaced too), placed before Decisions / Rules / Attachments; a Bug's Fix Checklist is never touched
- `readSectionFromBody` returns one section's text and Blocks on a missing heading
- A live write on a shipped node changes only `<id>.mdx`
- Ship, discard, retire, and unship leave no next file or `next-attachments/`; promotion copies the revision's attachments into `attachments/` first
- A leftover `state: mirror` next file is not a revision: the node loads with no `next`, `open_next` replaces the file, and `removeLegacyMirror` deletes it
- `writeNodeRules` then a `patch_node_territory` body write leaves the rules text unchanged
- A body containing `## Rules` is rejected; an empty rules string removes the section
- With an open evolution, rules written to live are also in the next file, and promote keeps exactly one Rules section
- Rules checkboxes (`- [ ]`) inside the section are not counted as Atomic Ops
- CRLF territory stays CRLF through a rules write and a body write
- Writing rules to a retired node or a closed Bug is Blocked
- A `mounts` edge round-trips through link, unlink, open_next, and ship
- A section patch changes only that section; a replace changes exactly one occurrence; the Rules section cannot be patched through either
- Verified via `npm test`
- A `contains` matching two checkbox lines is Blocked and the Blocked text lists both lines; with `all: true` both toggle
- A note or not-applicable reason is appended to the line without rewording it; unticking removes it
- `change` / `change_ref` round-trip through the live and next files and are gone after ship
- `appendDecision` then a `patch_node_territory` body write leaves the decisions section unchanged; a body containing `## Decisions` is Blocked
- On a shipped node with an open evolution the entry lands in `<id>.next.mdx` only; promote keeps it in `<id>.mdx` and discard drops it
- On a shipped node with no open evolution the entry lands in `<id>.mdx` only
- Recording on a `ready` revision does not reset readiness
- A file with both sections keeps the order Decisions, Rules, Attachments, and CRLF territory stays CRLF
- A parsed entry round-trips through `formatDecisionEntry`; an alternative that reads like a checkbox is not counted as one
- An `added_claims` entry stays through claim writes until the body names it; a body patch that names it removes it, and removing the last entry removes the field
- `deleteNextSlotFiles` lists the next file, `next-attachments/.gitkeep`, and the folder
- Setting an open revision's change id writes the next file only; the live file is untouched
- A body naming only a longer path keeps the `added_claims` entry; naming the exact path (even before a period) removes it
- `writeTestsFrontmatter` writes the list to live and an open next and leaves a `ready` revision ready
- The `tests` list survives `open_next`, body, claim, edge, and change writes, and ship; an empty list removes the field
- Aliases round-trip JSON-quoted, survive other territory writes and promotion, and `[]` removes them
- `loadGraph` returns the same graph with the cache on, off, and in a second process; a Blocked territory file stays Blocked on every load
- A node file that starts with a run of blank lines below the frontmatter (LF or CRLF) has exactly one after any write, status moves included; `get_node_context` returns its body without leading blank lines, and a whole-body write of a body that starts with blank lines writes one
- A live `planned:` list survives an edge write, a claim write, and a territory patch; `open_next` leaves it out of the next file; promotion keeps another change's entries and drops the shipped change's
- `attributed:` is written to the revision's slot, survives other writes, and is gone from the live file after first ship and after promotion

- A first ship writes `revisions: 1`; promoting a revision writes `revisions: 2`; promoting with `splitInto: [f-a]` writes `split_at: 2` and `split_into: [f-a]`, and a later promotion keeps them
- `writeProjectVersion` writes `{ package, graph, migrations }`; `readProjectVersion` reads a stamp without `migrations` as level 0 and an unparseable one as `"invalid"`

## Cleanup (0.18)

The loader no longer reads `<id>.next.mdx` (a leftover is a version-gate upgrade; only `state: mirror` twins are removed); `scanFrontmatter` backs node and revision frontmatter; `writeRevision` applies body, scalars, and readiness to one loaded revision and writes it once; `loadRevision` reads one named revision; `listNodeFolders(root)` lists node folders for the loader, the after-merge check, and the version status; sections and checklists use `f-revision-model`'s scanner.

## Checklist items

Parsing and editing a checklist use one line splitter that keeps each line's own ending (CRLF, LF, or a lone CR), so a toggle always edits the line it matched; a line that is not there is Blocked.

Every checkbox the Completion Check counts (the whole body except the owned Rules and Decisions sections, and lines inside a fenced code block, which are example text) is a checklist item; it may end with a tag `{#<id>}` or `{#<id> <kind>}`: `id` is a stable slug, `kind` is `build` (the default when absent), `review` (a human or after-deploy check), or `deploy` (an environment variable or a migration applied live). Default Atomic Ops carry the same ids for every type: `{#spec}`, `{#impl}`, `{#verify}`. The tag is part of the line on disk and is hidden from nothing; `toggleCheckboxesInBody` matches an item by `id` or by its exact text (without tag and annotations), and refuses substring matches. `checklistItems(body)` returns `{ id?, kind, text, checked, line }` for every item, and counts by kind feed the Completion Check; `itemsOfLines` and `countCheckboxesInText` both skip fenced lines, so the two always agree.

**Ship onto live.** `assertRevisionShipsOntoLive` (`revisions.ts`) Blocks a revision whose rebase onto the current live would leave conflicts; `shipRevision` and the change walk's in-memory simulation both call it, so a walk foresees the conflict before it writes. `resolveConflict` writes a section the revision lacks where a rebase would put it (`replaceSection`: a `_preamble` at index 0); a changing resolution resets a ready or in-review revision to draft (as `carryRevision` does), and `opts.checkBody` lets the caller judge the resolved body before the write. `patchNodeTerritory` takes the same optional `checkBody(before, after)` hook, called on the final body before anything is written or assigned to the in-memory node (role, change, and change_ref are set only after every Blocked check). `appendChecklistItems` picks its insertion point from unfenced lines only and inserts after the last item's continuation lines (`afterContinuation`, judged against the item's content column, `itemContentColumn`: the marker plus the spaces after it, with tabs expanded to 4-column stops (`columnOf`, `indentColumn`); a fence indented to that column is skipped whole to its close; a fence or a thematic break at the item's indent or shallower ends the item; the insertion point is never inside a fence). A `take: "text"` resolution keeps the section's real heading line (from the revision, else live) and strips a ` (N)` duplicate-key suffix only when neither body has that heading. A graph load reports a cache hit only when it read at least one node folder and parsed none.
