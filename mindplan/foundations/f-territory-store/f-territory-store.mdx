# Territory store

## Purpose

Infra — persist territory through the store only; keep a shipped next file as a state-only twin (`mirror`). Sync the twin on every live write; restore on ship/discard; delete on unship/retire. Own `writeProjectBrief` for `mindplan/project.md` and, for every node, the `## Rules` section of its `<id>.mdx`. That section has one writer (`writeNodeRules`); body writes can neither read it as prose nor clobber it, otherwise a territory rewrite would silently erase rules. Because the heading is the storage format, a `## Rules` section that already existed becomes that node's rules, so the contract names that adoption instead of leaving it to surprise a consumer. Small body fixes (one section, one phrase) are first-class writes so an agent does not resend a whole body to change a line.

## Shared Substrate Spec

Intended files: `src/foundations/f-territory-store/`

- Discover: `mirror` does not set `node.next`; pipeline states do
- `writeMirrorTwin` / `syncMirrorAfterLiveWrite` / `deleteNextSlotFiles` / `mirrorDriftReason`
- `openNextSlot` flips mirror→draft (creates twin from live when missing); does not reset checkboxes
- `discardNextSlot` / `promoteNextSlot` restore the mirror twin (do not delete the next file)
- Reject writes aimed at a mirror file
- A whole-body write converts the new body to the file's own line endings, so CRLF territory stays CRLF
- `writeProjectBrief` for MCP `patch_project_description` and `patch_project_rules`
- **`mounts` edge field.** `mounts` is a frontmatter edge array like `exposes`: parsed, written, removed by `unlink`, copied by `open_next`, promoted on ship, and a pipeline node with an open evolution writes it to the next slot
- **Section and replace patches.** `patchNodeTerritory` also takes `section: { heading, text }` and `replace: { find, with, all? }`
  - `replaceSectionInBody(body, heading, text)` rewrites the lines under one level-2 heading (heading line and other sections untouched, line endings kept; a `## ` line inside a fenced code block is code, not a heading); a missing heading is Blocked and lists the sections
  - `replaceTextInBody(body, find, with, all?)` replaces one exact piece; Blocked when `find` is not found or matches more than once without `all`
  - Neither may touch `## Rules`: a `## Rules` heading as the section or inside the new text is Blocked, naming `patch_node_rules`
- **Node rules section.** A node's rules are the `## Rules` section of its territory body: from a line that is exactly `## Rules` to the next level-1 or level-2 heading or end of file. At most one such section per file
  - `splitNodeRules(body)` → `{ body, rules }` — `body` has the section removed, `rules` is its trimmed text (empty string when absent)
  - `joinNodeRules(body, rules)` — inserts the section immediately before `## Attachments` when present, else appends it; an empty `rules` adds no section (no empty heading)
  - `writeNodeRules(node, rules)` — the only writer of the section. Writes the live `<id>.mdx` and, when an evolution is open, the same text into `<id>.next.mdx`; re-syncs the mirror twin when no evolution is open. Does not touch frontmatter, state, or edges. Blocked on an inactive node (`isInactiveNode`: retired or a closed Bug) or on rules containing a level-1/2 heading line. Returns the slots and repo-relative paths written
  - Discover reads `node.rules` from the live `<id>.mdx` via `splitNodeRules`
  - Body writes (`patch_node_territory`, `open_next` seeding, promote) keep the rules text unchanged; a body that itself contains a `## Rules` heading is rejected with `Blocked:` naming `patch_node_rules`. Promote keeps the live file's rules
  - Territory reads for tools split the body from the rules with `splitNodeRules` (`get_node_context` returns the body without the section plus `rules` separately)
  - **Adoption.** A `## Rules` section already in a body is read as that node's rules on the next load; nothing migrates it and nothing warns. SPEC §6.1.1 documents this so authors rename such a heading first
  - **Fences.** Parsing is line-based and ignores code fences; a heading-like line inside a fence counts as a heading (documented in SPEC §6.1.1)
- Checkbox counting and label comparison ignore the Rules section, so it does not affect Minimum Territory Shape, Atomic Op counting, or mirror-twin equality (the twin is a byte copy, section included)
- **Checkbox toggles.** `toggleCheckboxesInBody` returns `{ body, toggled }`. A `contains` that matches more than one checkbox line is Blocked with the matching lines unless the toggle passes `all: true`; zero matches stay Blocked. `note` ticks the line and appends ` — note: <text>`; `not_applicable` ticks it and appends ` — n/a: <reason>`; unticking strips an annotation and re-toggling replaces it, so the item's own wording never changes
- **Readiness demotion.** `demoteReadySlot(node, slot)` sends a `ready` slot to `draft`. The contract writers call it after writing and return whether they did: `patchNodeTerritory` (any field but `change` / `change_ref`, as `readinessReset`), `writeImplementsFrontmatter` (only when the list changes), `addEdgeToFrontmatter`, and `removeEdgesFromFrontmatter`. `validateChangeInput` is the one change-id validator
- **Annotated completion.** `countCheckboxesInText` counts an `— n/a:` line with an empty reason as unchecked; `checkboxLabels` strips annotations
- **Change frontmatter.** `change` / `change_ref` scalars are read from the live file and the open next file; `writeChangeFrontmatter(node, { change, change_ref }, slot)` sets or clears them (empty string clears) without touching state or `updated_at`; `patchNodeTerritory` takes them as patch fields (validated slug / one-line ref); `create_node`, `open_next`, and first ship call the writer; `promoteNextSlot` drops them because it rebuilds the live frontmatter

Depends on: `f-domain-model`, `f-source-index`.

## Acceptance Criteria

- Standing twin after first ship; open_next is a state flip
- Live MCP writes keep the twin true when no evolution is open
- Ship/discard restore mirror; retire/unship delete it
- `writeNodeRules` then a `patch_node_territory` body write leaves the rules text unchanged
- A body containing `## Rules` is rejected; an empty rules string removes the section
- With an open evolution, rules written to live are also in the next file, and promote keeps exactly one Rules section
- Rules checkboxes (`- [ ]`) inside the section are not counted as Atomic Ops
- CRLF territory stays CRLF through a rules write and a body write
- Writing rules to a retired node or a closed Bug is Blocked
- A `mounts` edge round-trips through link, unlink, open_next, and ship
- A section patch changes only that section; a replace changes exactly one occurrence; the Rules section cannot be patched through either
- Verified via `npm test`
- A `contains` matching two checkbox lines is Blocked and the Blocked text lists both lines; with `all: true` both toggle
- A note or not-applicable reason is appended to the line without rewording it; unticking removes it
- `change` / `change_ref` round-trip through the live and next files and are gone after ship
