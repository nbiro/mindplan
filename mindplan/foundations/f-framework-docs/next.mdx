# Framework documentation (systems dialect first)

## Purpose

Own MindPlan’s normative documentation: `SPEC.md`, `README.md`, and `templates/` (playbook, stub, skills, integration guides). MindPlan is a tool that helps an agent think in systems. The documentation puts that first. What an agent carries every turn is the **systems dialect**: orient on the graph, place work on it, respect the edges, claim files, and classify change by blast radius. Review, checklists, and revision bookkeeping are procedures that the agent loads only at the moment they apply.

Keep the shipped guarantees: live-presence skip for released implements entries (SPEC §9.6); Implementation review **Approve** is a quality verdict that **Infrastructure First** or cascading Behavior First does not void; ship is a separate transition; unfinished Foundation deps are not a Reject reason; one `update_node_status` `revisions` call orders Foundations, Interactions, Interfaces, then Bugs and stops on the first `Blocked:`.

## Shared Substrate Spec

Claims: `SPEC.md`, `README.md`, `templates/`

### Playbook = systems dialect

`templates/agent/playbook.md` is the canonical systems dialect. `f-mcp-runtime` serves it verbatim as the MCP server `instructions`, and `i-init-project` copies it to `mindplan/agent/playbook.md`. It contains only:

- Orient with `orient_for_work` before substantial work; trust the mutation `anchor`; do not invent architecture from chat or greps
- Taxonomy (Journey, Foundation, Interaction, Interface, Bug) and edges (`belongs_to`, `depends_on`, `exposes`, `leads_to`, `affects`), including Interaction Independence and “Interaction owns the body, Interface mounts”
- MCP writes structure; file tools write territory prose; never hand-edit server-owned frontmatter
- `Blocked:` is a hard failure: fix the stated cause
- Claim files with `set_implementation_files` before writing them
- A change to shipped work is a blast-radius classification: source, neighbor, unaffected
- One line on shipping: do not ship your own work when review is due; follow `review-work`
- Routing to `define-entities`, `plan-project`, and `review-work`
- Architectural nevers only (no tickets outside the graph, no Interaction→Interaction `depends_on`, no Interface-owned screen bodies, no writes on `main`/`master`)

It does **not** contain the review procedure, the revision freeze, verdict formats, check/typecheck handoff steps, or checklist rules.

### Stub = trigger

New `templates/agent/agents-stub.md` is what `i-init-project` installs into root `AGENTS.md` and `.cursor/rules/mindplan.mdc`. A few lines: MindPlan models this repository; before planning or changing code, call `orient_for_work` and place the work on the graph; follow the MindPlan MCP server instructions; if the host does not show server instructions, read `mindplan/agent/playbook.md`.

### Review is proportional (SPEC §3.1, §3.7, review-work)

- The agent MAY ship (or resolve) its own revision after default `mindplan-mcp check` and the project typecheck are green, when the revision has **no Foundation source** and **at most one source**.
- The agent MUST spawn one independent Reviewer when any source is a Foundation, or the revision has two or more sources. One spawn covers the revision; the Reviewer judges source contracts and the diff together.
- `templates/agent/skills/review-work/SKILL.md` owns everything about that gate: when it is due, check + typecheck before handoff, the revision snapshot handed to the Reviewer, the verdict the Reviewer returns, the ship-deferral carve-out, and Reject → fix → fresh Reviewer. The playbook and integration guides point at it and do not restate it.
- The verdict format is for the Reviewer only. The parent acts on the outcome: shipped, ship-deferred, or Reject with findings.

### Neighbors edit in place (SPEC §3.6, §3.7)

- **Source** (own contract changed): `open_next` and a full successor contract — unchanged.
- **Neighbor** (pulled in by reverse `depends_on`, `exposes`, or inbound `leads_to`; owned files change; behavior does not): edit the owned files in place. No `open_next`, no `## Impact` note. List neighbors on the revision so a Reviewer, when one is due, reads their files in the diff.
- A neighbor whose `implements` must change is not a pure neighbor: `open_next` it like a source.
- **Unaffected**: no change, not listed for edits.
- `## Impact` is no longer part of any template. The compiler still rejects an empty one when the heading exists.

### Atomic Ops are a ship-time ledger (SPEC §3.3, §5.6)

- Atomic Ops remain Markdown checkboxes; Completion Check still blocks `ship` / `resolved` with unchecked items.
- The “leave one Atomic Op open while building” rule is removed (`f-compiler-rules`, `i-steer-plan`, `i-check-integrity`). SPEC §5.6, Appendix A, and the Appendix B walkthrough drop it.
- Skills describe Atomic Ops as the record checked before ship, not as the plan and not as progress narration.
