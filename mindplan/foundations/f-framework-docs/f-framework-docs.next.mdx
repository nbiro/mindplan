# Framework docs

## Purpose

Infra — SPEC, playbook, and skills. Project rules are mandatory via `get_rules` before each action, and node rules are mandatory via the `rules` block of `orient_for_work`. Tool descriptions carry when-to-call hints. New-feature code waits until nodes are updated or created through the plan-project skill. Host install docs cover Cursor and Claude Code. Agents must be told the two rule scopes and which tool writes each, or area rules will keep landing in the global list. The check must be impossible to miss: the playbook and `get_project` name `run_check` (CLI `mindplan-mcp check`), because an agent that only ever saw the CLI never ran it and shipped nodes that failed it. Decision records need the same treatment: agents must be told to record a decision when they choose between viable designs, and that MindPlan blocks `in-review` on shared-contract, schema, or wide-radius changes without one, or the gate reads as an arbitrary obstacle. Neighbors need it too: an agent that is not told to pass the change id on a neighbor's in-place writes, or that a new file beside a shipped node's own can be claimed in place, keeps opening needless revisions or putting files in the wrong folder.

## Decisions

### d-docs-stay-whole

- Decision: The framework docs (SPEC, CHANGELOG, README, skills, playbook) stay one node: they change with every release because they describe every behavior.
- Alternatives:
  - Split SPEC from the skills and templates (each release still edits both, so both parts would be hotspots and every feature would revise two nodes)
- Why: A docs node's ship rate tracks the project's release rate by design, so a high rate here is not a smell.
- Change: hotspot-splits
- Date: 2026-10-31
- Keep whole: true

### d-filters-fan-out-one-change

- Decision: Graph filters and the fan-out warning ship as one change (graph-filters-fan-out) with one docs revision and one 0.14.0 release.
- Alternatives:
  - Two changes in sequence (a shipped node holds one open revision, so the second feature's docs revision would wait for the first to ship)
- Why: Both features edit SPEC and the skills; the owner chose one PR over sequencing the docs revision.
- Change: graph-filters-fan-out
- Date: 2026-10-31

### d-type-names-only

- Decision: The type names (Journey, Interaction, Interface, Foundation, Bug) are the only vocabulary for node types, in docs, skills, warnings, and with the user; no plain-word synonyms.
- Alternatives:
  - Keep the plain-word glossary (area, action, entry point, building block) beside the type names: two names per type confused the owner and let agents drift between them
  - Rename list_areas and the area parameter to Journey wording too: a breaking tool-contract change, kept out of this release
- Why: One name per type is easier to follow than two layers, and the spec already fixes the type names.
- Consequences: Prose must say Journey, Interaction, Interface, Foundation, or Bug even where a plain word would read more naturally; list_areas and area keep their names until a tool-contract change renames them.
- Change: spec-type-names
- Date: 2026-10-31
