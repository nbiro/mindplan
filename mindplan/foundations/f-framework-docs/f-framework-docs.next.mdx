# Framework docs

## Purpose

Infra — SPEC, playbook, and skills. Project rules are mandatory via `get_rules` before each action, and node rules are mandatory via the `rules` block of `orient_for_work`. Tool descriptions carry when-to-call hints. New-feature code waits until nodes are updated or created through the plan-project skill. Host install docs cover Cursor and Claude Code. Agents must be told the two rule scopes and which tool writes each, or area rules will keep landing in the global list.

## Shared Substrate Spec

Claims: `SPEC.md`, `README.md`, `templates/`

- SPEC §1.1.1 / §8: short instructions; `get_rules`; when-clause on every tool; twenty-four tools
- SPEC node rules: the `## Rules` territory section (§2), inheritance (own, up `belongs_to`, along transitive `depends_on`, Bugs from affected nodes; never downward or across siblings), the `orient_for_work` `rules` block, `get_blast_radius` `rules_impact`, `get_node_context` `rules`, `patch_node_rules`, and that enforcement is prose only
- Playbook / stub: get_rules then orient_for_work before each action; both global rules and the node `rules` block are mandatory; graph-first new features via plan-project
- Playbook / plan-project skill: a rule that applies everywhere goes in `patch_project_rules`; a rule about one area goes on that node with `patch_node_rules`; editing a node's rules is a blast-radius question (read `rules_impact`)
- `templates/agent/project.md` rules comment points at the same split
- The stub's offline fallback names the host copies for both hosts (`.cursor/` or `.claude/` plus `CLAUDE.md`)
- README, SPEC, and the Claude Code integration guide document `init --host cursor|claude|all` and what each host receives
- plan-project skill description: load when creating or patching the graph, including before new-feature code
- Never paste rules, playbook, or description into MCP instructions

Depends on: `f-domain-model`.
