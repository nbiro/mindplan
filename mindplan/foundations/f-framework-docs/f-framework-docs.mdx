# Framework docs

## Purpose

Infra — the text that tells people and agents how MindPlan behaves: `SPEC.md` (normative), the always-on playbook, the served skills, the setup and upgrade guides, the `MINDPLAN.md` pointer, the host integration notes, `README.md`, and `CHANGELOG.md`. Agents act on what these say, so each rule is stated once, in one home, and describes current behavior only; a second copy drifts, and a stale copy is followed.

## Shared Substrate Spec

Claims: `SPEC.md`, `README.md`, `CHANGELOG.md`, `templates/`

**Each file's job**

| File | Holds |
|---|---|
| `SPEC.md` | The normative contract: layout, taxonomy and edges, state machines, compiler rules, file format, every tool's parameters and results (§8), the check (§9.6), the error catalog (Appendix A). Each rule has one home section; other sections point to it. |
| `CHANGELOG.md` | Every behavior change per release, in a section titled with the version that ships it. The only place for release history and migration stories. |
| `README.md` | The pitch, requirements, quick start (register the server, ask the agent to set up MindPlan), the five types with their established terms, what the server enforces, the tools grouped one line each (details: SPEC §8), the check and merge gate, config keys and environment variables (the graph cache's `MINDPLAN_GRAPH_CACHE` and per-call `MINDPLAN_GRAPH_MEMO` among them), where search keeps its model and its copy of the native runtime, and links to SPEC, CHANGELOG, and CONTRIBUTING. |
| `templates/agent/playbook.md` | The systems dialect `get_project` returns every session, one screen: what the server enforces (each gate, when it fires, the call that clears it), the taxonomy table, how to place work on the graph and evolve a shipped node in a few lines, and where to look things up (`get_spec`, `get_skill`). It states the planning duty (a new behavior is a new node, created before its files are claimed; update the nodes a change touches) and otherwise prescribes no per-action ritual and no session mode; the gates and the merge check guarantee that the graph matches the code before a merge. Option mechanics stay in SPEC and the skills. |
| `templates/agent/agents-stub.md` | The pointer `setup_project` returns for `MINDPLAN.md`, four points: `get_project` first; the planning duty, worded as in the server instructions and the playbook; `mindplan/` only through the MCP server; `run_check` before handoff, with the merge gate in CI. This repo's `MINDPLAN.md` is identical to it. |
| `templates/agent/skills/` | Reference the agent loads when it needs it (`get_skill`): `plan-project` — modeling a product and evolving a shipped graph (breakdown, scope, blast radius, revisions and conflicts, planned wiring, parallel worktrees); `define-entities` (+ `examples.md`) — creating and linking nodes, required sections. Neither prescribes a plan-only session mode or a stop-and-confirm step. |
| `templates/agent/setup-guide.md`, `upgrade-guide.md` | The steps `setup_project` and `upgrade_project` return. |
| `templates/agent/integrations/`, `mcp.json.example` | Per-host server registration. |
| `templates/agent/project.md` | The seed brief `setup_project` writes. |
| `templates/ci/github/mindplan-merge-gate.yml` | The merge-gate workflow `setup_project({ ci: "github" })` writes. |

**Rules for every file**

- The type names Capability, Interaction, Interface, Foundation, and Bug are the only words for node types. SPEC §2.0.0 keeps a non-normative table of the closest established term for each type and edge; no doc uses those terms as synonyms.
- MCP is the only writer of `mindplan/`; no doc tells anyone to read or edit `mindplan/**` with host file tools.
- No release history outside `CHANGELOG.md`: SPEC, README, the playbook, and the skills describe what the server does now. Legacy handling the server still performs is described as current behavior (SPEC §1.1.2 lists what `upgrade_project` converts).
- SPEC section numbers and the headings `get_spec` topics name stay stable; the Minimum Territory Shape table in SPEC §6.5 and in the define-entities skill is generated from `TERRITORY_SHAPE` between the shape-table markers.
- Features that are specified but not built (SPEC §6.4 MDX components, §10 external UI sync) are labelled as not implemented.
- Docs describe `orient_for_work` at its default depth (`body`): the blast radius, neighborhood, and stability are named with `depth: "full"`. Every `open_next` example and fix text passes `reason`; the hotspot advice names the diagnosed refactor (invert through a registry the node depends on, or split), never a generic split.
- The playbook stays one screen (≤ 60 lines) and tells the agent what is enforced, not what to call before each action: a sentence of the form "before each action, call …" or "always call …" either names a gate the server runs or goes.
- A duty the docs still state as prose is one no gate can hold (the planning duty; run the check before handoff); everywhere else the docs name the gate and its fix. The planning duty is worded identically in the stub, the server instructions, and the playbook.

## Acceptance Criteria

- The shape table in SPEC §6.5 and in the define-entities skill equals `shapeTableMarkdown()`, and every `get_spec` topic resolves against `SPEC.md` (`agent-guidance.test.mjs`).
- The playbook is at most 60 lines, names `get_project.playbook`, `get_rules`, `plan-project`, `run_check`, and `mindplan-mcp check`, says to ship the node when the implementation is done and a merge is requested, and carries no review or checklist procedure text (`smoke.mjs`).
- `setup_project` returns `agents-stub.md` as the pointer, and it names `get_project`, `get_rules`, `plan-project`, `get_skill`, `mindplan/**`, and `setup_project` (`smoke.mjs`).
- SPEC §8 documents every registered tool (37): the parameters many tools share (`root`, `change`, `slot`, `verbose`) once, in the §8 Common parameters table, and every other parameter and result field once, in its tool's entry.
- No doc tells agents to edit `mindplan/**` with host file tools, names `init` as a command, or names Journey as a type.
- `CHANGELOG.md` has a section for every release.
