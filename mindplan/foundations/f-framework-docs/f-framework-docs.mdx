# Framework docs

## Purpose

Infra — SPEC, playbook, and skills. Project rules are mandatory via `get_rules` before each action, and node rules are mandatory via the `rules` block of `orient_for_work`. Tool descriptions carry when-to-call hints. New-feature code waits until nodes are updated or created through the plan-project skill. Host install docs cover Cursor and Claude Code. Agents must be told the two rule scopes and which tool writes each, or area rules will keep landing in the global list. The check must be impossible to miss: the playbook and `get_project` name `run_check` (CLI `mindplan-mcp check`), because an agent that only ever saw the CLI never ran it and shipped nodes that failed it.

## Shared Substrate Spec

Claims: `SPEC.md`, `README.md`, `templates/`

- SPEC §1.1.1 / §8: short instructions; `get_rules`; when-clause on every tool; twenty-five tools
- SPEC node rules: the `## Rules` territory section (§6.1.1), inheritance (own, up `belongs_to`, along transitive `depends_on`, Bugs from affected nodes; never downward or across siblings), the `orient_for_work` `rules` block, `get_blast_radius` `rules_impact`, `get_node_context` `rules`, `patch_node_rules`, and that enforcement is prose only
- SPEC check and gate: `run_check` (§8.1), the in-review / ship gate and import fixes (§5.10, §9.6), stale-text warnings (§9.6)
- SPEC small writes: `verbose`, the default write result, one line per node for a batch, scoped drift and its classes (§8 preamble), orient `depth`, `patch_node_territory` `section` / `replace`, `update_node_status` `scope` / `dry_run` (§8.2)
- SPEC composition root: the `mounts` edge (§2.2) and the multi-template registry example (§1.2.2)
- Playbook / stub: get_rules then orient_for_work before each action; both global rules and the node `rules` block are mandatory; graph-first new features via plan-project; `run_check` before handoff
- Playbook / plan-project skill: a rule that applies everywhere goes in `patch_project_rules`; a rule about one area goes on that node with `patch_node_rules`; editing a node's rules is a blast-radius question (read `rules_impact`)
- define-entities skill and examples: the `mounts` edge and the multi-template example
- The stub's offline fallback names the host copies for both hosts (`.cursor/` or `.claude/` plus `CLAUDE.md`)
- README, SPEC, and the Claude Code integration guide document `init --host cursor|claude|all` and what each host receives
- plan-project skill description: load when creating or patching the graph, including before new-feature code
- Never paste rules, playbook, or description into MCP instructions
- **Honesty behavior in SPEC and the playbook.** SPEC documents: which writes reset a `ready` revision to `draft` (and which never do); `Blocked: Coverage` with its probable owner and fix; the import rule over next-slot and released claims (warnings for one release); `skip_review` and the per-step dry run; unambiguous `toggle_checkboxes` with `all`, `note`, and `not_applicable`; change ids (`change`, `change_ref`, `scope: "change"`, change blast radius, change check); glob claims; and the shared-route rule (the Assembler owns routes that dispatch to the active template; a template's entry point owns only its own routes) with its split-family warning. The bundled playbook names readiness reset, skip_review, notes, and change ids
- **Changelog.** `CHANGELOG.md` lists every behavior change per release

Depends on: `f-domain-model`.
