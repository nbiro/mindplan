# Compiler rules

## Purpose

Infra — validation-at-transition rules. A next file in state `mirror` is not an open evolution: `open_next`, cancel, deprecate, and `force_unship` key off `node.next`, not path existence. The same module owns the import matrix, so the check, the claim step, and the ship gate cannot disagree about which imports are legal, and it names the exact graph edit that would make an illegal one legal. It also owns the decision gate. MindPlan never makes or judges a decision; it asks for one only where a missing one is costly. A revision is decision-worthy when it changes a shipped Foundation's contract, claims a new migration or schema file, has more dependents than the configured blast radius, or adds or removes a `depends_on` edge of a shipped node. Such a revision warns while no decision is recorded for it and is `Blocked: Decision` on its move to `in-review`; any other revision is never gated, so small single-area changes stay cheap. A node's first build is not gated on its initial edges, because every new Interaction has to add them. A change's members are its open revisions and the shipped nodes with planned edges under it; a shipped node whose files a change edits in place is not a member and carries no change id.

## Shared Substrate Spec

Intended files: `src/foundations/f-compiler-rules/`

- `validateOpenNext` accepts a standing mirror (blocks only when `node.next` is set)
- Cancel / deprecate / force_unship messages name an open evolution, not mere file presence
- Pipeline rules continue to evaluate against live or open-evolution slots only
- `validateLink` accepts `mounts` only as Foundation → Interface; `effectiveMounts(node)` reads `next.mounts` while a Foundation evolves
- `importAllowed` lets a Foundation import exactly the Interfaces it mounts (a composition root); without the edge a Foundation → Interface import stays illegal
- `integrity.ts`:
  - `findAllImportViolations` (whole universe, for the check), `findImportViolationsForClaim` (files being claimed), `findImportViolationsForNode` (a node's active-slot files)
  - Each `ImportViolation` carries the fix: `{ tool: "link_nodes", args }` with `depends_on`, `exposes`, or `mounts`, or `not_allowed` text when no edge can make the import legal (an Interaction importing an Interface, a `depends_on` that would cycle)
  - `assertCheckCleanForNode` — the gate for moves to `in-review` and `ship`: import and exclusivity violations on the node's active-slot files become one `Blocked: Check failed …`
  - `staleTextWarnings` — non-blocking: a body names a repo path that does not exist, a claimed file changed after the body was last updated, checkboxes are unticked, a live `added_claims` entry the body does not name yet as a whole path (`namesPath`; `stale: "<id>" claims … added in place without a revision`, only while no next is open); relative references (`./`, `../`) are skipped; closed checklist items are skipped by the missing-path signal, because they record history, not claims about the current code: an item is closed when `countCheckboxesInText` (the completion rule) counts its line as checked, so `- [x] …`, `— note:`, and `— n/a: <reason>` are skipped and an `— n/a:` with no reason is not; the skip covers the item's continuation lines (indented lines, nested non-checkbox bullets, and lazy lines before a blank line) up to the next list item at its level or a heading; the changed-file signal compares a claimed file's mtime with the territory file's own mtime (plus two seconds), so a fresh checkout does not warn; callers choose which signals
  - `findAllImportViolations` scans every claimant of a file (live, next-slot, and released current-slot owners) and resolves import targets through every claim. A violation found only through a next-slot or released claim, which the check did not scan before, is marked `advisory`; the check reports it as a warning for one release before it Blocks
  - `probableOwner(graph, file)` — the non-retired pipeline node whose claim shares the longest directory prefix with an unclaimed file (a file two or more folders deep needs at least two shared folders), and `coverageFix` — the exact call that claims it (`set_implementation_files` with the active-slot list plus the file, preceded by `open_next` for a shipped owner with no open evolution, unless that owner dominates the file's folder (`isDominatedFolder` with the file as a probe) and the file is not a migration or schema file (`schemaClaimEntries`), where the claim is added in place; `coverageFix(graph, root, owner, file, ctx?)`, where `createCoverageFixContext(root)` holds the schema globs and each owner's `collectOtherClaims`, so one check run expands the other nodes' claims once per owner, not once per unclaimed file)
  - `routeFamilySplits(graph, buckets, universe)` — warnings when the route files (`page`, `route`, `layout`, `template`, `loading`, `error`, `not-found`, `default`) of one route family are owned by more than one node. Only router roots count (`appRouterRoots`: an `app/` folder with a root `layout`, directly or in a route group). `findAllImportViolations` also takes the universe so the check lists it once. A route family is the route folder cut after its last static segment, so `app/sites/[site]/[lang]/blog/[slug]/page.tsx` belongs to `app/sites/[site]/[lang]/blog/`. Rule (SPEC): the Assembler owns routes that dispatch to whichever template is active; a template's Interface owns only routes that exist for that template alone; the warning labels each owner by its type (`(Assembler)`, `(Interface)`)
- `changeMembers(graph, change)` (`rules.ts`) — the open revisions of a change: pipeline nodes whose `activeChange` is the id, shipped with an open next or pre-ship and not retired; shared by the change walk, the change check, and the change blast radius
- `changesWithRevisions(graph)` (`rules.ts`) — every change id with at least one open revision (the same membership test as `changeMembers`); the steer handlers compare it before and after a write to find the changes that write closed
- Completion Check counts `- [x] … — note: …` and `- [x] … — n/a: <reason>` as done; a `— n/a:` with no reason counts as unchecked
- **Decision gate** (`decisions.ts`):
  - An **open revision** is a shipped Foundation/Interaction/Interface with an open next, or a pre-ship, non-retired one at any pre-ship state. Nothing else is ever decision-worthy (Capabilities and Bugs are not revisions)
  - `isOpenRevision(node)` answers the line above
  - `decisionTriggers(graph, node, ctx)` → `{ kind, message }[]`:
    - `foundation_contract` — a Foundation with an open next: `contract changes (an open revision of a shipped Foundation)`
    - `schema` — a migration or schema file (`matchesSchemaFile` with config `decisions.schema_files`) covered by the active-slot claims that is new in this revision: for a shipped node's next, one its live claims do not cover or the branch adds (`newFilesSinceBase`); for a first build, one the branch adds, or any claimed one outside git, so a node modeling a file the repository already had is not gated
    - `blast_radius` — more non-retired dependents (`blastRadiusDependents`) than config `decisions.blast_radius`
    - `depends_on` — a shipped node whose next `depends_on` set differs from the live one, naming the targets added and removed
  - `revisionHasDecision(graph, node)` — true when an active node's decisions include one whose `change` is the revision's change id (`activeChange`) and whose `date` is on or after the change's start day (the earliest start among its open revisions: `next.opened_at`, else `created_at`; no bound when a member's next predates `opened_at`), so a member added later still gets credit, so a reused change id is not satisfied by an earlier change's decisions, or the node's own active slot holds a decision new in this revision (before first ship: any own decision; with an open next: an id the live file does not hold). One decision under a change clears every member of that change
  - `decisionGap(graph, node, ctx)` → `{ triggers, fix }` or null; `fix` is the `record_decision` call with the node id and, when set, the change id filled in
  - `decisionWarnings(graph, node, ctx)` → `decision: "<id>" <trigger messages>; record the choice and the alternative you rejected with record_decision before in-review.`
  - `assertDecisionForReview(graph, root, node, ctx?)` → `Blocked: Decision. "<id>" <trigger messages>, and no decision is recorded for this revision (under change "<change>" or on the node). Record the choice and the alternative you rejected. Fix: record_decision({...}).`
  - `DecisionContext` (`createDecisionContext(root, settings?)`) loads the config once and runs the git probe lazily and at most once: only when a claimed schema file is not already new by its claims
- `staleTextWarnings` reads the body without the `## Decisions` section: a recorded decision may name a path the revision since removed
- **Linked tests** (`integrity.ts`):
  - `testPresenceFailures(node, root)` — each `tests` entry that matches nothing on disk (`claimEntryExists`), once the node's live state is in-review or shipped or its next is in-review; nothing for a draft plan. `assertCheckCleanForNode` adds them to its `Blocked: Check failed …`, so a move to in-review or ship with a broken test link is Blocked
  - `untestedWarning(node)` — `tests: "<id>" is in review with no linked tests; link the files that verify it with set_test_files.` for a Foundation, Interaction, or Interface whose active slot is in-review and whose `tests` list is empty; null otherwise. It never Blocks

- **Minimum Territory Shape** (`shape.ts`):
  - `TERRITORY_SHAPE` — the one constant of required sections per type (Foundation: `## Purpose`, `## Shared Substrate Spec`, `## Acceptance Criteria`, `## Atomic Ops` or `## Checklist` with a checkbox, and a role; Interaction: `## Purpose`, `## Actor & Trigger`, `## PRD / Execution Logic` (or `## Execution Logic` / `## PRD`), `## Acceptance Criteria`, `## Atomic Ops`; Interface: `## Purpose`, `## Kind`, `## Spec`, `## Acceptance Criteria`, `## Atomic Ops`; Bug: `## Summary`, `## Repro Steps`, `## Fix Checklist`) and the gates that read it (`ready`, `in-review`, `ship` for the build pipeline; `in-review`, `resolved` for a Bug). An optional `## Impact` must not be a stub when present
  - `shapeProblems(node, slot)` — every gap at once: a missing section, a prose section that is empty or still holds `create_node` placeholder text (`stub`), a checklist section with no checkbox, a stub `## Impact`, a Foundation with no role
  - `assertMinimumTerritoryShape(node, slot)` Blocks once with every problem: one problem keeps the single-section wording; several are listed in one `Blocked: Minimum Territory Shape. "<id>"/<file> has N problems: …` message
  - `shapeReport(node, slot)` → `{ slot, gates, sections: [{ heading, kind, status }], role? }`, `status` being `present`, `missing`, or `stub`; null for a Capability, a shipped node with no open next, a retired node, and a closed Bug
  - `shapeWarning(node)` → `shape: "<id>" is missing "## X" and has stub "## Y" (required before ready)` (`before in-review` for a Bug) for a draft active slot or a Bug before in-review; null when the shape is complete
  - `shapeTableMarkdown()` — the per-type table that the define-entities skill and SPEC embed (the playbook, which stays one screen, points to them) between `<!-- shape-table:start -->` / `<!-- shape-table:end -->` markers; a test fails when an embedded copy differs from it, so the docs cannot drift from the gate
- **Planned edges.** `plannedEdges(graph, change?)` lists `{ source, change, type, target }` for every planned entry of a shipped, non-retired node, leaving out the entries an open revision of their change has already applied to its next slot (an entry that revision lacks stays pending). `changePlannedSources(graph, change)` returns those sources: members of the change with `kind: "planned"`, never walked by status moves. `changeMembership(graph, change)` returns `{ revisions, planned }`, each node once, for the check, the change blast radius, and change-wide orientation. `plannedEdgeProblems(graph, change)` checks each entry as `link_nodes` would — the target exists and is active, `validateLink` accepts the shape (Interaction Independence included), the edge does not already exist on the slot it will land in, and a planned `depends_on` closes no cycle in the effective graph plus the change's planned `depends_on` (`withPlannedDependsOn`) — and returns one problem string each. `validatePlannedLink(graph, source, target, type, change)` is the same check for one new entry
- **Attributed files in the decision gate.** `newSchemaFiles` also reads the active slot's `attributed` list: an attributed file matching `decisions.schema_files` is new when the branch adds it (`newFilesSinceBase`), or always outside git, so a schema node's revision that adds a migration in the composition root's folder is decision-worthy
- **Open–closed signals** (`open-closed.ts`). Graph facts only, never code; every signal is a warning or an informational field:
  - `fanInIndex(graph)` — target id → its fan-in sources from one pass over the live edges; the check and orient build it once per call
  - `fanIn(graph, node, index?)` → `{ count, nodes }` — the distinct non-retired nodes with a direct live edge into the node that a change to it reaches: `depends_on` (any source), `exposes` (an Interface showing an Interaction), and `mounts` (a composition root importing an Interface)
  - `nodeChurn(node)` → `{ change, date?, reasons }[]` — the distinct change ids that revised the node, oldest first: the `change` of each of its decisions (live and open next, superseded included, since a superseded decision still records a revision; the first build's change counts like any other) plus a shipped node's open revision's change. `reasons` are the decision sentences recorded under that change; the open revision's change with no decision yet has none. The node holds no revision log: decisions are the record, and git keeps the rest
  - `recentRate(node, settings, now?)` — how often the node shipped lately: its stored `churn` (a decayed ship count, f-territory-store) decayed from its `shipped_at` to now with `hotspots.half_life_days`, plus 1 while a revision is open; 0 for a node with no `churn` yet. A split resets the stored value, so a root that split its parts out starts again from zero
  - `graphRateMedian(graph, settings, now?)` — the median `recentRate` (open revisions not counted) of the established nodes: shipped, active Foundations, Interactions, and Interfaces that shipped at least twice since their last split (a node with no count yet is counted). A node shipped once or a root that just split has no pace yet, so a change that adds many nodes does not drag the median down
  - `keepsWhole(node)` — true while the node (live or open next) holds an active decision with `keep_whole: true`: the owner decided it stays one node, so it is never a hotspot
  - `hotspotFor(graph, node, settings, ctx?)` → `{ node_id, rate, median, fan_in, changes, split_into? }` or null — a shipped, active pipeline node, not `keepsWhole`, whose `recentRate` is at least `hotspots.min_rate` and at least `hotspots.outlier_ratio` times the graph median (a median of 0 counts as 1). Fan-in never decides it; it ranks hotspots (`rate × max(1, fan_in)`). `changes` are the most recent change groups of `nodeChurn` (at most three). `ctx` carries one fan-in index and the median, so the check computes them once
  - `hotspots(graph, settings)` — every hotspot, highest rank first — a shipped, non-retired Foundation, Interaction, or Interface whose fan-in is at least `hotspots.fan_in` and whose churn is at least `hotspots.churn` (`hotspotSettings`, f-source-index)
  - `hotspotWarning(h)` → `hotspot: "<id>" ships R times as often as the median node lately (rate X vs Y)[ since it split into <ids>], and N nodes depend on it directly; it may change for several reasons. Its recent changes fall into these groups: change "a" (<reason>; <reason>), change "b" (no decision recorded), … Move each group into its own Foundation that "<id>" depends_on, so a later feature revises one part and the rest stays closed.` The split it suggests keeps imports downward: the node stays the composition root and imports the parts
  - `openClosedWarning(graph, node, settings)` — for `open_next` on a shipped node that is a hotspot counting the revision it opens (and is not `keepsWhole`): `Warning: "<id>" has N direct dependents, and this revision reaches every one. Prefer extending it: add a new node that depends_on "<id>", or split it so this change revises a smaller part. If revising it is still right, record why with record_decision and name the additive alternative you rejected.` (plus the hotspot groups when it is one); null below the threshold
  - `changeAdditivity(graph, change)` → `{ summary, new_nodes, revised, planned }` from `changeMembership`: `new_nodes` are revisions never shipped, `revised` the shipped nodes with an open next (`{ id, state, fan_in }`), `planned` the planned sources (`{ id, state, fan_in }`). `summary` reads `change "<id>": 5 new nodes, 1 revised shipped node (f-payload, fan-in 43)`, plus `, 1 planned revision (…)` when there are planned sources, and ends `; purely additive` when nothing shipped is revised or planned
- **What each type splits into** (`open-closed.ts`): `splitPartType(type)` — a Foundation splits into Foundations, an Interaction or Interface into Interactions; `splitPartProblem(graph, node, partId)` — why a part cannot be marked (wrong kind, inactive, the node itself), or null; `splitPartLinked(graph, node, partId)` — whether a marked part counts when the node's open revision ships, by the edge that keeps imports legal (a Foundation `depends_on` it, an Interaction shares one of its Capabilities, an Interface `exposes` it); `splitLinkHint(node)` — the edge the warning names. `hotspotWarning`'s advice for an Interaction and an Interface also tells the agent to mark the parts with `split_into`
- **Ship history** (`ship-history.ts`): `shipHistory(relPath)` → `{ date, shipped_at, depends_on, implements }[]` oldest first — one ship per distinct `shipped_at` in the node file's git history (`fileHistory`, f-source-index), parsed with the store's `parseFrontmatter`; `null` outside git, `[]` for a path git has not seen. `inferredSplits(graph, node, ships, partShips)` — the ships at which a Foundation split parts out of itself, judged from claims, not edges: at ship j it gained `depends_on` on a Foundation first shipped between ship j-1 and ship j, and some claim of that part (at its first ship) was covered by the node's claims at ship j-1 and is no longer covered at ship j (`claimsOverlap`: equal, one a folder holding the other, or a glob covering it). A node that only starts using a new Foundation moved nothing, so no split. `replayChurn(shipTimes, splitShips, halfLife)` — the stored rate a node would have after those ships, reset to 0 at each split ship
- **Decision gate wording.** When a shipped node's revision is decision-worthy because it revises a shipped Foundation or has a wide blast radius, the `Blocked: Decision` message also names the open–closed alternative: `An additive alternative leaves "<id>" closed: a new node that depends_on it, or a split of it; name it in alternatives if you rejected it.`
- **Planned paths.** `staleTextWarnings` returns `{ warnings, info }`. For a node whose active slot is `draft` or `ready` and none of whose claimed files exist on disk yet, missing named paths are not `stale:`: they are one `planned: "<id>" names N path(s) not on disk yet (…)` info line per node. A path named on a line that says "at build time" is planned on every node.

Depends on: `f-domain-model`, `f-territory-store`, `f-source-index`.

- **Description warnings.** `descriptionWarnings(node)` (`integrity.ts`) returns `description: …` warnings for a non-retired node's active-slot description: empty; equal to the title (letters and digits compared, case ignored); longer than `DESCRIPTION_MAX_CHARS` (300); an Interaction's that contains none of a loose list of actor words; or, except on a Bug (whose description describes a regression), revision wording (`now`, `no longer`, `was changed to`, `used to be`, `previously`, `anymore`). Heuristics, so warnings only

- **Open revisions (0.18.0).** Every gate (Infrastructure First, Behavior First, Coverage, imports, ownership, shape, the decision gate, the Completion Check) judges a revision against `graphUnder(graph, change)`: live plus that change only. `changeMembers` and `changesWithRevisions` read `open_revisions`. A move to `in-review` is Blocked while the revision has `conflicts`, naming `resolve_conflict`. `revisionHasDecision` reads decision files and accepts a decision whose `nodes` lists the node. One import and ownership implementation serves the full check and the per-transition gates

## Checklist kinds

- The Completion Check at ship still needs every item ticked, `review` and `deploy` included.
- At `in-review`, only `build` items must be ticked.
- Infrastructure First and Behavior First treat a dependency as satisfied for a dependent when the dependency is shipped, or when its active slot is `in-review` with every `build` item ticked (only `review` / `deploy` items open). The dependent may then reach `in-review` and ship; the dependency still cannot ship until its own items are ticked.
- `openHumanItems(graph)` lists every unticked `review` and `deploy` item: `{ node_id, change?, id?, kind, text }`.

## Acceptance Criteria

- A mirror twin does not block `open_next`
- An open evolution still blocks a second `open_next`
- Retire / force_unship wording matches the twin model
- A registry that mounts two Interfaces may import them; the same import without the edge is illegal and its fix is the `mounts` `link_nodes` call
- A missing `depends_on` / `exposes` yields the exact `link_nodes` call; an Interaction importing an Interface yields `not allowed`
- The gate Blocks on an import violation and on a file claimed by two nodes
- Stale-text signals are warnings and never throw; relative paths and fresh checkouts do not warn
- Cancelling an Interface is Blocked while an active Foundation mounts it
- Verified via `npm test`
- An illegal import in a file claimed only by an open next slot (or a released file) is found and marked advisory
- `probableOwner` picks the node with the longest shared claim prefix; the fix opens the evolution first for a shipped owner that does not dominate the file's folder
- A route family owned by an Assembler and a template Interface yields one warning; a family with one owner yields none
- An annotated tick passes the Completion Check; an `— n/a:` with no reason does not
- A Foundation `open_next` revision with no decision warns and is `Blocked: Decision` at in-review; recording a decision under its change clears both
- A shipped Interaction revision that only changes its body is never gated
- A first build is not gated on its initial `depends_on` edges; a shipped node's next that adds or removes one is
- In a git repository a new migration file inside an already-claimed folder trips `schema`; a modified existing one does not
- In a git repository a first build that adopts a migration the repository already had is not decision-worthy; outside git it is
- A pre-ship Foundation with more dependents than `blast_radius` trips `blast_radius`
- One decision under a change clears every member of the change
- A revision that reuses a change id is not cleared by that change's older decisions
- A decision's text naming a missing path does not warn as stale
- A ticked checklist item naming a missing path does not warn as stale, on its first line or a continuation line; an unticked one, and an `— n/a:` with no reason, still do
- A live `added_claims` entry the body does not name warns `stale:`; once the body names it, it does not
- The Coverage fix for a file in a folder its shipped owner dominates is `set_implementation_files` alone, with no `open_next`; for a migration or schema file in that folder it opens the evolution first
- A body naming only a longer path (`pkg/a.tsx` for an entry `pkg/a.ts`) still warns `stale:`
- `changesWithRevisions` lists a change while it has an open revision and drops it once the last one ships or is cancelled
- A `tests` entry missing on disk Blocks the move to in-review and ship, and is not reported for a draft
- An in-review revision with no tests yields one `tests:` warning; a draft one, or one with tests, yields none

- Each bad-description case warns and a good description does not; none fails the check
- A draft with three shape gaps is Blocked once at `ready`, naming all three; one gap keeps the single-section message
- `shapeReport` marks each required section `present`, `missing`, or `stub`; following it brings a scaffolded draft to `ready` with no shape `Blocked:`
- A draft with gaps yields one `shape:` warning; a complete draft, a ready node, and a shipped node yield none
- The shape table embedded in the define-entities skill and SPEC equals `shapeTableMarkdown()`
- A plan-only node (draft or ready, no claimed file on disk) naming missing paths yields one `planned:` info line and no `stale:` line; once one claimed file exists the missing paths are `stale:` again
- A path on an "at build time" line is planned on a shipped node's revision too
- A planned `depends_on` that would close a cycle, a planned `exposes` from a Foundation, and a planned edge to a missing node are each a problem; a legal planned edge is none
- A planned entry of a change already open on its node is not listed
- A revision attributing a new migration file in another node's folder trips `schema`; without the attribution it does not

- A node shipping several times as often as the graph median is a hotspot whatever its fan-in; a node with 40 dependents that ships at the median rate is not; `hotspotWarning` lists its recent change groups
- A pre-ship node, a retired node, a node below `min_rate`, and a node with an active `keep_whole` decision are never hotspots; superseding that decision makes it one again
- `changeAdditivity` counts never-shipped revisions as new nodes and shipped revisions with their fan-in, and says "purely additive" when no shipped node is revised or planned
- `openClosedWarning` is null for a node at the graph's pace and names the depends_on alternative for an outlier
- A stored `churn` decays by half every `half_life_days`, so a node busy a year ago and quiet since is no hotspot
- The `Blocked: Decision` message for a shipped Foundation or a wide blast radius names the additive alternative; other triggers keep their wording

- `splitPartProblem` accepts an Interaction for an Interaction or Interface and refuses a Foundation; `splitPartLinked` counts an Interaction's part that shares its Capability and an Interface's part it exposes, and not one elsewhere

- A ship that adds `depends_on` on a newly shipped Foundation while keeping all its own claims is no split; one whose earlier claim moves to the new Foundation is
