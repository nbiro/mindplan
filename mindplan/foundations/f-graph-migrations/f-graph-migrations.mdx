# Graph migrations

## Purpose

Infra — the one place that knows which migrations a graph needs and whether tools may touch it. Every migration is idempotent and runs in code, never by hand: an agent cannot replay git history to backfill revisions, and must not write `mindplan/` with host tools. The level, not the package version, decides the Block, so a release without a new migration asks nothing of a project.

## Shared Substrate Spec

Intended files: `src/foundations/f-graph-migrations/` (`migrations.ts`, `status.ts`, `tree.ts`)

- **Migrations (`migrations.ts`).** `migrateJourneysToCapabilities` (level 3, runs first, before any graph load): moves every `mindplan/journeys/<id>/` node folder (one holding a live `<id>.mdx` or `current.mdx`), attachments included, to `mindplan/capabilities/<id>/`, after rewriting `type: Journey` in its live file's frontmatter to `type: Capability` (keeping its line endings) and the scaffold stubs `create_node` wrote before level 3 to the current ones. Every run applies the same rewrite to every `capabilities/<id>/` live file, so a folder moved by hand, or one whose rewrite failed, is repaired by the next upgrade. It removes `journeys/` once it holds nothing but `.gitkeep` files and empty folders; a folder there without a live file is not a node and is left alone. `hasLegacyCapabilityFolders()` says whether `journeys/` still holds a node folder. A failed move or rewrite throws `LegacyTerritoryMigrationError` with the moves made before it. It keeps ids and body text as they are. A Capability folder that already exists under the same id is `Blocked:` naming both paths, after the moves made before it, which it reports. The rest moved from the retired init, unchanged in behavior: `migrateLegacyTerritoryFilenames` (legacy `current.mdx` / `next.mdx` → `<id>.mdx` / `<id>.next.mdx`, with `LegacyTerritoryMigrationError` carrying the renames applied before a failure; runs before any graph load), `migrateImplementationPackages` (legacy `implementation_packages` → `{ sources, exclude }`, seeding `implements` and `role`; writes the default config when none exists), `dropShippedAtomicOps`, `removeLegacyMirrorTwins`, `backfillRevisions` (revision counts, churn, and splits from git, `f-compiler-rules` ship history), `removeRetiredAgentFiles` (deletes `mindplan/agent/`, the copies the retired init installed, through the lock-tolerant `f-source-index` I/O), and `clearStaleChangeLabels` (level 2: strips the `change` and `change_ref` scalars from the live file of every shipped, non-retired pipeline node, with or without an open next (a revision's own change lives on its next file; `open_next` before 0.15.0 copied a label there and left it on live), the neighbor labels releases before 0.15.0 wrote). Like the others it is idempotent and runs on every upgrade: once no such scalar exists it changes nothing
- `runMigrations(): MigrationReport` runs them in that order and returns `{ capabilitiesMoved, territoryFilenames, config, atomicOpsDropped, mirrorTwinsRemoved, mirrorTwinSkips, revisionsBackfilled, splitsFound, agentFilesRemoved, staleChangeLabelsCleared }` (`capabilitiesMoved`: the ids moved, sorted; `staleChangeLabelsCleared`: `{ node_id, change }` per cleared label, sorted by node id). A graph that cannot load is skipped by each graph pass (as before)
- `MIGRATION_LEVEL` (now `3`): the level a graph reaches after `runMigrations`. A release that adds a migration raises it by one; a release that adds none leaves it
- `stampGraph()` writes `mindplan/version.json` with the running package, `GRAPH_VERSION`, and `migrations: MIGRATION_LEVEL` (`writeProjectVersion`, `f-territory-store`) and returns its repo-relative path
- **Status (`status.ts`).** `graphStatus()` never throws and returns `{ state, level, required, warning?, call? }`:
  - `setup` — no `mindplan/` directory, or one with no stamp and no node folder (the empty folders a 0.12 server created at boot, or a setup that stopped before its stamp); `call: "setup_project"`
  - `upgrade` — the stamp is missing, unreadable, or its `migrations` level (absent counts as 0) is below `MIGRATION_LEVEL`, with the same graph format, or `mindplan/journeys/` holds a node folder whatever the stamp says (a branch from before level 3 merged one in); `call: "upgrade_project"`
  - `server-behind` — the stamp's level is above `MIGRATION_LEVEL` or its graph format above `GRAPH_VERSION`; the fix is to upgrade `mindplan-mcp` to the stamp's package
  - `current` — no warning
  Each non-current state carries one `warning` sentence that names the fix
- `versionGate()` throws `Blocked: Version — <warning>` unless the state is `current`. `MINDPLAN_VERSION_GATE=off` turns it off (test fixtures without a stamp), like `MINDPLAN_ORIENT_GATE`
- **Tree diff (`tree.ts`).** `snapshotTree()` maps every file under `mindplan/` (`map.md` included) to a content hash; `changedSince(snapshot)` returns the repo-relative paths added, changed, or deleted since, sorted. Setup and upgrade report their `changed_files` with it, so every `mindplan/` path they touch is listed

Depends on: `f-territory-store`, `f-source-index`, `f-compiler-rules`, `f-domain-model`.

## Acceptance Criteria

- `graphStatus()` is `setup` without `mindplan/`, `upgrade` for a graph with no stamp or a stamp without `migrations`, `current` after `runMigrations` + `stampGraph`, and `server-behind` for a stamp whose level is above `MIGRATION_LEVEL`
- `versionGate()` Blocks in every state but `current` and never with `MINDPLAN_VERSION_GATE=off`
- `runMigrations()` on a migrated graph changes nothing; on legacy fixtures it renames, migrates config, drops shipped Atomic Ops, removes mirror twins, backfills revisions and splits, and removes `mindplan/agent/` (the suites that covered init now cover it)
- `changedSince` lists every file a migration wrote or deleted
- `clearStaleChangeLabels` strips and reports the live `change` of every shipped node, whatever its change and whether or not a revision is open; it leaves a pre-ship node's change and an open revision's next-slot change alone; a second run clears nothing
- `migrateJourneysToCapabilities` moves a Journey folder with its attachments to `capabilities/`, rewrites its type, keeps its id and body, removes the empty `journeys/`, and Blocks on an id that exists in both; a second run moves nothing; a hand-moved Capability with `type: Journey` is repaired; a `journeys/` folder without a live file neither moves nor blocks
- `graphStatus()` is `upgrade` for a level-3 stamp while `mindplan/journeys/` holds a node folder
- Verified via `npm test`

## Decisions

### d-block-on-pending-migration

- Decision: mindplan/version.json records the migration level the graph reached ({ package, graph, migrations }); every gated tool and the check are Blocked while that level is below the server's newest migration (call upgrade_project), above it or on a newer graph format (upgrade mindplan-mcp), or while no graph exists (call setup_project); a release without a new migration changes nothing.
- Alternatives:
  - Keep warning on any package mismatch and never Block (d-version-stamp-file): an agent on a new server keeps writing an old-format graph it may misread
  - Block on any package version difference: every patch release forces an upgrade commit in every repo even when no migration changed anything
  - Run pending migrations automatically at server start: an unasked-for diff lands in whatever change the agent is working on, and a teammate on an older server cannot read it
- Why: Migrations change the graph's shape, so code that expects the new shape must not read or write the old one; tying the Block to the migration level, not the package version, keeps releases without migrations free.
- Consequences: A release that adds a migration must raise MIGRATION_LEVEL; every project then runs upgrade_project once in its own commit. A branch opened before an upgrade that adds an old-format node is caught by the check, and rerunning upgrade_project fixes it. Test fixtures without a stamp set MINDPLAN_VERSION_GATE=off.
- Supersedes: d-version-stamp-file
- Change: setup-upgrade
- Date: 2026-10-31

### d-migrate-stale-change-labels

- Decision: Migration level 2 clears the change label of every shipped neighbor whose change has no open revision and no pre-ship member, and reports each { node_id, change } in staleChangeLabelsCleared.
- Alternatives:
  - Clear only labels whose change also holds a decision on that node (misses labels left by older decision-then-claim sequences, and cannot tell which write set the label)
  - No migration: leave existing stale labels for users to clear by hand (every repo keeps finished changes listing shipped nodes)
- Why: A label with no open revision behind it cannot be told apart from the stale labels record_decision left, and upgrade_project is a reviewed commit of its own, so the report shows what was cleared.
- Consequences: A neighbor-only change in flight at upgrade time (shipped nodes labeled, no revision yet) loses its labels; relabel with patch_node_territory change. Raises MIGRATION_LEVEL to 2, so every project runs upgrade_project once.
- Change: graph-edges-stale-labels
- Date: 2026-10-31

### d-migrate-strip-change-labels

- Decision: Migration level 2 strips the change scalar (and any change_ref) from every shipped, non-retired node with no open next and reports each { node_id, change } in staleChangeLabelsCleared; it runs on every upgrade (idempotent, a no-op once no label exists).
- Alternatives:
  - Clear only labels whose change has no open revision (labels no longer exist as a concept, so a live one is as meaningless as a stale one)
  - Rename the report field to changeLabelsCleared (0.15.0 is unreleased, but the existing name already reached tests and docs; keeping it avoids churn)
- Why: With labels removed, any change scalar on such a node is leftover state; stripping all of them makes the invariant hold, and an old branch merged later is cleaned on the next upgrade instead of keeping its labels.
- Supersedes: d-migrate-stale-change-labels
- Change: graph-edges-stale-labels
- Date: 2026-10-31

### d-migrate-strip-all-live-labels

- Decision: Migration level 2 strips the live change and change_ref from every shipped, non-retired pipeline node, with or without an open next, and reports each { node_id, change } in staleChangeLabelsCleared; it runs on every upgrade.
- Alternatives:
  - Only nodes with no open next (open_next before 0.15.0 left the label on live beside the revision; after a discard that label could no longer be cleared, since change on such a node is Blocked)
  - Also make discard_next drop a live change (covers only that path; the migration already makes the invariant hold everywhere)
- Why: A shipped node's live change is never read while a revision is open (activeChange and promotion use the next slot's), so stripping it everywhere is safe and closes the gap the review found.
- Supersedes: d-migrate-strip-change-labels
- Change: graph-edges-stale-labels
- Date: 2026-10-31

### d-capability-migration-moves-folders

- Decision: Migration level 3 moves each mindplan/journeys/<id>/ folder to mindplan/capabilities/<id>/ and rewrites its type frontmatter, and nothing reads the old folder or the old type name at load time.
- Alternatives:
  - Accept both Journey and Capability when loading: a compatibility layer the project rules rule out, and two names for one type is what the rename removes
  - Also rename ids (j- to c-): ids are stable names that commits, decisions, code comments, and other branches reference, so renaming them breaks more than it tidies
  - Rewrite Journey in node bodies too: prose may use the word in its UX sense, and the migration cannot tell which
- Why: The version gate already Blocks every tool until upgrade_project runs, so a one-way move in code is enough and the loader stays single-named.
- Consequences: A branch cut before the upgrade that adds a node under journeys/ needs upgrade_project again after it merges; graphStatus reports upgrade while journeys/ holds a node folder, whatever the stamp says.
- Change: capability-type
- Date: 2026-11-01
