# Source index

## Purpose

Infra — ownership universe (`sources` / `exclude`) and MCP write of `mindplan/config.json` via existing `writeProjectConfig` (force overwrite for `patch_config`). The same file holds the decision-gate settings, so a project tunes when a decision is required without a code change. A read-only git probe lists the files a branch adds, because a new migration usually lands inside a folder its owner already claims, and the claims alone cannot tell that it is new. A second read-only probe reports the plan's own git state (its tree id and the paths git status lists under it), so the graph cache can trust a clean, committed folder without touching its files. Folder dominance answers where a shipped node may grow its claims without a revision: a file in a folder no other node can own reaches no dependent's contract.

## Shared Substrate Spec

Intended files: `src/foundations/f-source-index/`

- `writeProjectConfig` remains the store write for config
- Steer exposes `patch_config` that calls it with `force: true`
- Claim expansion / ownership unchanged
- **Glob claims.** An `implements` entry with `*`, `**`, or `?` is a glob claim (`isGlobClaim`); `[` and `]` stay literal so route folders such as `[slug]` are plain paths. `validateClaimPath` accepts globs; `expandClaims` walks from the glob's static prefix and keeps matching files (a trailing `/` matches every file beneath each matching directory, e.g. `src/templates/*/actions/i-read-post/`); `claimEntryExists` is true for a glob that matches at least one file; `claimCoversPath(claim, path)` answers for files, directories, and globs. Exclusivity stays per expanded file, so two nodes whose claims overlap on a file still conflict. Directory and glob expansion skip `.git/` and `node_modules/`. Glob expansions are cached until the event loop turns, so one tool call walks each glob once
- **Claimants.** `claimantsOf(buckets, file)` lists every non-retired claim on a file: its live owner, its next-slot owner, and a released current-slot owner
- **Folder dominance** (`dominance.ts`, re-exported from `index.ts`):
  - `isDominatedFolder(graph, nodeId, folder, root?, probes?, others?)` — true when the node's live claims expand to at least one file directly in the folder, and no other non-retired pipeline node (live or open-next claims) claims the folder or anything under it, has a directory or glob entry covering it or one of `probes` (the paths about to be claimed), has a glob whose static prefix is at or under it, has a glob rooted above it that can reach beneath it (conservative: it may match files the folder holds later), or has an expanded file beneath it. The repo root is never dominated
  - `collectOtherClaims(graph, nodeId, root?)` → `OtherClaims` `{ entries, files }` — every other non-retired pipeline node's claim entries and their expanded files; callers that test several folders compute it once and pass it in
  - `folderClaimSuggestions(graph, nodeId, entries, root?)` → `FolderClaimSuggestion[]` `{ folder, files, note }` — folders where the list names two or more exact files (not already under a directory or glob entry of the list), every file on disk under the folder is covered by the list, and no other node claims anything under it: one `folder/` entry would claim the same files
  - `schemaClaimEntries(entries, globs, root?)` — the entries that reach a migration or schema file under the decision gate's `schema_files` globs: an exact file that matches, or `F/` when F is itself a schema folder (a file added to it later would match) or holds a matching file. A shipped node never adds one of these in place
- **Claim-list helpers** (`claims.ts`): `claimListKeeps(list, entry)` — the list still holds the entry verbatim or under one of its non-glob directory entries (a glob never keeps another entry); `namesPath(text, entry)` — the text names the entry as a whole path, not as part of a longer one (`pkg/a.ts` is not named by `pkg/a.tsx`, `pkg/a.ts.bak`, or `lib/src/a.ts`; `pkg/a/` is not named by `pkg/a/b.ts`; a sentence-ending period still counts)
- **Decision-gate settings.** `mindplan/config.json` may carry `decisions: { blast_radius?, schema_files? }`. `loadProjectConfig` validates it (`blast_radius` a non-negative integer, `schema_files` an array of non-empty glob strings, unknown keys Blocked) and keeps it as stored; `decisionGateSettings(config)` fills the defaults: `blast_radius: 5`; `schema_files`: `**/migrations/**`, `**/migration/**`, `**/*.prisma`, `**/schema.sql`, `**/structure.sql`, `**/db/schema.rb` (database migrations and schema dumps only: a generic `schema.*` would also match JSON Schema, zod, and GraphQL modules). `writeProjectConfig` writes `decisions` only when the config it is given has them, so a config without them loads and writes exactly as before
- `matchesSchemaFile(path, globs)` — whether a repo path is a migration or schema file under those globs (the universe glob syntax)
- **Search settings.** `mindplan/config.json` may carry `search: { enabled?, model? }` (`SearchConfigSettings`). `loadProjectConfig` validates it (`enabled` a boolean, `model` a non-empty string, unknown keys Blocked) and keeps it as stored; `f-search-index` fills the defaults. `writeProjectConfig` writes `search` only when the config it is given has it
- **Search cache.** The no-git walk of the universe skips the top-level `.mindplan-cache/` folder (the derived search cache) as it skips `.git/`; in a git repo the cache's own `.gitignore` keeps it out of `ls-files`
- **Files a branch adds.** `newFilesSinceBase(root)` — files that are untracked, staged as added, or added (`--diff-filter=A`) since `defaultBaseRef(cwd)` (the merge base of `HEAD` with `main`, `origin/main`, `master`, then `origin/master`; the dirty-src check uses the same helper), or only untracked and staged ones when no base resolves; paths are read with `-z`, so non-ASCII names come back unquoted; `null` when the root is not a git repository. Read-only; the caller decides when to probe
- **Plan git state.** `dirGitState(dir, ignoredExt, root?)` → `{ tree, dirty }` or `null`. One `git status --porcelain=v2 --branch -z --untracked-files=all --ignored=matching --no-renames` call gives both the dirty paths and the commit they were taken against (`# branch.oid`), so a commit landing between two calls cannot pair an old status with a new tree. `tree` is the id of `<prefix><dir>` in that commit, read with `git ls-tree --full-tree` (null before the first commit or while the directory is untracked); `dirty` is every path under `dir` the status lists, made relative to the project root even when it sits below the repository top (`--show-prefix`, cached per root). `null` outside a work tree, when git fails, or when git ignores a folder under `dir` or an untracked file ending in `ignoredExt` (any case): git cannot vouch for a file it ignores. `treeChanges(fromTree, toTree, root?)` → the paths (relative to `dir`) that differ between two tree ids, from the plumbing `git diff-tree -r`, which porcelain settings such as `diff.relative` cannot filter: empty when they are equal, `null` when git fails (a tree gone after a gc). Both are read-only

## Acceptance Criteria

- Config writes go through the store API used by MCP
- Verified via `npm test`
- `src/templates/*/actions/i-read-post/` expands to the files under that folder in every template, and a glob that matches nothing is missing on disk
- `[slug]` in a claim is a literal folder name
- Two nodes whose claims (glob or not) cover the same file conflict
- A config without `decisions` loads with the defaults, and a `patch_config` of `sources` rewrites it without adding `decisions`
- A negative or non-integer `blast_radius`, or a non-string schema glob, is Blocked as invalid config
- A `search` object with an unknown key, a non-boolean `enabled`, or an empty `model` is Blocked as invalid config; a config without `search` writes back without it
- `.mindplan-cache/` is never part of the universe
- `newFilesSinceBase` lists an untracked file and a file added on the branch, not a file only modified on the branch, and returns `null` outside git
- A folder where the node owns a file directly and no other node claims anything is dominated; another node's file, directory, or glob claim under it, or a glob above it that can reach beneath it, makes it not dominated, and so does owning files only in its subfolders
- The repo root is never dominated
- `folderClaimSuggestions` suggests `F/` only when the list covers every file under F and no other node claims under it
- `schemaClaimEntries` returns `db/migrations/002.sql`, `db/migrations/`, and `db/` when `db/` holds a migration, and nothing for a plain source file
- `namesPath` rejects a longer path that contains the entry and accepts the exact path followed by punctuation
- `dirGitState` gives the plan tree and dirty paths relative to a project root below the repository top, and `null` when git ignores an untracked plan file; `treeChanges` lists the paths that differ between two commits' plan trees

## Decisions

### d-git-finds-new-migrations

- Decision: A new migration is detected from git (untracked, staged, or added on the branch) as well as from claims.
- Alternatives:
  - Claims only (misses a migration added inside a folder the node already claims)
  - File modification times (a fresh checkout makes every file look new)
- Why: Migrations usually land in an already-claimed migrations folder, so the claim list does not change.
- Change: decision-records
- Date: 2026-10-20

### d-additive-claims-in-dominated-folders

- Decision: A shipped node with no open next may add claims in place only when no claimed file is lost and each new entry is a file in, or the directory of, a folder it dominates (it owns a file directly there and no other node claims anything under it); globs, removals and moves still need open_next.
- Alternatives:
  - Always require open_next for any claim change (agents misplace files into folders the node already claims, splitting code for ownership reasons)
  - Allow any additive claim on a shipped node (a new file in a shared folder can belong to a dependent's contract)
- Why: A file in a folder nobody else can own affects no dependent's contract, which is the files-change-behavior-doesn't case the playbook already treats as an in-place edit.
- Consequences: The live file records added entries in added_claims and run_check warns stale until the body names each one, so the addition stays visible in review without a revision.
- Change: shipped-claims-and-neighbors
- Date: 2026-10-23

### d-additive-claims-skip-schema-files

- Decision: A shipped node with no open next may add claims in place only when no claimed file is lost, each new entry is a file in, or the directory of, a folder it dominates, and no new entry reaches a migration or schema file (config decisions.schema_files); globs, removals, moves, and schema claims need open_next.
- Alternatives:
  - Allow schema claims in place like any other file (a new migration would never reach the decision gate, since only open revisions are decision-worthy)
  - Make in-place schema claims decision-worthy without a revision (the gate runs on the move to in-review, which an in-place write never makes)
- Why: A new migration or schema file is decision-worthy by the gate's own rule, and only a revision reaches the gate; a file in a dominated folder affects no dependent's contract, but a schema change can.
- Consequences: A node whose only change is a new migration in its own folder still needs open_next and a decision; a folder entry over a schema folder is refused even when the folder is empty today.
- Supersedes: d-additive-claims-in-dominated-folders
- Change: shipped-claims-and-neighbors
- Date: 2026-10-25
