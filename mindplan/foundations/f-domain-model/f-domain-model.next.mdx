# Domain model

## Purpose

Infra — shared TypeScript taxonomy for MindPlan nodes, edges, pipeline states, the standing next-file `mirror` twin, open evolutions, per-node rules, and decision records. `node.next` means an open evolution only; a standing twin does not populate it. Rules are prose attached to a node but are not frontmatter: they live in the node's `## Rules` body section (owned by `f-territory-store`), so the §9 frontmatter schema and `GRAPH_VERSION` (`1`) do not change. Decision records use the same storage idea in a `## Decisions` section, but they belong to a slot: a revision records why its design looks the way it does on its own file, and the record ships or is discarded with it. A record's status is never stored: it is computed from whether another active decision supersedes it, so abandoning the revision that superseded a decision makes it active again instead of leaving a stale mark on another node's file. One shared predicate says which nodes no longer carry live work, so the store and the rules queries cannot disagree about it. A sixth edge, `mounts` (Foundation → Interface), names a composition root: the one module that has to import several Interface entry points (a template registry, a route dispatcher) and has no legal home on `depends_on` alone. A change id belongs to an open revision only: a shipped node with no open next carries none, so editing its files in place (no contract change) needs no change id and leaves no state to clear. A shipped node that claims a new file in place keeps that entry in `added_claims` until its body names it, so an addition made without a revision stays visible in review.

## Shared Substrate Spec

Intended files: `src/foundations/f-domain-model/`

- `types.ts` — `NODE_TYPES` (`Capability`, `Interaction`, `Interface`, `Foundation`, `Bug`), edges, state machines, `MindPlanNode` / `NextSlot`
- **Capability.** The top-level type, a permanent group of Interactions, is `Capability`; its computed states are `CAPABILITY_STATES` / `CapabilityState` (`draft | incubation | stable | evolving`). No type is named `Journey`: graphs from before migration level 3 are moved by `f-graph-migrations`, and nothing here keeps the old name
- `EDGE_TYPES` — `depends_on | belongs_to | exposes | leads_to | affects | mounts`
- `MindPlanNode.mounts?: string[]` and `NextSlot.mounts?: string[]` — Foundation → Interface ids; on the next slot they are proposed edges applied on ship, like `exposes`
- `MIRROR_STATE` (`mirror`) and `isMirrorState` — next-file twin state, not a pipeline state
- `NextSlot` remains draft|ready|in-progress|in-review only
- `MindPlanNode.rules?: string` — the node's own rules text, trimmed; omitted when empty. Loaded from the live `<id>.mdx` only (rules are slot-independent; `next` carries no separate rules)
- `RULE_VIAS` / `RuleVia` — `self | belongs_to | depends_on | affects`: how a rule entry reached the node it is resolved for
- `RuleEntry` — `{ node_id, node_type, via: RuleVia, distance: number, rules: string }`: one node's rules, labeled with the node it came from
- `RulesImpactEntry` — `{ id, type, state, via: RuleVia, distance }`: a node that inherits some other node's rules
- `isInactiveNode(node)` — true for `cancelled`, `deprecated`, and closed Bugs (`resolved`, `wontfix`): such nodes neither take nor give rules
- **Change groups.** `MindPlanNode.change?` / `change_ref?` and `NextSlot.change?` / `change_ref?`: a change id (`CHANGE_ID_PATTERN`, a slug) that ties revisions into one change, and an optional branch or PR reference. `activeChange(node)` is the open revision's change: `next.change` while a shipped node evolves, the live `change` before first ship, and nothing for a shipped node with no open next
- **No change id on a shipped node with no open next.** Such a node's live file carries no `change` / `change_ref`; editing its files in place needs none. `isShippedWithoutNext(node)` (a shipped, non-retired Foundation, Interaction, or Interface with no open next) is the one test for such a node, shared by the writers that Block `change` on it and by migration level 2, which strips a leftover scalar. `activeChange` ignores a leftover live `change` on such a node
- **In-place claims.** `MindPlanNode.added_claims?: string[]` — MCP-only, live slot only: claim entries a shipped node added in place without a revision, kept as a review marker until the live body names each one verbatim or the entry is no longer claimed. A promotion rebuilds the live frontmatter and drops it. `GRAPH_VERSION` stays `1`: a graph without it loads exactly as before
- **Decision records.** `DecisionRecord` — `{ id, decision, alternatives: string[], why, consequences?, supersedes?, change?, date? }`: what was chosen (one sentence), what else was considered (one line each), the constraint or trade-off that decided it, what it makes harder or forbids, the id of the decision it replaces, and the change id and date (`YYYY-MM-DD`) it was recorded under. `DECISION_ID_PATTERN` is `d-` followed by a slug
  - `MindPlanNode.decisions?` (from the live `<id>.mdx`) and `NextSlot.decisions?` (from an open `<id>.next.mdx`), in recorded order; omitted when empty
  - `activeDecisions(node)` — a node's decisions: the open next slot's while a shipped node evolves (that file starts as a copy of live), else the live ones
  - `DECISION_STATUSES` / `DecisionStatus` — `active | superseded`, computed and never stored
  - `DecisionEntry` — a record plus `node_id`, `node_type`, `status`, `superseded_by?`, and, when it reached a node through inheritance, `via` / `distance` (the `RuleVia` labels)
- `NextSlot.opened_at?` — when open_next opened the revision; promotion and discard drop it. The decision gate dates a revision's start from it
- **Linked tests.** `MindPlanNode.tests?: string[]` — MCP-only: repo-relative test files, directories ending in `/`, or globs that verify a Foundation, Interaction, or Interface. It is not ownership: a test file is still claimed through some node's `implements`, and several nodes may list the same file. Slot-independent like rules: one list, read from the live `<id>.mdx`; an open next carries the same list, so `NextSlot` has no field of its own. `GRAPH_VERSION` stays `1`: a graph without it loads exactly as before

Depends on: none.

- **Aliases.** `MindPlanNode.aliases?: string[]` — other words for the node (synonyms, user wording, other languages) that search indexes with its text. Any node type; slot-independent like `tests` (`NextSlot` has none)

- **Planned edges.** `PlannedEdge = { change, type, target }`, and `MindPlanNode.planned?: PlannedEdge[]`, read from the live file only: wiring a shipped Foundation, Interaction, or Interface will gain when the named change opens it (`belongs_to`, `depends_on`, `exposes`, `leads_to`, or `mounts`). Planned edges are not graph edges: `graph.edges` never contains them, so no rule, search, or projection treats them as real until the change opens the node
- **Attributed files.** `MindPlanNode.attributed?: string[]` and `NextSlot.attributed?: string[]`: exact files in another node's claimed folder that this slot's revision adds (a migration in a composition root's single migrations folder). Ownership stays with the folder's claimant; attribution only says which revision a file belongs to

- **Revision count and split record.** `MindPlanNode.revisions?: number` — how many times the node shipped (first ship and each promotion), on the live file of a shipped Foundation, Interaction, or Interface; absent on a node that never shipped or predates the field until init backfills it. `split_at?: number` — the revision at which the node last split parts out of itself; `split_into?: string[]` — the ids of the parts it split into, across every split. `churn?: number` — a decayed ship count as of `shipped_at`: each ship sets it to `previous × ½^(days since the previous ship / half-life) + 1`, and a split sets it to 0. All four are server-owned frontmatter, written only by ship and init; current state, not a log (git keeps the history). Not edges: `split_into` changes no import rule and no blast radius.
- **`keep_whole` decisions.** `DecisionRecord.keep_whole?: boolean` — the owner decided the node stays one node (for example auth, where every change is a security change). While such a decision is active, hotspot detection skips the node; superseding it turns detection back on.

## Acceptance Criteria

- `mirror` is a typed next-file state distinct from pipeline states
- Open-evolution types unchanged apart from the proposed `mounts` array and the next slot's `decisions`
- `mounts` is an `EdgeType`; a graph with no `mounts` edges loads exactly as before
- `MindPlanNode.rules` is optional; a graph with no rules sections loads exactly as before
- `RuleEntry` always names its source node and `via`
- `isInactiveNode` is true for exactly the four inactive states
- `GRAPH_VERSION` remains `1`
- Verified via `npm test`
- `activeChange` returns the next slot's change while evolving, the live change before first ship, and nothing for a shipped node with no open next
- `MindPlanNode.decisions` is optional; a graph with no `## Decisions` sections loads exactly as before
- `activeDecisions` returns the next slot's decisions while a node evolves and the live ones otherwise
- No stored decision field carries a status
- `activeChange` of a shipped node with no open next is nothing even when its live file still holds a leftover `change`
- `MindPlanNode.added_claims` is optional; a graph without it loads exactly as before
- `isShippedWithoutNext` is false for a retired node, a node with an open next, a pre-ship node, and a Capability or Bug
- `NODE_TYPES` is exactly `Capability`, `Interaction`, `Interface`, `Foundation`, `Bug`; `Journey` is not a node type
- `MindPlanNode.tests` is optional; a graph without it loads exactly as before, and `NextSlot` has no `tests`

- A node record carries `aliases` when its frontmatter has them

- `planned` and `attributed` round-trip through the graph load and the graph cache; no planned edge appears in `graph.edges`

- A node with `revisions: 4`, `split_at: 3`, and `split_into: [f-a, f-b]` loads them as a number, a number, and a list, and its record returns them

## Decisions

### d-computed-decision-status

- Decision: A decision's status is computed from whether an active decision supersedes it, never written into the old entry.
- Alternatives:
  - Write superseded into the old entry (cross-node writes into shipped files, and a stale mark when the superseding revision is discarded)
- Why: Supersession often crosses nodes (an Interaction replacing its Foundation's decision), and the superseding record can still be discarded with its revision.
- Consequences: Readers of a raw .mdx do not see that an entry is superseded; list_decisions and orient_for_work do.
- Change: decision-records
- Date: 2026-10-20

### d-neighbor-label-in-live-change

- Decision: A change's neighbor is a shipped node with no open next whose live <id>.mdx carries the change id in its existing change: scalar; one label per node, a new id replaces the old one.
- Alternatives:
  - A new neighbor_of list field so one node can sit in several changes (new schema field and merge noise for a case not yet seen)
  - Keep change ids revision-only and return a hint instead of Blocked (agents keep guessing and the change-scoped tools never see neighbors)
- Why: The live change scalar already exists, is cleared on first ship, and is ignored by activeChange for shipped nodes, so the label needs no schema change; two concurrent features on one shipped helper has not happened yet.
- Consequences: A node labeled by a second change silently leaves the first (the result reports replaced_change); open_next on a neighbor inherits its label as the revision's change because the mirror twin copies live.
- Change: shipped-claims-and-neighbors
- Date: 2026-10-23

### d-tests-as-file-list

- Decision: A node links its tests through an optional `tests` list of repo-relative test files, directories, or globs on its frontmatter, not through a new node type or edge.
- Alternatives:
  - A Test node type with a verifies edge (changes the taxonomy, the SPEC tables, and the lifecycle; every suite becomes a node to create and ship)
  - Move each suite under the node it tests and rely on implements claims (no many-to-many: a suite covering several nodes can be claimed by only one)
- Why: Tests are files, and one suite often verifies several nodes; a non-exclusive file list beside implements says exactly that with one optional field, so GRAPH_VERSION stays 1.
- Consequences: Ownership of a test file stays with whoever claims it in implements; tests only says which nodes it verifies. The graph cannot hold per-case test names, only files.
- Change: node-tests
- Date: 2026-10-25

### d-tests-slot-independent-evidence

- Decision: A node's `tests` list is slot-independent evidence, like its rules: one writer sets it on live and on an open next alike, a shipped node changes it in place without open_next, and the write never resets readiness.
- Alternatives:
  - Treat tests like implements: a contract write that needs open_next on a shipped node and sends a ready revision back to draft (linking an existing test to a shipped node would cost a full revision)
  - Keep tests only on the active slot (a discarded revision would drop links that still hold for the live code)
- Why: Linking a test records how a contract is verified; it does not change the contract, so it should neither cost a revision nor undo a review.
- Consequences: A revision cannot propose a different tests list from live; promote keeps the list it finds on next, which equals live.
- Change: node-tests
- Date: 2026-10-25

### d-aliases-slot-independent-search-words

- Decision: Aliases are an optional frontmatter list on any node, slot-independent like tests: create_node and patch_node_territory write them in place on shipped nodes too, without open_next or a readiness reset.
- Alternatives:
  - Treat aliases as contract text that needs open_next on a shipped node (adding a search word would cost a full revision)
  - A separate patch tool (one more tool for a field patch_node_territory can carry)
- Why: Aliases change how a node is found, not what it does; they should be as cheap to add as the moment a search misses.
- Consequences: A revision cannot propose different aliases from live; each alias is a JSON string in frontmatter.
- Change: aliases
- Date: 2026-10-25

### d-planned-edges-on-live-by-change

- Decision: Wiring a shipped node will gain is a planned edge: a live-file list of { change, type, target } entries, outside graph.edges, written by link_nodes with change, applied to the next slot when open_next opens the node with that change, kept on live until that revision ships (a discard leaves it planned), and dropped when its change closes.
- Alternatives:
  - Queued revisions: several pending next drafts per shipped node keyed by change id, each rebased when another ships (covers contract text too, but needs a rebase and conflict model for sections, claims, and decisions)
  - Write the edge live at once (it already works for a node with no open next, but the live graph would claim a shipped node exposes or depends on what is not built, and no gate reviews it)
  - Keep the wiring as prose in the feature's body (what the field report did; the check cannot validate prose)
- Why: The report's blocker was edges, not text: about 14 features each needed wiring on one shipped Interface. A planned edge records and validates that wiring without locking the node in a revision and without telling the live graph it already exists.
- Consequences: Contract text for a shipped node still waits for open_next; one revision per node at a time is unchanged. A change that ships without opening a node it planned wiring on loses those entries (reported as cleared_planned).
- Change: agent-guidance
- Date: 2026-10-30

### d-attributed-files-on-the-revision

- Decision: A revision lists the files it adds in another node's claimed folder as attributed on its own slot (set_implementation_files attributed); ownership stays with the folder's claimant, the decision gate and the blast radius count the files for the revision, and ship drops the list.
- Alternatives:
  - A migration_owner config mapping a migration name prefix or change id to a node (global and indirect: nothing on the revision says which migration is its own, and a naming convention must exist first)
  - Let the schema node claim the single migration file inside the root's folder (two owners would share one folder, which exclusivity and folder dominance forbid)
- Why: Payload and similar frameworks keep one migrations folder owned by the composition root, so the file's owner and the revision that needs it differ; naming the file on the revision is the smallest fact that lets the gate connect them.
- Consequences: An agent has to attribute the migration explicitly; an unattributed migration in the root's folder still counts only for the root, as before.
- Change: agent-guidance
- Date: 2026-10-30

### d-no-neighbor-labels

- Decision: A node's change id belongs to an open revision only (the next slot's, or a pre-ship node's live change); a shipped node with no open next carries no change id, and editing its files in place needs none.
- Alternatives:
  - Keep neighbor labels and fix how they clear (stored state that every write path must set, replace, and clear; the stale-label bug came from exactly that, and the label bought only a full stale-text pass and listings)
  - Keep the label but ignore it everywhere except the change check (dead state on disk that agents would still be told to write)
- Why: Editing a shipped node's files is already legal and the plain check already runs import and ownership rules on every node's files; the only real benefit (a full stale-text pass on files the change touched) can be derived from the git diff instead of stored.
- Consequences: A change's members are its open revisions and planned sources; in-place edits are invisible to change-scoped tools. Migration level 2 strips existing labels. change on a shipped node with no open next is Blocked.
- Supersedes: d-neighbor-label-in-live-change
- Change: graph-edges-stale-labels
- Date: 2026-10-31

### d-domain-model-revise-for-label-removal

- Decision: This revision reopens f-domain-model because it removes a field meaning (the neighbor label) rather than adding behavior.
- Alternatives:
  - A new node that depends_on f-domain-model (a removal cannot be added beside the node it removes from)
- Why: The change field's documented meaning and the shared predicate live here; leaving them would keep the removed concept in the model every node reads.
- Change: graph-edges-stale-labels
- Date: 2026-10-31

### d-capability-type-name

- Decision: The top-level node type is named Capability; Journey is no longer a type name.
- Alternatives:
  - Keep Journey: in UX a user journey is a sequence of steps, so agents and people model checkout steps as Journeys when the type is a permanent group of behaviors
  - Domain: in DDD the domain is the whole problem space, and it collides with this Foundation's own name
  - Area: already the tool word (list_areas, area), but it has no established architecture term behind it for agents to map onto
- Why: The type answers 'What does the product do?', which is what a business capability names; agents already know that term, so the name carries its meaning without a glossary.
- Consequences: Every existing graph needs upgrade_project (migration level 3) before any other tool works; tool inputs and outputs that said journey say capability; ids keep whatever prefix they were created with.
- Change: capability-type
- Date: 2026-11-01

### d-domain-model-revise-for-capability

- Decision: This revision reopens f-domain-model because the set of node types is its own contract, and renaming one type cannot be done beside it.
- Alternatives:
  - A new node that depends_on f-domain-model and adds the behavior without revising it: a type name cannot be added next to NODE_TYPES without keeping Journey as a second name, and ending that second name is the point of the change
- Why: NODE_TYPES and the computed state set live here and every reader imports them; a rename has to land in the one place that defines them.
- Change: capability-type
- Date: 2026-11-01
