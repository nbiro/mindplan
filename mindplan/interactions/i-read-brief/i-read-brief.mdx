# Read the brief

## Purpose

Gives the agent the systems dialect (playbook), the product description, and the mandatory project rules at session start, the rules again before each action (as a cheap `unchanged` reply when they still hold), and one SPEC section at a time from the running package, so rules are looked up instead of guessed.

## Actor & Trigger

Agent calls `get_project` before the first answer or code change in a session, `get_rules` before each action, `get_spec` when it needs a specific MindPlan rule, and `get_skill` when the playbook or server instructions route it to a skill.

## PRD / Execution Logic

Intended files: `src/interactions/i-read-brief/` (`handlers.ts`, `spec.ts`, `skills.ts`, `tools.ts`).

- `get_project` returns `{ path, description, rules, rules_version, playbook, check, version? }`: the bundled playbook (`templates/agent/playbook.md`), the brief from `mindplan/project.md`, the rules tagged with `rulesVersion` (`f-plan-views`), a `check` sentence naming `run_check`, and `version` only when `graphStatus()` (`f-graph-migrations`) is not `current`: its warning, which names `setup_project`, `upgrade_project`, or the package to upgrade to
- `get_rules({ known_version? })` returns `{ path, rules, rules_version }`, or `{ path, rules_version, unchanged: true }` when `known_version` still matches
- `get_spec({ topic? })` serves one part of the running package's SPEC.md by stable topic id (`SPEC_TOPICS`, matched by heading text without section numbers) or by tool name; without a topic it lists them; an unknown topic is Blocked and lists the valid ones (`findPackageFile` locates the bundled files)
- `get_skill({ name?, file? })` (`skills.ts`) serves the bundled skills under `templates/agent/skills/<name>/`: without `name` it lists `{ name, description, files }` for each (description from the SKILL.md frontmatter); with `name` it returns `{ name, text, files }`, `text` being SKILL.md without its frontmatter and `files` the other files in the folder; with `file` it returns `{ name, file, text }` for that file. An unknown name or file is Blocked and lists the valid ones; a `file` that leaves the folder is Blocked
- All four are reads with no drift, no orientation gate, and `gate: false`: they answer before setup and upgrade

Depends on: `f-plan-views`, `f-graph-migrations`, `f-tool-kit`.

## Acceptance Criteria

- `get_rules` returns the current rules, path, and `rules_version`; with the current tag as `known_version` it returns `unchanged: true` without the text, under 150 bytes; after `patch_project_rules` the tag changes
- `get_project` returns the playbook, brief, `rules_version`, and a `check` sentence naming `run_check`; its `version` names `setup_project` without a graph, `upgrade_project` for a graph behind the server, and the package for a stamp ahead of it, and is absent when current; it answers in every state
- `get_skill()` lists `plan-project` and `define-entities`; `get_skill({ name: "plan-project" })` returns its text without frontmatter; `get_skill({ name: "define-entities", file: "examples.md" })` returns that file; an unknown name, an unknown file, or a `../` path is Blocked
- `get_spec({ topic: "territory-shape" })` returns under 3 KB with the generated shape table; every topic resolves against the bundled SPEC.md; an unknown topic is Blocked and lists the valid ones
- Verified via `npm test`

## Decisions

### d-skills-served-by-server

- Decision: The MindPlan skills are served by the running server through get_skill (SKILL.md, plus a named supporting file), and the playbook and server instructions tell the agent when to load each; no host skill copies are installed.
- Alternatives:
  - Copy skills into .claude/skills and .cursor/skills (host auto-triggers them, but copies drift from the server and need the version stamp and a refresh step)
  - Serve them as MCP prompts (user-invoked only in most hosts, so the agent cannot load one when it needs it)
- Why: A served skill always matches the server that enforces it, and the playbook already routes agents to get_spec the same way; the owner accepted less reliable auto-triggering for that.
- Consequences: An agent loads a skill only when the playbook or instructions tell it to; skill names stay stable ids (plan-project, define-entities).
