# Read the brief

## Purpose

Gives the agent the systems dialect (playbook), the product description, and the mandatory project rules at session start, the rules again before each action (as a cheap `unchanged` reply when they still hold), and one SPEC section at a time from the running package, so rules are looked up instead of guessed.

## Actor & Trigger

Agent calls `get_project` before the first answer or code change in a session, `get_rules` before each action, `get_spec` when it needs a specific MindPlan rule, and `get_skill` when the playbook or server instructions route it to a skill.

## PRD / Execution Logic

Intended files: `src/interactions/i-read-brief/` (`handlers.ts`, `spec.ts`, `skills.ts`, `tools.ts`).

- `get_project` returns `{ path, description, rules, rules_version, playbook, check, version?, restart? }`: the bundled playbook (`templates/agent/playbook.md`), the brief from `mindplan/project.md`, the rules tagged with `rulesVersion` (`f-plan-views`), a `check` sentence naming `run_check` and the merge gate, `version` only when `graphStatus()` (`f-graph-migrations`) is not `current`: its warning, which names `setup_project`, `upgrade_project`, or the package to upgrade to, and `restart` only when the package installed under the running server differs from the one it booted: `packageRoot()`'s `package.json` is read fresh on every call and compared with `packageVersion()` (cached at boot), so an `npm install` that replaced the package under a running server is noticed. `restart` names both versions, says the running server's answers (`version` included) come from the version it booted, and tells the agent to have the MCP server restarted and call `get_project` again. It is advice only: no tool is gated on it, and an unreadable `package.json` gives none. The call records the rules as served to this session (`recordProjectRulesServed`, `f-orientation-ledger`), which is what lets the project rules gate (`Blocked: Rules`, `f-plan-writes`) pass for every later write
- `get_rules({ known_version? })` returns `{ path, rules, rules_version }`, or `{ path, rules_version, unchanged: true }` when `known_version` still matches, and records the rules as served. It is the explicit re-read: after a context summary, or when a reply's `project_rules` push was missed. Nothing requires it before each action: the gate needs the rules read once per session, and replies that orient and write results push them when they change
- `get_spec({ topic? })` serves one part of the running package's SPEC.md by stable topic id (`SPEC_TOPICS`, matched by heading text without section numbers) or by tool name; without a topic it lists them; an unknown topic is Blocked and lists the valid ones (`findPackageFile` locates the bundled files)
- `get_skill({ name?, file? })` (`skills.ts`) serves the bundled skills under `templates/agent/skills/<name>/`: without `name` it lists `{ name, description, files }` for each (description from the SKILL.md frontmatter); with `name` it returns `{ name, text, files }`, `text` being SKILL.md without its frontmatter and `files` the other files in the folder; with `file` it returns `{ name, file, text }` for that file. An unknown name or file is Blocked and lists the valid ones; a `file` that leaves the folder is Blocked
- **Session start (`session-start.ts`).** `sessionStartContext(input, root)` answers the Claude Code `SessionStart` hook (`mindplan-mcp hook session-start`, `if-cli`, wired by `if-claude-plugin`). For `source` `startup`, `clear`, or `compact` in a root that has `mindplan/` (the process root: `MINDPLAN_ROOT`, else cwd; the plugin's launcher runs it in the project directory), it returns `{ hookSpecificOutput: { hookEventName: "SessionStart", additionalContext } }`. `additionalContext` (`renderBrief`) is the `get_project` payload as Markdown, most binding first. It opens with one line saying that the server's write gate still needs `get_project` or `get_rules` once in this session. Then come the `version` warning when the graph needs setup or an upgrade, the `restart` notice, the project rules under their `rules_version`, the description, the `check` sentence, and the playbook. The playbook is replaced by a one-line pointer to `get_project` when including it would make the context longer than `BRIEF_BUDGET` (9,500 characters), because Claude Code caps hook context at 10,000 and swaps a longer one for a file preview. It is built by the same function `get_project` uses, so the two cannot drift. `resume` and `fork` return null, because the context still holds the brief. So do a root without `mindplan/`, malformed input, and an unreadable brief: the hook prints nothing. It does not record the rules as served (d-hook-brief-not-gate). `handlers.ts` splits `projectPayload()` (the payload, unrecorded) out of `getProject()` for it. The `hook` topic of `get_spec` names SPEC §9.8's heading, `Claude Code hooks and plugin`
- All four are reads with no drift, no orientation gate, and `gate: false`: they answer before setup and upgrade

Depends on: `f-plan-views`, `f-graph-migrations`, `f-tool-kit`, `f-orientation-ledger`.

## Acceptance Criteria

- `get_rules` returns the current rules, path, and `rules_version`; with the current tag as `known_version` it returns `unchanged: true` without the text, under 150 bytes; after `patch_project_rules` the tag changes
- `get_project` returns the playbook, brief, `rules_version`, and a `check` sentence naming `run_check`; its `version` names `setup_project` without a graph, `upgrade_project` for a graph behind the server, and the package for a stamp ahead of it, and is absent when current; it answers in every state
- In a fresh session a write before `get_project` is `Blocked: Rules`; after `get_project` (or `get_rules`) alone the same write passes the rules gate
- `get_project` has no `restart` while the installed package is the one the server booted; after the package's `package.json` version changes under a running server, `get_project` returns `restart` naming the installed and the running version, with or without a graph
- `get_skill()` lists `plan-project` and `define-entities`; `get_skill({ name: "plan-project" })` returns its text without frontmatter; `get_skill({ name: "define-entities", file: "examples.md" })` returns that file; an unknown name, an unknown file, or a `../` path is Blocked
- `get_spec({ topic: "territory-shape" })` returns under 3 KB with the generated shape table; every topic resolves against the bundled SPEC.md; an unknown topic is Blocked and lists the valid ones
- `sessionStartContext` for `startup`, `clear`, or `compact` in a graph returns `additionalContext` holding the gate line first, the rules text, `rules_version`, and the playbook; with rules long enough to pass `BRIEF_BUDGET` it keeps every rule, stays within 10,000 characters, and names the left-out playbook; for `resume` it returns null; without `mindplan/` it returns null; for a graph behind the server it carries the version warning naming `upgrade_project`
- After `sessionStartContext`, a write in a fresh MCP session before `get_project` is still `Blocked: Rules`
- Verified via `npm test`
