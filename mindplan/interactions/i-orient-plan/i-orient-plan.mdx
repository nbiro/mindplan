# Orient on the plan

## Purpose

Read-path orientation on one node or one change. `orient_for_work` returns the rules that apply to the focus node, each labeled with the node it came from, and the decisions that shaped it, at every depth: the reasoning behind a shared design reaches the agent before it touches anything, which is the moment it would otherwise simplify the design back into the problem it avoided. Because orientation runs before every action, it can be asked for less: a `depth` says whether the agent needs only the rules and record, also the body, or the full neighborhood, blast radius, and stability. A full reply also records the node as oriented, which is what lets the write actions' gate pass. The brief (`i-read-brief`), the blast radius alone (`i-assess-impact`), and graph-wide browsing (`i-browse-graph`) are separate actions.

## Actor & Trigger

- **Actor:** coding agent or human via MCP (`if-mcp-tools`) or console API (`if-console-api`)
- **Trigger:** MCP/HTTP orient tools; `get_project` / `get_rules` with no arguments; `orient_for_work` with a focus

## Execution Logic

Intended files: `src/interactions/i-orient-plan/` (`handlers.ts`, `tools.ts`).

This action covers `orient_for_work`, `get_node_context`, `get_node_implementation`, and `find_related_nodes`. The blast radius is `i-assess-impact`'s (`get_blast_radius`), the brief `i-read-brief`'s (`get_project`, `get_rules`, `get_spec`), and the paged graph, areas, and decision lists `i-browse-graph`'s; the payloads they share live in `f-plan-views`.

- **Hybrid ranking.** `find_related_nodes` and `orient_for_work` rank through `searchNodes` (`f-graph-search`) with the project root and `territoryBodyReader()` (`f-territory-store`), and are async (the query embedding); both take `area` (a Journey id; anything else is Blocked) and rank only its members
- **Summary first.** `orient_for_work({ query })` without `node_id` returns `{ query, matches, focus: null, next }`: rows `{ id, type, state, title, description (70 characters), area?, score }`, default 8, no body, rules, or decisions. A clear winner (`clearWinner`: its exact id, the only match, or twice the next score, looking one match past the limit) comes back in full with `auto_focus: true`. `orient_for_work({ node_id })` returns the full node: `rules`, `decisions`, `context`, from `depth: "body"` on `files` (`nodeOwnedFiles`) for a pipeline node; `full` adds the 1-hop `nodes` / `edges`, `blast_radius` (`buildBlastRadiusPayload`, `f-plan-views`), and for a pipeline node `stability` (`{ fan_in, rate, median_rate, revisions?, split_at?, split_into?, hotspot? }`, `f-compiler-rules`)
- **Rules block.** `{ node_id, entries }` from `reachingRules` (live edges plus an open revision's proposed ones), ordered self, `belongs_to`, `depends_on`, `affects`; each entry carries `version` (`rulesVersion`, `f-plan-views`); `known_rules_versions` leaves out known text (`unchanged: true`); `null` without a focus; never the project brief rules
- **Orientation ledger.** Every full reply and every `get_node_context` records the node with `recordOriented` (`f-orientation-ledger`), which is what lets the write actions' gate pass; `get_node_context` returns `resolved_rules` because it counts as orienting
- **Depth.** `full` (default), `body` (no neighborhood or blast radius, which are not computed), `rules` (the record only)
- **One slot, one section.** Both tools take `slot` (`orient_for_work` defaults to the active slot, `get_node_context` to both; `slot: "next"` without a revision is Blocked) and `section` (each returned body cut to that `## heading`; a missing heading is Blocked and lists the sections); `depth: "rules"` ignores both
- **Decisions.** `orient_for_work` returns `decisions` at every depth: `{ node_id, entries, inherited_decisions }`, the focus's own (`via: self`; a Bug: the nodes it affects) and `{ count, nodes }` for the inherited ones, with `include_inherited_decisions` adding them (whole at distance 1, one line beyond) and `include_superseded` adding superseded ones; compact entries at `depth: "rules"`. Its `context` leaves decisions out (the block is the reply's only copy). `get_node_context` keeps `decisions` and `next.decisions` (superseded left out unless asked), adds `inherited_decisions`, and returns `body` without `## Rules` and `## Decisions`
- **Shape up front.** Every full reply and `get_node_context` carry `shape` (`shapeReport`) while the node has a transition ahead
- **Change-wide orientation.** `orient_for_work({ change, known_rules_versions? })` returns `{ change, members, rules, decisions }` over `changeMembership` (revisions, neighbors, planned sources, each with `kind` and `rules_from`), each rule source once, and records every member, so one call clears the gate for a scoped walk; a change with no members, or `change` with `query` or `node_id`, is Blocked
- **Implementation.** `get_node_implementation` expands glob claims to concrete files (`files` / `next_files`) and finds a path's owner through a glob claim; node records carry `change` / `change_ref` and `tests`

Depends on: `f-plan-views`, `f-graph-search`, `f-territory-store`, `f-compiler-rules`, `f-source-index`, `f-orientation-ledger`, `f-tool-kit`.

## Acceptance Criteria

- A query-only `orient_for_work` returns rows only, under 2 KB for 10 rows; an exact id query auto-focuses; `orient_for_work({ node_id })` returns record, body, rules, own decisions, owned files, blast radius, and stability
- A full reply and `get_node_context` count as orienting on the node
- A search with `area` returns only that area's members and is at least as fast as a whole-graph search; a non-Journey `area` is Blocked
- Each `orient_for_work` rules entry carries `version`; a known version leaves out that entry's text, and a changed node rules text comes back with a new version
- `orient_for_work` on an Interaction returns its own rules, its Journey's, and its Foundations' (transitive), each naming its source and `via`; on a Journey only the Journey's own; on a Bug the resolved rules of the nodes it affects; siblings never appear in each other's `rules`; `rules` is `null` without a focus and `entries` is `[]` when no rules apply
- `depth: rules` returns rules and the record only; `depth: body` adds the body; neither returns `blast_radius`, `nodes`, `edges`, or `stability`
- `get_node_context` `body` excludes the Rules and Decisions sections, which come back as `rules` and `decisions`; a superseded decision is left out unless `include_superseded`
- `orient_for_work` on an Interaction returns only its own decisions by default, with `inherited_decisions.count` and `nodes`; with `include_inherited_decisions` it returns its Foundation's decision labeled with the Foundation's id, and one-line entries past distance 1; on a node shaped like skyloom's `i-contact-platform` the default reply carries one decision and `inherited_decisions.count` 12; on a Bug it returns the decisions of the nodes it affects
- An `orient_for_work` reply carries the focus's decisions once (no `context.decisions` or `context.next.decisions`)
- With a revision open, `orient_for_work` at `depth: "body"` returns only the next body; `slot: "current"` returns only the live body; `get_node_context` returns both unless `slot` is passed; `slot: "next"` without a revision is Blocked
- `section` returns only that section of each returned body and Blocks on a missing heading, listing the sections
- A full reply on a scaffolded draft lists every required section with `missing` or `stub`; a shipped node with no open revision has no `shape`
- `orient_for_work({ change })` on a change with three members returns their rules once per source and records all three; a known version leaves its text out
- A glob claim expands to concrete files in `get_node_implementation`, and a path under it resolves to its owner; `get_node_context` returns a node's `tests` list
- A full reply on a pipeline node carries `stability` with `fan_in`, `rate`, and `median_rate`, plus `hotspot` when the node is one
- Verified via `npm test`

## Decisions

### d-node-context-hides-superseded

- Decision: get_node_context leaves superseded decisions out of decisions and next.decisions unless include_superseded, the same default and flag as list_decisions and orient_for_work.
- Alternatives:
  - Keep returning every entry because the full read is meant for history (a node with a long trail buries its current decisions, and the two readers disagree on the same default)
  - Return every entry with status and let the caller filter (every caller reimplements the same filter that list_decisions already applies)
- Why: Every decision reader should answer the same question by default: what currently applies. The trail stays one flag away.
- Consequences: A client that relied on superseded entries in get_node_context must pass include_superseded.
- Change: node-context-superseded
- Date: 2026-10-20

### d-graph-paged-by-offset-limit

- Decision: get_mindplan_graph pages nodes by offset and limit (default 200, max 500), returns edges whose source is in the page, and reports totals and next_offset.
- Alternatives:
  - Truncate at a character budget and flag it (a cut JSON array is unparseable, and the agent cannot ask for the rest)
  - Return summaries only and point to get_node_context (changes the result shape for every small project that fits in one page)
  - Cursor-based paging (a cursor adds state for a sorted, static list that an offset already addresses)
- Why: Claude Code truncates a result over 25,000 tokens silently; a page the agent can walk keeps every node and edge reachable, and a graph that fits in one page keeps the old shape plus totals.
- Consequences: Edges are partitioned by source, so a client must walk every page to see every edge; the CLI and the map projection do not use the page.
- Change: mcp-audit-fixes
- Date: 2026-10-20

### d-own-decisions-by-default

- Decision: orient_for_work, get_node_context, and get_blast_radius return only the focus node's own decisions by default (a Bug: those of the nodes it affects directly), plus inherited_decisions: { count, nodes }; include_inherited_decisions: true adds the inherited entries, whole at distance 1 and as one line { id, node_id, distance, decision } beyond.
- Alternatives:
  - Keep returning every inherited decision in full (on a 54-node graph one orient reply carried 13 decisions and about 60% of 22 KB, mostly from nodes three links away)
  - Drop inherited decisions entirely (the agent would not know they exist, and could simplify a Foundation's design back into the problem it avoided)
- Why: Orientation runs before every action; the decisions that shape the focus itself are what an edit there must respect, and a count with the holding nodes is enough to ask for the rest when a change reaches them.
- Consequences: A client that read inherited decisions from decisions.entries must pass include_inherited_decisions; list_decisions still returns any node's full records.
- Change: own-decisions
- Date: 2026-10-25

### d-blast-radius-own-decisions

- Decision: get_blast_radius returns the focus's own decisions by default plus dependent_decisions: { count, nodes }; include_dependent_decisions: true adds the dependents' one-line entries as before.
- Alternatives:
  - Reuse include_inherited_decisions for dependents (dependents' decisions are downstream, not inherited, and the flag would mean two things)
  - Always list dependents' decisions (they made up most of an orient_for_work full reply through its embedded blast radius)
- Why: The radius answers who a change reaches; the count and node ids say whose reasoning to read, and the list stays one flag away.
- Consequences: orient_for_work at depth full embeds the default radius, so its reply no longer carries dependents' decisions.
- Change: own-decisions
- Date: 2026-10-25

### d-summary-first-orient

- Decision: orient_for_work with only a query returns ranked rows (id, type, state, title, a 70-character description, area, score; default 8) and the full node only for a clear winner (its exact id, the only match, or twice the next score: auto_focus); orient_for_work({ node_id }) returns the full node.
- Alternatives:
  - Keep the full payload for the top match (about 22 KB on a 54-node graph, mostly for a node the agent may not work on)
  - Rows only, never auto-focus (an exact id or an obvious winner would always cost a second call)
- Why: A summary list costs about 2 KB for 10 rows and lets the agent pick; with hybrid ranking the top row is usually right, and the second call happens only when the choice is unclear.
- Consequences: A client that read context, rules, or blast_radius from a query-only reply must pass node_id or read auto_focus; row descriptions are cut, so a node's full description comes with its full reply.
- Change: summary-orient
- Date: 2026-10-25

### d-orientation-write-gate

- Decision: Writes that act on a node are Blocked: Orientation until the node had a full reply in this MCP session (orient_for_work with node_id or auto_focus, get_node_context, its create_node, or a link result that returned its new rules), and again once the rules that reach it changed; create_node is never blocked; the CLI is never gated.
- Alternatives:
  - No gate (summary-first orientation would let an agent write without ever seeing a node's rules, making node rules optional)
  - Gate create_node too (the owner ruled it out: a new node has no rules yet beyond the ones its result returns)
- Why: Node rules are mandatory and used to arrive with every orient; once orient returns rows first, only a gate keeps them from being skipped.
- Consequences: A fresh session must orient on each node before writing it, and a rules change on a Journey or Foundation sends its dependents back to orient; the author of a rules change stays oriented.
- Change: summary-orient
- Date: 2026-10-25

### d-list-areas-table

- Decision: list_areas returns one compact table, { columns, rows }, a row per Journey: [id, title, description cut to 60 characters, interactions, interfaces, foundations, open_bugs], not an object per Journey.
- Alternatives:
  - An object per Journey with a counts object (the keys alone take about 95 bytes per area, so 30 areas cannot stay under the 4 KB budget)
  - Drop descriptions (a title alone often does not say what an area covers)
- Why: The tool exists to be cheap enough to call before orienting; a table keeps 30 areas under 4 KB with the description that makes the pick possible.
- Consequences: Clients read a row by its column index; the full description comes from orient_for_work on the Journey.
- Change: list-areas
- Date: 2026-10-25

### d-area-scope-members

- Decision: An area (a Journey id) scopes search to the Journey itself, the Interactions that belong to it, the Interfaces that expose them, and the Foundations they depend on transitively (live and proposed edges); Bugs are outside it.
- Alternatives:
  - Only the Interactions (the Interface and Foundation an agent changes for that area would never rank)
  - Everything one link away (pulls in unrelated Journeys' Interactions through shared Interfaces)
- Why: That set is where work for the area lands; a Bug is found by what it affects, or by searching without an area.
- Consequences: A shared Foundation appears in every area that uses it; a cross-cutting question searches without area.
- Change: list-areas
- Date: 2026-10-25

### d-orient-active-slot-default

- Decision: orient_for_work returns only the active slot's body by default (next while a revision is open) and its decisions only in the top-level block; get_node_context keeps both slots by default and both take slot and section.
- Alternatives:
  - Add slot and section but keep both bodies by default in orient_for_work (every orient on an evolving node still pays for two near-identical bodies)
  - Default get_node_context to the active slot too (it is the full read; comparing live with next is what it is for)
  - Page a body by character offset (a cut can split a section or a checkbox line; headings are the unit agents edit by)
- Why: Orientation runs before every action and nearly every edit targets the active slot; a reply that repeats the body and the decisions doubled its size and could exceed the host's result limit on a large node.
- Consequences: A client that read the live body from orient_for_work while a revision is open must pass slot: "current"; a client that read context.decisions must read the decisions block.
- Change: lean-node-replies
- Date: 2026-10-29

### d-spec-topics-by-heading-text

- Decision: get_spec serves the running package's SPEC.md through a fixed map of stable topic ids to SPEC headings, matched by heading text without section numbers; without a topic it lists the ids.
- Alternatives:
  - A spec field on get_project (every session start would pay for it, or get_project would grow a parameter it does not need)
  - Address sections by number (renumbering SPEC would silently change what a topic returns)
  - Serve the whole SPEC (about 1,700 lines, past what an agent should load for one answer)
- Why: Agents need one answer at a time from the version that is enforcing the rules; stable ids survive SPEC edits, and the npx cache can no longer hand them a stale copy.
- Consequences: A SPEC heading rename must update SPEC_TOPICS; a test resolves every topic so a rename fails the suite.
- Change: agent-guidance
- Date: 2026-10-30
