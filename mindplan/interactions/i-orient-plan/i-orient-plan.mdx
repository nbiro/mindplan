# Orient on the plan

## Purpose

Read-path orientation. `get_rules` returns only the mandatory project-wide rules so each action can re-load them without the full playbook; `orient_for_work` returns the rules that apply to the focus node, each labeled with the node it came from. A later session that skipped either would treat rules as optional after the first `get_project`, and a rule written on a Foundation would stop protecting the code that depends on it. Because orientation runs before every action, it can be asked for less: a `depth` says whether the agent needs only the rules and record, also the body, or the full neighborhood and blast radius. `get_project` names the check so the first read tells the agent how to verify its work. Next to the rules, `orient_for_work` returns the decisions that apply to the focus, labeled by source the same way and at every depth: the reasoning behind a shared design reaches the agent before it touches anything, which is the moment it would otherwise simplify the design back into the problem it avoided. Superseded decisions stay out of that block; `list_decisions` reads the full trail on request, and `get_blast_radius` names the decisions a change would reach.

## Actor & Trigger

- **Actor:** coding agent or human via MCP (`if-mcp-tools`) or console API (`if-console-api`)
- **Trigger:** MCP/HTTP orient tools; `get_project` / `get_rules` with no arguments; `orient_for_work` with a focus

## Execution Logic

Intended files: `src/interactions/i-orient-plan/`

- Keep existing query tools
- **Hybrid ranking.** `find_related_nodes` and `orient_for_work` rank through `searchNodes` (`f-graph-search`) with the project root and `territoryBodyReader()` (`f-territory-store`) for section headings, and pass the ranked rows to `findRelatedNodes` as `matches`; both handlers are async (the query embedding), and their result shapes are unchanged
- `get_project` — `{ path, description, rules, playbook, check, version? }` (first read of dialect + brief); `check` is a fixed sentence naming `run_check` and the CLI `mindplan-mcp check`; `version` is present only when `projectVersionStatus()` is not `current`, and is its warning sentence
- `get_rules` — `{ path, rules }` from `loadProjectBrief()`; empty string when the section is empty; no playbook, no description. These are the **global** rules only: rules that apply everywhere. Rules about one area of the code live on that area's node
- `orient_for_work` returns a separate `rules` block next to `context` and `blast_radius`: `{ node_id, entries: RuleEntry[] }` from `resolveNodeRules` (`f-graph-search`), or `null` when there is no focus. Each entry is `{ node_id, node_type, via, distance, rules }`, ordered self, then `belongs_to`, then `depends_on`, then `affects`. `entries` is `[]` when nothing applies. It does **not** repeat the project brief rules
- `orient_for_work` takes `depth`: `full` (default) returns everything; `body` returns `{ query, matches, focus, context, rules }` with the full context; `rules` returns the same keys with `context` cut to the record (and the next record). `body` and `rules` skip the neighborhood and the blast radius, and do not compute the blast radius
- `get_node_context` returns `body` without the `## Rules` section and a separate `rules` string for that node's own rules (and the same for the `next` slot's body)
- `get_blast_radius` adds `rules_impact` for every focus type: `{ node_id, has_rules, inherited_by: RulesImpactEntry[] }` from `rulesAudience`. It reports who is reached by the focus's rules, so editing a Foundation's rules shows every dependent; `affected` / `affected_files` / `reachability` are unchanged. When the focus has no rules, `has_rules` is `false` and `inherited_by` is `[]`
- Rules are advisory prose: nothing here is a `Blocked:`
- **Change blast radius.** `get_blast_radius` takes `node_id` or `change`. For a change it merges the members' radii: `{ change, members, affected, journeys_at_risk, affected_files, rules_impact }` where `affected` keeps the smallest distance and leaves out the members themselves. Members are the change's open revisions (`changeMembers`) and its neighbors (`changeNeighbors`, shipped nodes it edits in place), each listed with `kind: "revision" | "neighbor"`; a change with neither is Blocked (`has no members`)
- **Glob claims.** `get_node_implementation` expands glob claims to concrete files (`files` / `next_files`); path lookup finds the owner through a glob claim
- Node context shows `change` / `change_ref` on the live record and the next record
- **Decisions block.** `orient_for_work` returns `decisions` next to `rules` at every depth: `{ node_id, entries: DecisionEntry[], inherited_decisions }`. `splitNodeDecisions` splits `resolveNodeDecisions`: `entries` are the focus's own (`via: self`; for a Bug, the nodes it affects directly, `via: affects`, distance 1, since a Bug holds none), and `inherited_decisions: { count, nodes }` names the rest (`belongs_to`, `depends_on`, a Bug's further `affects`), nodes nearest first; `include_inherited_decisions: true` adds `inherited_decisions.entries`, whole at distance 1 (compact at `depth: "rules"`) and one line `{ id, node_id, distance, decision }` beyond. Each entry carries its record, `node_id`, `node_type`, `via`, `distance`, and `status`; superseded entries are left out unless `include_superseded: true` (then each names `superseded_by`); at `depth: "rules"` each entry is compact (`id`, `decision`, `why`, and its labels) because orientation runs before every action, while `body` / `full` and `list_decisions` return whole records; `null` without a focus
- **`list_decisions({ node_id?, change?, include_superseded? })`** → `{ decisions: DecisionEntry[], count }` from `listDecisions`: one node's own decisions (its active slot), every decision recorded under a change, or every decision in the graph; superseded entries only with `include_superseded`, each then naming `superseded_by`. Blocked on an unknown node. Listed in `QUERY_TOOLS`
- `get_node_context` returns `body` without the `## Decisions` section too, plus `decisions` (the live file's entries, each with `status`) and `next.decisions` for an open next, whose record also shows `opened_at`. It takes `include_superseded` (default `false`) like `list_decisions`: superseded entries are left out of both lists unless asked for, so a long trail does not bury the decisions that currently apply. `orient_for_work` passes its own `include_superseded` through to the `context` it embeds
- `get_blast_radius` adds `decisions`: the active decisions held by the focus (`via: focus`, distance 0), each `{ id, node_id, via, distance, decision }`, and `dependent_decisions: { count, nodes }` for the visible affected nodes that hold decisions; `include_dependent_decisions: true` adds their rows (`via: dependent`, their distance) to `decisions`; inactive nodes' decisions are left out and uncounted, even with `include_retired`. The change radius merges them across members (a member's own decisions are `focus`; each non-member holder counts once). `orient_for_work` at `depth: "full"` embeds the default radius
- `get_node_context` adds `inherited_decisions` (the same summary, except that a Bug's affected nodes, whose decisions orient lists as the Bug's own, are inherited there, whole at distance 1, since the context's `decisions` are the node's own file's) and takes `include_inherited_decisions` for its entries; a one-line entry names `status` and `superseded_by` when superseded; `orient_for_work`'s embedded `context` leaves it out because the decisions block carries it
- **Paged graph.** `get_mindplan_graph({ offset?, limit? })` returns `{ nodes, edges, total_nodes, total_edges, offset, limit, next_offset? }`. Nodes are sorted by id and sliced by `offset` (default 0) and `limit` (default `GRAPH_PAGE_DEFAULT` = 200, max `GRAPH_PAGE_MAX` = 500, both exported from this package); `edges` holds every edge whose source is in the page, so a client that walks every page sees every edge exactly once; `next_offset` is present only when nodes remain. A graph that fits in one page returns the same `nodes` and `edges` as before plus the totals, so a small project sees no truncation. `offset` past the end returns an empty page with the totals, not Blocked. The default page keeps one result of a typical graph (about 400 characters per node) under Claude Code's 25,000-token result limit; the tool description names `next_offset`
- **Linked tests.** `buildBlastRadiusPayload` adds `tests`: the sorted files that the `tests` lists of the focus and of every owner in `affected_files` expand to (`expandClaims`, `f-source-index`), so a change knows which suites to run; `buildChangeBlastRadiusPayload` merges them across members. Node records (`get_node_context`, `orient_for_work`, `get_mindplan_graph`) carry the node's `tests` list

Depends on: `f-graph-search`, `f-territory-store`, `f-compiler-rules`, `f-source-index`.

## Acceptance Criteria

- `get_rules` returns the current project rules string and path, unchanged in shape
- `get_project` still returns playbook + brief, plus a `check` sentence naming `run_check`
- `get_project` adds a `version` warning sentence when `mindplan/version.json` is missing, unreadable, behind, or ahead of the running package, and omits it when current
- `orient_for_work` on an Interaction returns its own rules, its Journey's, and its Foundations' (transitive), each entry naming its source node and `via`
- `orient_for_work` on a Journey returns only the Journey's own rules; on a Bug returns the resolved rules of the nodes it affects
- Sibling Interactions never appear in each other's `rules`
- `rules` is `null` without a focus and `entries` is `[]` when no rules apply
- `depth: rules` returns rules and the record only; `depth: body` adds the body; neither returns `blast_radius`, `nodes`, or `edges`; the default is unchanged
- `get_blast_radius` on a Foundation with rules lists its transitive dependents in `rules_impact.inherited_by`
- `get_node_context` `body` excludes the Rules section and `rules` carries it
- Verified via `npm test`
- Change blast radius lists the union of the members' dependents without the members
- Change blast radius includes a neighbor's dependents and lists the neighbor with `kind: "neighbor"`; a change with only neighbors is not Blocked
- A glob claim expands to concrete files in `get_node_implementation`, and a path under it resolves to its owner
- `orient_for_work` on an Interaction returns only its own decisions by default, with `inherited_decisions.count` and `nodes`; with `include_inherited_decisions` it returns its Foundation's decision labeled with the Foundation's id, at every depth, and one-line entries past distance 1; a superseded one is left out unless `include_superseded`
- On a node shaped like skyloom's `i-contact-platform` (one own decision, twelve inherited from its Journey and three Foundations), the default reply carries one decision and `inherited_decisions.count` 12
- `orient_for_work` on a Bug returns the decisions of the nodes it affects
- `list_decisions` returns a node's, a change's, and the graph's decisions; with `include_superseded` the superseded entry carries `superseded_by`
- `get_blast_radius` on a Foundation lists its own active decisions and names its dependents that hold decisions; with `include_dependent_decisions` it lists theirs too
- `get_node_context` `body` excludes the Decisions section and `decisions` carries it
- `get_node_context` leaves a superseded decision out of `decisions` by default and returns it with `include_superseded`, naming `superseded_by`; `orient_for_work` with `include_superseded` shows it in `context.decisions` too
- `get_mindplan_graph` on a graph larger than `limit` returns `limit` nodes, only edges from those nodes, the totals, and `next_offset`; walking every page yields every node and every edge exactly once; a graph within one page returns no `next_offset`; `limit` above 500 is rejected at the schema layer
- `get_blast_radius` lists the expanded tests of the focus and its affected owners, and the change radius merges them
- `get_node_context` returns a node's `tests` list

## Decisions

### d-node-context-hides-superseded

- Decision: get_node_context leaves superseded decisions out of decisions and next.decisions unless include_superseded, the same default and flag as list_decisions and orient_for_work.
- Alternatives:
  - Keep returning every entry because the full read is meant for history (a node with a long trail buries its current decisions, and the two readers disagree on the same default)
  - Return every entry with status and let the caller filter (every caller reimplements the same filter that list_decisions already applies)
- Why: Every decision reader should answer the same question by default: what currently applies. The trail stays one flag away.
- Consequences: A client that relied on superseded entries in get_node_context must pass include_superseded.
- Change: node-context-superseded
- Date: 2026-10-20

### d-graph-paged-by-offset-limit

- Decision: get_mindplan_graph pages nodes by offset and limit (default 200, max 500), returns edges whose source is in the page, and reports totals and next_offset.
- Alternatives:
  - Truncate at a character budget and flag it (a cut JSON array is unparseable, and the agent cannot ask for the rest)
  - Return summaries only and point to get_node_context (changes the result shape for every small project that fits in one page)
  - Cursor-based paging (a cursor adds state for a sorted, static list that an offset already addresses)
- Why: Claude Code truncates a result over 25,000 tokens silently; a page the agent can walk keeps every node and edge reachable, and a graph that fits in one page keeps the old shape plus totals.
- Consequences: Edges are partitioned by source, so a client must walk every page to see every edge; the CLI and the map projection do not use the page.
- Change: mcp-audit-fixes
- Date: 2026-10-20

### d-own-decisions-by-default

- Decision: orient_for_work, get_node_context, and get_blast_radius return only the focus node's own decisions by default (a Bug: those of the nodes it affects directly), plus inherited_decisions: { count, nodes }; include_inherited_decisions: true adds the inherited entries, whole at distance 1 and as one line { id, node_id, distance, decision } beyond.
- Alternatives:
  - Keep returning every inherited decision in full (on a 54-node graph one orient reply carried 13 decisions and about 60% of 22 KB, mostly from nodes three links away)
  - Drop inherited decisions entirely (the agent would not know they exist, and could simplify a Foundation's design back into the problem it avoided)
- Why: Orientation runs before every action; the decisions that shape the focus itself are what an edit there must respect, and a count with the holding nodes is enough to ask for the rest when a change reaches them.
- Consequences: A client that read inherited decisions from decisions.entries must pass include_inherited_decisions; list_decisions still returns any node's full records.
- Change: own-decisions
- Date: 2026-10-25

### d-blast-radius-own-decisions

- Decision: get_blast_radius returns the focus's own decisions by default plus dependent_decisions: { count, nodes }; include_dependent_decisions: true adds the dependents' one-line entries as before.
- Alternatives:
  - Reuse include_inherited_decisions for dependents (dependents' decisions are downstream, not inherited, and the flag would mean two things)
  - Always list dependents' decisions (they made up most of an orient_for_work full reply through its embedded blast radius)
- Why: The radius answers who a change reaches; the count and node ids say whose reasoning to read, and the list stays one flag away.
- Consequences: orient_for_work at depth full embeds the default radius, so its reply no longer carries dependents' decisions.
- Change: own-decisions
- Date: 2026-10-25
