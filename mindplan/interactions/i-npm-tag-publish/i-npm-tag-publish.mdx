# Publish on merge to main

## Purpose

Release by merging: when a push to `main` carries a `package.json` version that npm does not have yet, GitHub Actions runs the **same publish script** owned by `i-npm-publish`, publishes via npm Trusted Publishing (OIDC), and tags the commit `vX.Y.Z`. The version on the registry decides, not the commit message or a tag, so a merge without a version bump publishes nothing and a re-run never publishes twice.

This Interaction **solely owns** `.github/workflows/publish.yml` (a repo-root workflow path, an intentional exception to the prescribed package, like CI YAML).

## Actor & Trigger

- **Actor:** maintainer merging a PR (or pushing) to `main`; GitHub Actions runs the jobs
- **Trigger:** `push` to `main`, plus `workflow_dispatch` on `main` to retry a failed release

## Goal

Maintainer release path after the first claim:

```bash
npm version minor --no-git-tag-version   # in the PR that should ship
# merge the PR to main
```

CI publishes `mindplan-mcp@X.Y.Z` using OIDC and pushes tag `vX.Y.Z`.

## Acceptance Criteria

- [x] A push to `main` whose `package.json` version is not on npm publishes that version and pushes tag `vX.Y.Z` on the pushed commit. — note: merge of #52: run 40229545536 published 0.2.1 and pushed v0.2.1 on 71a5875
- [x] A push to `main` whose version is already on npm publishes nothing and does not wait for an environment approval. — note: merge of #50: run 39977013169 found 0.1.0 on npm and skipped the publish job in 11s
- [x] Auth is npm Trusted Publishing only — no `NPM_TOKEN` repository secret.
- [x] Only the publish job uses GitHub Environment `npm-publish` (where maintainers may require reviewers), so skipped pushes never wait for approval.
- [x] Release job invokes the shared publish script in CI mode (must include `npm test` — not a bare `npm publish`).
- [x] CI mode refuses any ref other than `refs/heads/main`, and exits 0 without publishing when the version is already on npm.
- [x] Two pushes in quick succession never publish concurrently. — note: workflow-level concurrency group `publish`, cancel-in-progress false
- [x] Live Trusted Publisher on npmjs.com is bound to this workflow **after** first claim. — note: 0.2.0 and 0.2.1 published over OIDC
- [x] `CONTRIBUTING.md` documents: bump the version in a PR → merge to main.
- [x] After a release, Dependabot opens a PR repinning the exact `mindplan-mcp` devDependency to it, and opens no version-update PR for any other dependency. — n/a: Dependabot replaced by the repin job in publish.yml before its first run; see the repin criterion below
- [x] After a release, the `repin` job opens a PR that pins the exact `mindplan-mcp` devDependency to it (bumping no version) and dispatches CI on it; a re-run does not open a second PR. — note: 0.2.2 release run 40230396563: repin opened #54 (package.json and lockfile only, 0.2.0 -> 0.2.2) and dispatched CI run 40230576949 (green); re-running the repin job logged that the branch exists and opened no second PR; merging #54 published nothing (run 40230756924 skipped publish and repin)
- [x] When the CI run dispatched on a repin branch is green, its `merge-repin` job merges the repin PR (merge commit; the branch stays); a red run, a PR touching other files, or a head that moved past the tested commit leaves the PR open. — note: 0.5.2 and 0.5.3: dispatched CI runs 40334685882 and 40376553178 passed and merge-repin merged #73 (93c074d) and #75 (c75a878) as github-actions, package.json and package-lock.json only; the red 0.5.0 run 40294907477 skipped merge-repin and left #69 unmerged

## Execution Logic

Belongs to: `j-npm-publish`. Depends on: `f-github-actions`, `f-npm-registry`. Runs the script owned by `i-npm-publish`.

### Owns

- `.github/workflows/publish.yml` — full workflow definition
- Live npm Trusted Publisher binding for `mindplan-mcp` → this workflow file + environment `npm-publish`
- the `repin` job in `publish.yml` — the self-dependency repin (below)

### Self-dependency repin

The repo pins its own package as an exact devDependency (`"mindplan-mcp": "X.Y.Z"`). Right after a release, the `repin` job opens the PR that repins it, so the pin never waits on a schedule (a Dependabot config did this daily before and is removed). The job runs only after `publish` succeeded, so the version is on npm and tagged. It has no environment, and its permissions are `contents: write` (push the branch), `pull-requests: write` (open the PR), and `actions: write` (dispatch CI). It is a separate job so that a repin failure never marks the release failed, and re-running failed jobs retries only the repin. Steps:

- check out the pushed commit and set up Node 22 with the npm cache
- skip with a log line when the branch `repin/mindplan-mcp-<version>` already exists on origin (a re-run) or the pin is already that version
- `npm install --save-dev --save-exact --ignore-scripts --prefer-online mindplan-mcp@<version>`, retried a few times because npm's listing can lag behind its registry check; the command changes only `package.json` and `package-lock.json`
- commit those two files as `github-actions[bot]`, push the branch, and `gh pr create` against `main`. The PR body says it bumps no version, so merging it publishes nothing (the version gate skips it)
- `gh workflow run ci.yml --ref <branch>`: the PR's own `pull_request` run waits for a maintainer's approval (a PR opened with `GITHUB_TOKEN`), so the job dispatches CI on the branch. The dispatched run is listed under Actions → CI for the branch, not as checks on the PR, and the PR body says so

### Repin auto-merge

The dispatched CI run merges the repin PR itself once it is green. `ci.yml` (claimed by `f-github-actions`) has a `merge-repin` job that `needs: test`, so it runs only when every Node leg passed, and only on a `workflow_dispatch` run of a `repin/mindplan-mcp-*` branch. Its permissions are `contents: write` and `pull-requests: write`. It:

- finds the open PR whose head is that branch and base is `main`; with none (already merged or closed) it logs and exits 0
- refuses (fails) when the PR changes any file other than `package.json` and `package-lock.json`
- `gh pr merge --merge --match-head-commit <tested sha>`, so a commit pushed after the tested one is never merged untested. The branch stays on origin, so a re-run of the `repin` job still finds it and opens no second PR

The merge is a merge commit by `github-actions[bot]`. Merging with `GITHUB_TOKEN` starts no workflow, so the push to `main` runs neither CI nor Publish; the repin bumps no version, so Publish would skip anyway. A red run leaves the PR open for a maintainer. GitHub's own auto-merge (`gh pr merge --auto`) is not used: `main` has no required status checks, so it would merge before CI finishes

The repository must allow GitHub Actions to create pull requests (Settings → Actions → General → Workflow permissions). If the publish job fails after publishing (as the 0.2.0 run did), the repin never runs; open it by hand (CONTRIBUTING)

### Jobs

1. **`version`** (no environment, `contents: read`): checkout, read `package.json` `version`, `npm view mindplan-mcp@<version> version`. Output `publish=true` only when the registry does not list it (E404 on an unclaimed package counts as not listed).
2. **`publish`** (`needs: version`, runs only when `publish == 'true'`, `environment: npm-publish`, `permissions: contents: write, id-token: write`):
   - checkout the pushed commit; setup Node 22 with `registry-url: https://registry.npmjs.org`; upgrade npm to 11.5.1+ (Trusted Publishing); `npm ci`
   - `npm run publish:release -- --ci` (preflight → `npm test` → tarball allowlist → publish → registry check)
   - tag the commit `v<version>` and push the tag; an existing tag on the same commit is not an error
3. **`repin`** (`needs: [version, publish]`, runs only when `publish` succeeded, no environment, `permissions: contents: write, pull-requests: write, actions: write`): opens the self-dependency repin PR (below)

Workflow-level `concurrency: { group: publish, cancel-in-progress: false }` queues pushes instead of running two publishes at once.

### Maintainer docs

`CONTRIBUTING.md` Publishing:

- First publish: `i-npm-publish` script + interactive login, then bind Trusted Publishing
- Later: bump the version in the PR (`npm version <level> --no-git-tag-version`) → merge → Actions publishes and tags

### Out of scope

- Automatic version bumps or changelog generation from commits (the repin job changes only the self devDependency; it never bumps the package version)
- GitHub Release notes
- Publishing from forks or branches other than `main`

## Failure / recovery

- **Publish failed after the merge** (OIDC, registry outage): fix the cause, then re-run the workflow or `workflow_dispatch` on `main`; the version is still unpublished so it publishes then
- **OIDC / Trusted Publisher misconfigured:** fix the npm binding; do not add `NPM_TOKEN` without a product decision
- **Broken published version:** bump patch in a new PR and merge; never unpublish or move a tag
