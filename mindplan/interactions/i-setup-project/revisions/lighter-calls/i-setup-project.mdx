# Set up the project

## Purpose

Agent sets up MindPlan in a repo that has no graph yet, from inside the session, with no CLI step. The tool creates only what MCP must own (the graph tree, the default config, the empty brief, the stamp, and the merge-gate workflow when the user asked for it) and hands the agent a guide for the rest: wiring the agent instruction files, the ignores, and filling the brief with the user. It never edits a file the user owns, because only the user and their agent can judge an existing `CLAUDE.md` or `AGENTS.md`.

## Actor & Trigger

- **Actor:** agent (asked by the user, or sent by `get_project`'s `version` field and every `Blocked: Version` while no graph exists)
- **Trigger:** MCP `setup_project({ ci? })`

## PRD / Execution Logic

Intended files: `src/interactions/i-setup-project/` (`handlers.ts`, `tools.ts`, `workflow.ts`)

- `setupProject({ ci? })` (handler, MCP tool `setup_project`, kind `write`, not version-gated):
  - `server-behind` → Blocked naming the package to upgrade to; `upgrade` (a graph exists but is behind) → Blocked: call `upgrade_project` first
  - Otherwise: `ensureDirectories()` (`f-territory-store`), the default `mindplan/config.json` when missing (`migrateImplementationPackages`, `f-graph-migrations`), `mindplan/project.md` from `templates/agent/project.md` when missing (never overwritten), and `stampGraph()` when the graph was just created. On a current graph it writes nothing and returns the guide again (re-wiring after a clone)
  - `ci: "github"` → `installMergeGateWorkflow` (`workflow.ts`, moved from init unchanged): copies `templates/ci/github/mindplan-merge-gate.yml` into the repository top's `.github/workflows/` folder (`MERGE_GATE_WORKFLOW`) (`repoTop`, `f-source-index`; outside git under the project root), replacing `{{MINDPLAN_DIR}}` and `{{MINDPLAN_VERSION}}` (the package's `major.minor`). An existing workflow is kept and reported `installed: false`
  - Returns `{ created, changed_files, ci?, pointer, guide }`: `changed_files` from `snapshotTree` / `changedSince` plus the workflow path when written; `pointer` is `templates/agent/agents-stub.md` (the text the agent writes to `MINDPLAN.md`); `guide` is `templates/agent/setup-guide.md`
- The guide (owned by `f-framework-docs`) tells the agent to: write `MINDPLAN.md` from `pointer`; add `@MINDPLAN.md` to `CLAUDE.md` (created when missing) and a one-line "read and follow MINDPLAN.md" to `AGENTS.md` when the repo has one; add `mindplan/**` to `.cursorignore` for Cursor and `.mindplan-cache/` to `.gitignore`; read the existing agent instruction files and propose which rules move into the brief (`patch_project_rules`) or onto nodes later, showing the user the diff and removing moved rules from their source only on approval; interview the user for the description (`patch_project_description`); offer the CI workflow; finish with `run_check`
- `tools.ts` defines `setup_project` with `gate: false`

Depends on: `f-graph-migrations`, `f-territory-store`, `f-source-index`, `f-tool-kit`.

## Tool descriptions

Each tool's description says when to call it, what it does, and its key parameters, and ends with `Details: get_spec({ topic: "<tool>" })`; the full contract is the tool's SPEC §8 entry. The setup guide it returns starts by telling the agent to call `get_project`, since writes wait until the seeded rules reached the session.

- **Client hook.** `install_hook: true` installs the Claude Code PreToolUse hook (`installHook`, `f-agent-hook`) into `.claude/settings.json` and lists it in `changed_files` when written; this is the one file setup writes outside `mindplan/` only when asked. The reply carries `hook` (`hookReply`): `{ installed: true, path }`, `{ installed: false, offer }` in a Claude Code project without it, or nothing

## Acceptance Criteria

- A `mindplan/` with empty type folders and no stamp (left by a 0.12 server) reads as `setup`, and `setup_project` finishes it
- In an empty directory `setup_project` creates `mindplan/` with config, brief, and a current stamp, lists those paths in `changed_files`, and returns `pointer` and `guide`; after it, gated tools work
- A second call writes nothing and returns the guide
- On a graph behind the server it is Blocked naming `upgrade_project`; on a stamp ahead of the server it is Blocked naming the package
- `ci: "github"` writes the workflow with the project path and the package's minor version; a second call keeps an edited workflow
- It never writes `CLAUDE.md`, `AGENTS.md`, `MINDPLAN.md`, `.gitignore`, or `.cursorignore`
- Verified via `npm test`
