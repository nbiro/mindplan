# Check integrity

## Purpose

Default check Blocks a shipped pipeline node whose next file is missing or is not a state-only twin (`state: mirror`), and an illegal import with the exact fix. It prints non-blocking warnings when a node's text no longer matches the repo. The same check is reachable by agents as `run_check`, because a check only the CLI exposes is never run. Also builds a read-only drift report of uncommitted source files and their owners, classified so the actionable files are not buried under expected edits. A later session that only grepped `src/` would miss those owners. The check also warns about every decision-worthy open revision that has no decision yet, from draft on, so the `Blocked: Decision` at `in-review` is never the first the agent hears of it. A change's check covers its neighbors too, the shipped nodes it edits in place, so a feature that touches a shipped helper without revising it is still checked as one piece.

## Actor & Trigger

- **Actor:** human or CI via `mindplan-mcp check`; agents via `run_check`; MCP tools via `f-mcp-runtime` `withDrift`
- **Trigger:** CLI check; `run_check`; `buildDriftReport` from the Assembler envelope used by `if-mcp-tools`

## PRD / Execution Logic

Intended files: `src/interactions/i-check-integrity/`

- Keep mirror twin and ownership checks
- Import rule: `findAllImportViolations` (`f-compiler-rules`); each failure ends with `Fix: link_nodes({...})` or `not allowed: ...`; a Foundation importing an Interface it mounts is legal
- `runIntegrityCheck` returns `{ ok, failures, warnings, removedLegacyFiles }`; `renderCheckOutput` formats it (`mindplan-mcp check: ok`, or one `Blocked:` line per failure, then `Warning:` lines) for both the CLI and `run_check`
- Warnings never change `ok` or the exit code: a node in review gets every stale-text signal (body names a missing path, a claimed file changed after the body was updated, unticked checkboxes); a shipped node with no open update gets only the path signals (a missing path, and a live `added_claims` entry its body does not name); nodes still being built are skipped
- `runCheckHandler({ base? })` — the `run_check` handler: `{ ok, output, failures, warnings }`
- `buildDriftReport({ nodeIds? })` — uncommitted working tree (`git status --porcelain`), including tracked files deleted from disk. Each path is classified: `unowned`; `owner_idle` (shipped owner with no open update, or a pre-ship owner not in-progress); `claimed_missing` (a claimed path gone from disk); or expected (the owner has an open update claiming the file) — expected is only a count. With `nodeIds` it lists those owners' files and counts the rest (`other_count`); lists are capped. Null when there is nothing to act on or git is unread
- Default `check` still ignores the dirty tree; shipped neighbor edits still pass
- `if-mcp-tools` imports this package because it exposes it (`run_check`); the Assembler re-exports the drift envelope
- **Coverage.** An in-universe file (configured `sources` minus `exclude`) that no current or next claim of a non-retired node covers is `Blocked: Coverage: …` with the probable owner (by path) and the exact `set_implementation_files` call, preceded by `open_next` when that owner is shipped with no open evolution and either does not dominate the file's folder or the file is a migration or schema file. One `createCoverageFixContext(root)` per run is passed to every `coverageFix`, so the schema globs are read once and each owner's view of the other claims is expanded once, not once per unclaimed file. A retired node's claim no longer counts as coverage; such a file is reported once, by the leftovers rule, not again as Coverage. The universe is listed once per run and shared by coverage, imports, and route families
- **Next-slot imports.** The import rule runs over every claimant of a file (live, next-slot, released). Violations the check did not scan before (advisory) print as `Warning: imports (next slot): …` for one release, then Block
- **Route families.** Split ownership of one route family is a warning
- **Changes.** `runCheckHandler({ base?, change? })` adds `change: { id, members, failures, warnings }`: each member's active-slot import and ownership violations (Blocked lines that make `ok` false) and its stale-text warnings; a member violation the global import rule already reported is not repeated. Members are the change's open revisions (`changeMembers`) and its neighbors (`changeNeighbors`), each listed with `kind: "revision" | "neighbor"`; a neighbor is checked on its live files. Decision warnings apply to revisions only. A change with neither revisions nor neighbors is Blocked (`has no members`)
- **Decisions.** For every open revision (a shipped node with an open next; a pre-ship, non-retired pipeline node at any pre-ship state), `decisionWarnings` (`f-compiler-rules`) adds `Warning: decision: …` lines naming the triggers. One `DecisionContext` (config plus the lazy git probe) serves the whole run. Decision warnings never change `ok`; with `change`, the members' decision warnings are part of the change's warnings
- The dirty-src base is `defaultBaseRef` (`f-source-index`), the same merge base the decision gate uses
- **Version.** When `projectVersionStatus()` (`f-territory-store`) is not `current`, its warning prints as `Warning: version: …`. It never changes `ok`, so CI keeps passing while a project catches up
- **Linked tests.** `checkPresence` also reports `testPresenceFailures` (`f-compiler-rules`): `Blocked: presence: "<id>" tests entry missing on disk: "<entry>".` for a node in review or shipped. Each in-review revision with no linked tests adds its `untestedWarning` as `Warning: tests: …`; it never changes `ok`. The change check reports both for its members

Depends on: `f-territory-store`, `f-compiler-rules`, `f-mcp-runtime`, `f-source-index`.

- **Merge gate.** `CheckOptions.merge` (`true` or `"strict"`; off by default) adds the rule that the default branch holds only done (`stable` / `unstable`) or still-building (`in-progress`, and the plan states `draft` / `ready`) work. `checkMerge` walks the pipeline nodes and Bugs: a Foundation, Interaction, or Interface whose active slot (the open next while one exists, else live; a mirror twin is not an open next) is `in-review`, and a Bug in `in-review`, are each `Blocked: Merge: …` naming the id, type, state (with `(next)` for a next slot), the change id, and the fix: `update_node_status({ scope: "change", change, new_status: "ship" })` for a node with a change, `update_node_status({ node_id, new_status: "ship" })` without one (a Bug: `"resolved"`), or move it back (`"in-progress"`; a Bug: `"fixing"`) if the work is unfinished. Lines are ordered by change id, then node id, so a change's lines sit together, and the result carries `merge: { level, base?, changes: [{ change, nodes: [{ id, type, state, slot, files? }] }] }` with one group per change (`change: null` for the nodes with none). Cancelled and deprecated nodes pass
- **Strict merge gate.** With `merge: "strict"`, an `in-progress` active slot whose claims cover a path that changed against the base is also `Blocked: Merge (strict): …` listing up to five changed paths: the work looks finished but was never moved to review. Changed paths are `git diff --name-only --relative <base>...HEAD` plus the working tree under the project root (`collectDirtySrcPaths`, `git status -- .` with the root's repository prefix stripped, so a project below the repository top gets project-relative paths), deleted paths included, matched with `claimCoversPath` against the active slot's claims. One memoized probe per run serves dirty-src and strict, so `--merge=strict --base` runs git once and reports a failed probe once. The base is `options.base`, else `defaultBaseRef`; strict outside git or with no resolvable base is `Blocked: Merge (strict): …` with the fix (`--base <ref>`). Strict stays opt-in because it blocks the incremental PRs of a large feature
- `runCheckHandler({ base?, change?, merge? })` passes `merge` through and returns `merge` when the gate ran

- The default check adds `descriptionWarnings` (`f-compiler-rules`) for every node to its warnings; they never change `ok` or the exit code

## Acceptance Criteria

- `run_check` output equals the CLI check output
- An illegal import fails the check with its fix; a registry that mounts two Interfaces passes and the same import without the edge is still blocked
- A stale body path warns without failing the check
- Drift lists owner_idle, claimed_missing, and unowned files, counts expected edits, and scopes to the focus node
- Clean tree or git failure yields no report (or empty)
- Default check pass/fail behavior otherwise unchanged
- Verified via `npm test`
- A new unclaimed source file fails with `Blocked: Coverage`, its probable owner, and the claim call
- An illegal import in a file claimed only on a next slot warns with `imports (next slot)` and does not fail
- `run_check` with `change` reports the members and fails when a member has an import violation
- `run_check` on this repository's graph reports no new failures
- A Foundation `open_next` revision with no decision prints a `decision:` warning and `ok` stays true; recording a decision under its change removes the warning
- A revision that is not decision-worthy never prints a `decision:` warning
- A missing or older `mindplan/version.json` prints a `version:` warning and `ok` stays true; a current stamp prints none
- `run_check` with `change` lists revisions and neighbors with their `kind`, fails on a neighbor's import violation, and gives decision warnings for revisions only
- A change with only neighbors is checked; a change with no members is Blocked
- A shipped node's `added_claims` entry that its body does not name prints a `stale:` warning and `ok` stays true
- The Coverage fix for a file beside a shipped owner's own files, in a folder no other node claims into, has no `open_next`; for a migration or schema file there it does
- A shipped node linking a missing test file fails the check; a draft node linking one does not
- An in-review revision with no tests prints a `tests:` warning and `ok` stays true

- `run_check` stays ok with bad descriptions and lists one `description:` warning per kind
- A graph with one `in-review` next twin fails the merge gate with a `Blocked: Merge` line naming the node, its change, and the ship call, and passes the default check
- `draft`, `ready`, `in-progress`, `stable`, `unstable`, and mirror twins pass the merge gate; a Bug in `in-review` fails and a `resolved` one passes
- Several in-review nodes of one change produce one group in `merge.changes`, and their lines are adjacent
- The strict gate fails an `in-progress` node only when a claimed file differs from the base

## Decisions

### d-merge-gate-opt-level-existing

- Decision: The merge gate is an opt-in level of the existing check (`check --merge`, `run_check({ merge })`), failing on in-review active slots and in-review Bugs, with a strict level for in-progress nodes whose claimed files changed against the base.
- Alternatives:
  - Fail in-review nodes in the default check (every branch with a node in review would fail CI, though in-review on a branch is the normal pre-merge state)
  - A separate `mindplan-mcp gate` command (a second output format and exit path that could drift from run_check)
  - Make strict the only level (blocks every incremental PR of a large in-progress feature)
- Why: In review is legal on a branch and illegal on the default branch, so only a check that knows it is guarding a merge can fail on it; reusing the check keeps one output format for the CLI, run_check, and CI.
- Consequences: CI must opt in (the init workflow, or a required status check the repository configures); strict needs git history and a resolvable base.
