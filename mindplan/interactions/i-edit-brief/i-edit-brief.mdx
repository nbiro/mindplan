# Edit the brief and config

## Purpose

Writes the project brief's description and rules and `mindplan/config.json` through MCP, each piece separately, so a rules edit never rewrites the description and a config edit keeps every setting it does not pass.

## Actor & Trigger

Agent calls `patch_project_description` when the product summary changes, `patch_project_rules` when a rule that applies everywhere changes, and `patch_config` when source roots, exclusions, decision-gate, hotspot, fan-out, or search settings change.

## PRD / Execution Logic

Intended files: `src/interactions/i-edit-brief/` (`handlers.ts`, `tools.ts`).

- `patch_project_description` replaces only the brief description; `patch_project_rules` changes only the brief rules (global); each leaves the other section unchanged and lists `mindplan/project.md` in `changed_files`. Neither echoes the brief: `patch_project_description` returns `{ path, changed_files }`, `patch_project_rules` a confirmation `{ path, rules_version, count, added?, removed?, skipped?, changed_files }` (`added` / `removed` / `skipped` with `add` / `remove`); `get_project` and `get_rules` return the text
- `patch_project_rules` takes `rules` (replaces the whole section; an empty string clears it), or `add` (rules to append, one bullet each; one already present is skipped) and/or `remove` (rules to drop, by full text or a fragment matching exactly one rule; applied before `add`); at least one is required, and `rules` is not combined with `add` / `remove`; an empty entry, or a `remove` entry matching no rule or several, is Blocked
- `patch_config` takes `sources`, `exclude`, `decisions: { blast_radius?, schema_files? }`, `hotspots: { half_life_days?, outlier_ratio?, min_rate? }`, `fan_out: { warn_at? }`, `fan_in: { exempt_roles? }` (Foundation roles), and `search: { enabled?, model? }`; a field it does not pass keeps its stored value; at least one is required; unknown keys inside an object are rejected
- No orientation gate: the brief and config belong to no node. Like every write, each is `Blocked: Rules` until the project rules reached the session (`f-plan-writes`); `patch_project_rules` then records the rules it wrote as served (`projectRulesPush`), so its author is not blocked by its own change while every other session is until it re-reads them
- Each tool's description says when to call it, what it does, and its key parameters, and ends with `Details: get_spec({ topic: "<tool>" })`

Depends on: `f-plan-writes`, `f-territory-store`, `f-compiler-rules`, `f-tool-kit`.

- **Config keys (0.23.0).** `patch_config` also takes `replies` (`budget_bytes`, `legacy`), `tests` (`command`), and `rule_checks` (`commands`); a key not passed keeps its stored value, and keys the tool does not take are written back unchanged
- **Rule checks on write.** `patch_project_rules` Blocks, writing nothing, when a `check:` line of the resulting rules is invalid (`f-graph-search` rule checks), naming the rule and the problem

## Acceptance Criteria

- Description and rules are separate project-brief writes
- `patch_project_rules({ add })` appends a rule and skips one already present; `remove` drops a rule by text before `add` applies, and Blocks on no match or several; `rules` with `add` or `remove`, or none of the three, is rejected
- `patch_config` with `decisions` writes them and leaves `sources` and `exclude` unchanged; with `search` or `hotspots` it writes them and a later `sources` write keeps them
- `patch_config({ fan_out: { warn_at } })` writes it and keeps every other setting; a later `sources` write keeps it
- `patch_config({ fan_in: { exempt_roles } })` writes it and keeps every other setting; a later `sources` write keeps it (`fan-in.test.mjs`)
- An unknown key inside `decisions`, `hotspots`, `fan_out`, or `search` is rejected
- A `patch_project_rules` result carries neither the description nor the rules text, only the version, the count, and the rules added, removed, and skipped; a `patch_project_description` result carries neither section
- After `patch_project_rules`, the same session's next write passes the rules gate and another session's is `Blocked: Rules`
- Verified via `npm test`
