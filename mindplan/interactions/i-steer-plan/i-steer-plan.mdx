# Steer the plan

## Purpose

Compiler-gated mutate tools: status, links, `open_next` (writes the next file), required `patch_node_territory`, `patch_node_rules`, `record_decision`, `patch_project_description`, `patch_project_rules`, `patch_config`, attachment put/remove, ordered revisions, and scoped status walks. `patch_node_rules` is the single writer of a node's rules so a territory rewrite can never silently drop them, and a rules edit never needs a contract evolution because rules are standing constraints, not behavior. Writes are cheap to read and cheap to repeat: a default result is the touched node's state and the changed files, a one-line fix does not resend a body, and a whole open set ships in one call. Claiming files and moving toward review run the same import rules as the check, so an illegal import is caught when it is written, with its fix, not after the node merged. `record_decision` is the single writer of decision records. A record is never rewritten: changing a decision means recording a new one that supersedes it, so the reasoning trail survives and an agent asking why the old design was dropped finds the answer without git archaeology. Moving a decision-worthy revision to `in-review` with no decision is Blocked with the exact `record_decision` call, so the reason is captured while the agent that made the choice still knows it. A shipped node grows without a revision only where that cannot reach anyone else's contract: `set_implementation_files` adds a file or folder in place when the node dominates the folder, and marks it so review still sees it. A change that edits shipped nodes in place labels them its neighbors, so the change-scoped tools see every node the change touches; the labels go away with the change, so a stale label never pulls a node into the next one.

## Actor & Trigger

- **Actor:** coding agent or human via MCP
- **Trigger:** MCP mutate tools

## PRD / Execution Logic

Intended files: `src/interactions/i-steer-plan/`

- `open_next` writes the next file from live; ship and `discard_next` delete it with `next-attachments/` (there is no standing twin), listing every deleted path in `changed_files`
- `patch_node_territory` is the required prose path; it preserves the node's `## Rules` section and Blocks a body that contains one, naming `patch_node_rules`. Besides `body` it takes `section` + `text` (rewrite one `## heading`'s content) and `replace { find, with, all? }` (one exact edit); `body` cannot be combined with them; `section` without `text` is Blocked
- `patch_node_rules({ node_id, rules })` replaces the `## Rules` section of that node via `writeNodeRules`; an empty string clears it. Works on any node type in any state except inactive ones (retired, or a closed Bug), including shipped nodes with no open evolution, and never changes state, edges, or checkboxes. With an open evolution it writes the same text to live and next
  - Blocked: unknown node; `cancelled` / `deprecated` node; a Bug that is `resolved` or `wontfix`; rules text containing a level-1 or level-2 heading line
  - Output: `{ node_id, rules, slots: ["current"] | ["current","next"], rules_impact, changed_files }` where `rules_impact` is `{ has_rules, inherited_by }` from `rulesImpact` (`f-graph-search`), so the author sees whose work the edit reaches. `changed_files` lists the live `.mdx` plus the open `.next.mdx`; `mindplan/map.md` is not rewritten because rules are not graph structure
- `patch_project_description` replaces only the brief description; `patch_project_rules` replaces only the brief rules (global, apply everywhere); each leaves the other section unchanged
- `patch_config`, `put_attachment`, `remove_attachment`
- First ship writes no next file; promote, retire, and unship delete any next file and `next-attachments/`
- **Ship drops the ledger.** First ship removes the live file's Atomic Ops (`stripLiveAtomicOps`, `f-territory-store`), and promote does the same through `promoteNextSlot`; the shipped node shows its current state and git keeps the ledger. `open_next` returns a next file with a fresh list of unticked default ops for the agent to rewrite, and `force_unship` gives the live file one (`freshLiveAtomicOps`), since the unshipped node must pass the shape and completion checks again; a failure anywhere in the unship (the target's gates or a later frontmatter write) puts the live file back as it was, so a still-shipped node never keeps ops it did not ship with
- **Small results.** Each single-node write returns its own fields plus `state` and `next_state` and `changed_files`; the record and 1-hop neighborhood (`anchor`) only with `verbose: true`. A batch returns `lines`, one `id: from -> to` per node
- **One file per live write.** A live write lists only the live file it wrote; the stability and Journey recompute after links, unlinks, and status moves lists each node's live path (`syncNodes`)
- **Claim-time import scan.** `set_implementation_files` writes the claim, then scans the claimed files with `findImportViolationsForClaim` and returns `import_violations: [{ file, imports, fix | not_allowed }]`; `fix` is the exact `link_nodes` call (`depends_on`, `exposes`, or `mounts`)
- **Status gate.** A move to `in-review` or `ship` runs `assertCheckCleanForNode` (import and ownership violations on the node's active-slot files) after the transition's own rules and before any write; Blocked with every violation and its fix. `staleTextWarnings` for the node return as `warnings` and never block
- **Links.** `link_nodes` / `unlink_nodes` handle `mounts` (Foundation → Interface) like `exposes`: written to the next slot while a node evolves, promoted on ship
- **Scoped status.** `update_node_status` takes `scope` (`all_open_updates` | `node_and_dependents` with `node_id`) and `new_status` as the target. It selects the open updates (`all_open_updates`: shipped nodes with an open next and pre-ship nodes that are in-progress or in-review, never draft or ready plans; `node_and_dependents`: the named node plus the nodes that depend on or expose it, including edges proposed on a next slot, at any pre-ship state), orders them Foundations, Interactions, Interfaces (dependency order within a tier), walks each from its active state through `draft → ready → in-progress → in-review → ship`, and first validates the whole walk in memory, writing nothing when any step would be Blocked. `dry_run` returns `{ dry_run, plan, blocked, warnings? }` for any form (single, revisions, scope) without writing
- **Readiness reset.** A contract write to a slot whose state is `ready` moves that slot back to `draft`: `patch_node_territory` (title, description, role, body, section, replace, toggle_checkboxes), `set_implementation_files` (when the list changes), and `link_nodes` / `unlink_nodes` on the source node. The territory store's writers make the reset (`demoteReadySlot`) and report it; the handlers only turn that into the result, which carries the new `state` / `next_state` and `readiness_reset: { slot, from: "ready", to: "draft", note }`. Writes that never reset: `patch_node_rules`, `record_decision`, `change` / `change_ref` writes, attachments, and any write to a slot in `draft`, `in-progress`, or `in-review` (ticking finished work is how a revision completes)
- **Review is not skipped silently.** A scoped walk to `ship` that would move a node whose active state is before `in-review` is Blocked unless `skip_review: true`. With it each node still walks `in-progress → in-review → ship`, runs the in-review gate at that step, and the result lists `skipped_review`. `dry_run` lists every transition, one `id: from -> to` line per step
- **Change groups.** `create_node` and `open_next` take `change` / `change_ref`; `patch_node_territory` sets or clears them on the active slot. `update_node_status` with `scope: "change"` and `change` walks every open revision in that change, including draft and ready ones
- **Checkbox results.** `toggle_checkboxes` items take `all`, `note`, and `not_applicable`; the result returns `toggled`, the lines as written
- **`record_decision({ node_id, decision, alternatives, why, consequences?, supersedes?, change?, id? })`** appends one entry with `appendDecision` to the node's active slot: the open next file while a shipped node evolves, else the live file. `decision`, `why`, and `consequences` are trimmed and collapsed to one line; `alternatives` needs at least one non-empty item, each collapsed to one line. `id` defaults to `generateDecisionId`; a given id must match `DECISION_ID_PATTERN` and be unused anywhere in the graph. `change` defaults to the node's active change (`activeChange`) and is omitted when there is none; `date` is today in UTC. `supersedes` must name a decision that is active and is held by the node itself or by a node it inherits decisions from (its Journeys, its transitive Foundations); the old entry is left exactly as written and its status becomes `superseded`
  - Blocked: unknown node; inactive node; a Bug (record the decision on the node the fix shapes); empty `decision` or `why`; no alternative; a bad or taken id (an id a `supersedes` still names is taken); an invalid change id; `supersedes` that is unknown, already superseded, or held by a node outside that reach
  - Output: `{ node_id, slot, decision: DecisionEntry, supersedes?: { id, node_id }, changed_files, state, next_state }` (`anchor` with `verbose`). Never resets readiness and does not rewrite `mindplan/map.md`; listed in `MUTATE_TOOLS`
- **Decision gate.** A move to `in-review` (single, batch, scoped walk, and the dry run of each) runs `assertDecisionForReview` after the transition's own rules and the check gate, before any write. Moves to other states, and Bugs, are never decision-gated. The in-memory walk promotes a node field for field as `promoteNextSlot` does (scalars, edges, claims, role, decisions; the change id dropped) and rebuilds its edges with the same helper as the real walk, so every later gate sees what the real walk will see. One `DecisionContext` serves a call's validation and every step
- `patch_config` takes `decisions: { blast_radius?, schema_files? }` and `search: { enabled?, model? }`; a field it does not pass keeps its stored value, and `sources` / `exclude` are unchanged unless passed (a `sources`-only write keeps the stored `decisions` and `search`)
- **Orientation gate.** `gateWrite(graph, ids, tool)` calls `assertOriented` (`f-orientation-ledger`) when the gate is on: `set_implementation_files`, `set_test_files`, `patch_node_territory` (checkbox toggles included), `patch_node_rules`, `record_decision`, `open_next`, `put_attachment`, `remove_attachment`, and `force_unship` gate on `node_id`; `link_nodes` (after `validateLink` and the cycle check) / `unlink_nodes` on `source_id`; `update_node_status` on every node a non-dry single, batch, or scoped walk transitions (a dry run is not gated). An unknown id still reports that it does not exist. Every unoriented node of one call is named in one `Blocked: Orientation` (a scoped walk validates every node it would transition before the first write); a `scope: "change"` walk passes its change id, so the message names `orient_for_work({ change })`. `create_node` is never gated: its result records the new node and carries `rules` (the rules that reach it) and `shape` (`shapeReport`, `f-compiler-rules`: the required sections of its type, each `present`, `missing`, or `stub`, and the gates that read them), so the agent writes the sections before the first transition instead of finding them one `Blocked:` at a time. A link or unlink that changes the rules reaching its source returns them as `rules` and records the source; `patch_node_rules` keeps its author oriented, while the nodes that inherit the new rules must orient again
- **Planned edges.** `link_nodes({ ..., change })` on a shipped source with no open revision of that change writes a planned edge instead of a live one: `validatePlannedLink` (`f-compiler-rules`) first, then `writePlannedEdges` appends `{ change, type, target }` to the live `planned:` list; the result carries `planned: { source, type, target, change }` and the live file in `changed_files`. Graph edges, Journey states, stability, the map, and the search cache do not change (none is refreshed), and readiness is never reset (a shipped node has no ready slot). A duplicate planned entry is Blocked. When the source has an open revision of that change, or is not shipped, `change` changes nothing and the edge is written as it is without it. `unlink_nodes({ source_id, target_id, change })` removes that change's planned entries from source to target (the target need not exist any more) and Blocked when there are none; without `change` it is unchanged. `open_next` with a change (given, or inherited from a neighbor label) is Blocked while any of that change's planned entries on the node is no longer legal (`plannedEdgeProblems`, with the `unlink_nodes` fix); otherwise it applies that change's planned entries to the next slot's edges (`addEdgeToFrontmatter` on next, skipping one already there) and returns `applied_planned`; the entries stay on live until the revision ships. A change that closes (`withNeighborCleanup`) also drops its remaining planned entries from every node and lists them as `cleared_planned`
- **Attributed files.** `set_implementation_files({ node_id, files?, attributed? })`: `attributed` replaces the revision slot's list of files it adds in another node's folder (`files` may then be omitted, keeping the claims). Each entry is an exact repo path (no glob, no trailing `/`) that another active node's claim covers and this node's own claims do not; anything else is Blocked with the fix (claim it with `files`). A shipped node with no open next is Blocked with `open_next`: attribution belongs to a revision. The write resets a `ready` slot like a claim change. A first ship clears the live list (`clearAttributed`)
- **Aliases.** `create_node` takes `aliases` (validated with `normalizeAliases` before any write, written after the scaffold). `patch_node_territory` takes `aliases` on any active node, shipped ones included, without `open_next` (the aliases are validated and a retired or closed node is Blocked before any write; an empty list in another field does not count as a territory field): the territory fields (if any) are written first, then `writeAliasesFrontmatter`; the result carries `aliases` and both writes' `changed_files`; an aliases-only patch returns `{ node_id, patched_fields: ["aliases"], aliases, changed_files }` and refreshes the map and the search cache. Neither resets readiness
- `refreshPersistedMap()` (after every write that rewrites the map) loads the graph once, rewrites `mindplan/map.md`, and calls `refreshSearchIndex` (`f-graph-search`) with `territoryBodyReader()`: the search cache syncs now and the embeddings of what changed are computed in the background. The cache lives outside `mindplan/` and is never in `changed_files`
- **In-place claims.** `set_implementation_files` on a shipped node with no open next (no `slot`, or `slot: "current"`) writes the live list in place after `assertAdditiveInPlace`, before any write: every old entry is kept verbatim or under a new non-glob `dir/` entry (`claimListKeeps`), and each new entry is an exact file whose folder the node dominates (`isDominatedFolder`, with the entry as a probe) or `F/` for a dominated folder F. A dropped entry, a glob, an existing directory written without a trailing `/`, a folder the node does not dominate, or an entry that reaches a migration or schema file (`schemaClaimEntries` over config `decisions.schema_files`) is Blocked with `open_next`: a schema claim is decision-worthy, and only a revision reaches the decision gate. With an open next, `slot: "current"` stays Blocked. The new entries join the live `added_claims` marker (`writeImplementsFrontmatter(node, files, "current", added)`). The result carries `added_in_place` (possibly empty) and, when an entry was added, a `hint` to name each one in the body with `patch_node_territory`
- **Folder suggestions.** A `set_implementation_files` result carries `folder_claims` (`folderClaimSuggestions`) when one `folder/` entry would replace several per-file entries; it is never written
- **Neighbor labels.** On a shipped, non-retired pipeline node with no open next, `change` on `patch_node_territory` (live slot), `record_decision`, and `set_implementation_files` labels the node a neighbor of that change: `writeNeighborLabel` sets the live `change` scalar, and the result carries `neighbor_of`. One label per node: a different id replaces the old one and the result reports `replaced_change`; `""` clears it. `change_ref` on such a node is Blocked (it belongs to a revision), and a retired node takes no `change` on `set_implementation_files`. On any other node `change` is the written slot's change id, as before; on a next slot the store also drops a live label that no longer matches it (`replaced_change`, the live file listed). `record_decision` without `change` on a neighbor records the decision under its label. The neighbor test everywhere is `isNeighborNode`
- **Clearing labels.** A change with no open revisions has no neighbors. Every write that can end a membership runs inside `withNeighborCleanup`: `update_node_status` (not a dry run), `discard_next`, and `patch_node_territory` / `set_implementation_files` when they pass `change`. It takes `changesWithRevisions` before the write and after it, and `clearOrphanedNeighbors` clears the labels of every change that had a revision before and has none after; the result lists `cleared_neighbors` and the files. So a ship or promotion, a cancel or deprecation, a discard, or a change id moved or cleared clears its change once per call, a batch or scoped walk included, and a neighbor-only change (no revision before either) keeps its labels. The cleanup also runs when a batch throws part-way, since earlier nodes stay transitioned. A `scope: "change"` walk to `ship` also clears the change's labels after the walk, which closes a neighbor-only change
- **Labels on lifecycle moves.** `scope: "change"` walks revisions only and is Blocked only when the change has neither revisions nor neighbors. `open_next` without `change` inherits a live label as the revision's change; with a different `change` it clears the live label and returns `replaced_change`, so `discard_next` cannot restore a stale one. Deprecating a shipped node clears its label (`cleared_change`); `force_unship` clears the label (`cleared_change`) and the `added_claims` marker (`clearAddedClaims`)
- **Linked tests.** `setTestFiles({ node_id, files, change?, verbose? })` — the `set_test_files` handler: replaces the node's `tests` list through `writeTestsFrontmatter` (`f-territory-store`) on live and an open next alike; it never needs `open_next` and never resets readiness. `change` on a shipped node with no open next labels it a neighbor, as the other in-place writes do. Returns `{ node_id, tests, changed_files, state, next_state }`; Blocked for a Journey, a Bug, a retired node, or an invalid path

Depends on: `f-compiler-rules`, `f-graph-search`, `f-view-projection`, `f-territory-store`, `f-source-index`.

**Open–closed warning on `open_next`.** Reopening a shipped node that many nodes depend on is where a feature should most often have been additive, so `open_next` warns at once rather than at in-review: when the node is a hotspot counting the revision it opens (`openClosedWarning`: its recent ship rate an outlier against the graph's median, not `keep_whole`), the result carries `warnings: [openClosedWarning(...)]` and `decision_prompt`, the `record_decision` call whose `alternatives` names the additive option (a new node that depends_on it). It never Blocks; the in-review decision gate still applies.

**Revision count and splits at ship.** First ship writes `revisions`; promotion adds one. A split is declared on the revision: `patch_node_territory({ node_id, split_into: [parts] })` on a Foundation with an open revision (each part another active Foundation; Blocked otherwise) writes the next file's `split_into` as the live list plus the parts, without a readiness reset. When the revision ships, the marked parts it `depends_on` by then are recorded: `split_at` becomes the new count, the parts join `split_into`, and `churn` resets to 0. A revision that only starts using a new building block marks nothing and records no split. A reship after `force_unship` adds one to `revisions` and carries `churn` decayed from `churn_at` (written by the unship). Marking a part the revision does not `depends_on` yet returns a `split_into:` warning, since only parts it depends on at ship are recorded.

## Acceptance Criteria

- Description and rules are separate project-brief writes
- `patch_node_rules` then `patch_node_territory` leaves the rules text intact
- `patch_node_rules` on a stable node leaves it stable with no open evolution and writes only `<id>.mdx`
- With an open evolution the rules appear in both `<id>.mdx` and `<id>.next.mdx`
- Blocked on unknown id, retired node, closed Bug, or a heading line inside the rules
- `open_next` creates `<id>.next.mdx`; ship, discard, retire, and unship delete it and `next-attachments/`, and their `changed_files` list each deleted path; no write creates a `state: mirror` file
- Every write's `changed_files` covers every `mindplan/` file it touched, including the live files of nodes whose stability it recomputed
- A default write result has no `anchor`; a single write is under about 1k tokens and a batch of many nodes returns one line per node
- Claiming a file that imports from an unlinked node returns the `link_nodes` call; a registry importing Interfaces gets one `mounts` fix per Interface
- Moving a node whose file has an import violation to `in-review` or `ship` is Blocked, and the Blocked text names the fix
- `section` rewrites one section and leaves the rest; `replace` is Blocked unless the text matches exactly once (or `all`)
- `all_open_updates` never walks a draft or ready plan, even one that already claims files
- A scoped walk ships every open update in one call in dependency order, `dry_run` writes nothing, and a Blocked step writes nothing
- Verified via `npm test`
- Each contract write on a `ready` next slot (territory patch, claim, link, unlink) returns `next_state: "draft"` and `readiness_reset`; the same write on an in-progress slot changes no state
- `patch_node_rules` and change writes never reset readiness
- A scoped walk to `ship` from `ready` is Blocked without `skip_review`; with it the result lists `skipped_review` and every node passed the in-review gate
- `dry_run` of a scoped walk lists one line per transition
- `scope: "change"` walks exactly the change's open revisions
- `record_decision` writes a structured entry that `list_decisions` returns; on a node with an open evolution it lands in the next file only
- Superseding marks the old decision superseded (listable with `include_superseded`); superseding an unknown, already-superseded, or out-of-reach decision is Blocked, and so is a taken id
- A decision-worthy revision is Blocked at `in-review` with the `record_decision` call; after recording, the same move passes; the dry run of a scoped walk reports the same Blocked
- A revision that is not decision-worthy moves to `in-review` with no decision
- `record_decision` on a `ready` revision does not reset readiness
- `patch_config` with `decisions` writes them and leaves `sources` and `exclude` unchanged
- `patch_config` with `search` writes it; a later `sources` write keeps it
- In a fresh session every gated write on a node that was not oriented on is `Blocked: Orientation` with the fixing call and succeeds after `orient_for_work({ node_id })`; a rules change on a Journey sends its Interactions back to orient; `create_node` is never blocked
- After a write, the changed node is searchable on the next call and no `.mindplan-cache/` path is in `changed_files`
- A shipped node with no open next claims a new file beside its own, in a folder no other node claims into, in place: the live list grows, `added_in_place` and `hint` return, and `run_check` warns until the body names the file
- Dropping an entry, adding a glob, or claiming in a folder another node claims into is Blocked with `open_next`; replacing per-file entries with their folder's `dir/` entry is allowed
- `change` on a shipped node with no open next returns `neighbor_of`; a second id returns `replaced_change`; `change_ref` there is Blocked
- Shipping, cancelling, or discarding a change's last revision clears its neighbors' labels and lists `cleared_neighbors`; a `scope: "change"` walk to ship clears a neighbor-only change
- `open_next` with a different change clears the live label, and a later `discard_next` does not bring it back
- `force_unship` and deprecation clear the label and report `cleared_change`
- After first ship and after promotion the live file has no Atomic Ops section; `open_next` on that node returns a next file with unticked default ops, so shipping it without new ticks is Blocked by the Completion Check; `force_unship` of a shipped node leaves a live file with unticked default ops that can move to `ready`
- Claiming a new migration file, or a migrations folder, in place is Blocked with `open_next`; a plain sibling in the same dominated folder is still claimed in place
- Moving an open revision's change id off its inherited label (`patch_node_territory` or `set_implementation_files`) reports `replaced_change` and leaves live unlabeled
- `record_decision` on a labeled neighbor without `change` records the decision under the label
- A batch that ships a change's last two revisions lists each cleared neighbor once
- `set_test_files` on a shipped node writes only live, with no `open_next`; on an open revision it writes both files; a `ready` slot stays ready
- `set_test_files` with an invalid path, or on a Journey, a Bug, or a retired node, is Blocked

- `create_node` and `patch_node_territory` write `aliases`; `[]` clears them; an alias over 60 characters is rejected; the next search finds the node by its alias
- `create_node` returns `shape` listing every required section of its type as `stub` (the scaffold) or `missing`; a Journey's result has none
- A scoped walk over a change with three unoriented members is Blocked once, naming all three and `orient_for_work({ change })`
- `link_nodes` with `change` on a shipped Interface writes a planned `exposes`: the live `exposes` list and `graph.edges` are unchanged; an illegal or cyclic planned edge is Blocked; `unlink_nodes` with `change` removes it
- `open_next` with that change adds the planned edge to the next slot and returns `applied_planned`; shipping the revision makes it live and drops the planned entry; a discard leaves it planned; a planned edge whose target was cancelled Blocks `open_next` with the `unlink_nodes` fix
- Shipping the change's last revision drops another node's unopened planned entries and lists them in `cleared_planned`
- `set_implementation_files` with `attributed` on a schema node's revision writes the list; a path no other node claims, a glob, or a shipped node with no open next is Blocked
- `record_decision` with `keep_whole: true` writes it on the record, and the node stops being a hotspot until the decision is superseded
- `open_next` on a shipped node that ships far more often than the graph's median returns `warnings` with the open–closed line and `decision_prompt` (the `record_decision` call with the node, the change, and the depends_on alternative filled in); below the threshold the result has neither; the revision opens either way
- First ship writes `revisions: 1` and `churn: 1`, and each promotion adds one; shipping a root revision marked with `split_into` and depending on the part writes `split_at`, the part in `split_into`, and `churn: 0`, and `run_check` stops reporting the root as a hotspot; a revision that gains a new dependency without `split_into` records no split
- `split_into` on the node itself, on a node with no open revision, or on a non-Foundation is Blocked
- `patch_config` with `hotspots` writes them and leaves the other settings unchanged; an unknown `hotspots` key or a threshold below 1 is rejected

## Decisions

### d-bugs-hold-no-decisions

- Decision: record_decision refuses Bugs; the decision goes on the node the fix shapes.
- Alternatives:
  - Allow decisions on Bugs (nothing inherits from a Bug, so the reasoning would never reach the next agent)
- Why: Decisions are only useful where inheritance delivers them.
- Change: decision-records
- Date: 2026-10-20

### d-optional-decision-id

- Decision: record_decision takes an optional id and otherwise generates one from the decision's first words.
- Alternatives:
  - Require an id (more friction for every record)
  - Always generate (no stable, readable names like d-capacity-on-booking)
- Why: Readable ids matter for supersedes, but a missing id should not block recording the reason.
- Change: decision-records
- Date: 2026-10-20

### d-neighbor-cleanup-by-before-after

- Decision: Neighbor labels are cleared by one wrapper around every write that can end a change membership, which compares the changes with open revisions before and after the write and clears the labels of each change that lost its last revision.
- Alternatives:
  - Call the cleanup from each handler path that ends a membership (eight call sites; a new path that forgets it leaves stale labels, and a scoped walk reloads the graph at every step)
  - Validate labels when reading neighbors, ignoring those whose change has no revisions (a neighbor-only change has no revisions by design, so it would lose its neighbors)
- Why: A neighbor-only change is legitimate, so only an event (a change losing its last revision during a call) can tell an orphaned label apart; checking it once per call covers every write path and costs two graph loads instead of one per step.
- Consequences: A new write tool that can end a membership must run inside withNeighborCleanup; the store keeps the invariant that an open revision's live label names its own change, so discard_next needs no special case.
- Change: shipped-claims-and-neighbors
- Date: 2026-10-25

### d-split-declared-on-revision

- Decision: A split is declared on the root's open revision with patch_node_territory split_into and recorded when it ships (for the marked parts it depends_on); live ships never infer one. Only init infers past splits from git, best-effort.
- Alternatives:
  - Infer a split when a Foundation's revision adds depends_on to Foundations first shipped while it was open (a revision that only starts using a new building block looks the same, and the false split would silence a real hotspot)
  - Infer it from claims moving from the root to the part (this repo's convention gives each node its own folder, so moved code never shows as moved claims)
  - A separate split tool (one more tool for a field that belongs with the revision's other territory metadata)
- Why: The owner asked for a split-into record that marks the revision; only the agent knows whether a new dependency is an extracted part, and a wrong split resets the hotspot rate.
- Consequences: An agent that splits a node must mark the parts, or the root keeps its rate; the hotspot warning and the plan-project skill say so.
- Change: open-closed
- Date: 2026-10-31
