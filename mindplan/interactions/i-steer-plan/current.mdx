# Steer (ordered revision status)

## Purpose

Mutate the graph through compiler-gated tools. Keep `set_implementation_files`, Foundation `role` on `create_node`, and no package scaffolds. Claim validation uses `f-source-index`.

`update_node_status` still transitions one node when called with `node_id` and `new_status`. It also accepts `revisions`: a list of `{ node_id, new_status }`, mutually exclusive with the single-node fields. The server orders Foundations, then Interactions, then Interfaces, then Bugs, preserves caller order within a tier, applies each transition against the graph as updated by the previous one, and stops on the first `Blocked:`. Earlier nodes stay transitioned. The error names the stopped node and the nodes already applied, and begins with `Blocked:`.

## Actor & Trigger

- **Actor:** coding agent or human via MCP (`if-mcp-tools`) or console API (`if-console-api`)
- **Trigger:** MCP/HTTP mutate tools, including one status call for a revision

## PRD / Execution Logic

Intended files: `src/interactions/i-steer-plan/`

- Keep existing mutate tools + map refresh via `f-view-projection`
- Keep `set_implementation_files(node_id, files, slot?)`:
  - Pre-ship writes `current`; shipped writes only open `next` (else Blocked → open_next); retired may only shrink
  - Reject bad paths (`..`, under `mindplan/`) and immediate ownership conflicts
- `create_node` for Foundations requires `role`
- Do not scaffold `src/<type>/<id>/.gitkeep`
- `update_node_status`:
  - Single-node input and output stay as they are
  - `revisions` rejects duplicates, empty lists, and being combined with `node_id` or `new_status`
  - Journeys are rejected before any write
  - On `Blocked:`, do not roll back nodes already applied in the call

Depends on: `f-compiler-rules`, `f-graph-search`, `f-view-projection`, `f-territory-store`, `f-source-index`.

## Acceptance Criteria

- `set_implementation_files` enforces slot rules and rejects conflicts
- Foundation create without role is Blocked
- No package scaffolds on create
- Single-node `update_node_status` behavior is unchanged
- A `revisions` call applies Foundations before Interactions before Interfaces even when the caller lists them in another order
- The first `Blocked:` stops the call; earlier nodes stay transitioned; later nodes are not written
- Existing mutate behavior preserved
- Verified via `npm test`
