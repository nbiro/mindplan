# Revise a shipped node

## Purpose

Opens a revision of a shipped Foundation, Interaction, or Interface while the live node keeps serving, or discards it, and warns at the moment of reopening when the node ships far more often than the rest of the graph, since that is when an additive design is still cheap.

## Actor & Trigger

Agent calls `open_next` when a shipped node's contract changes, before editing that contract, and `discard_next` to abandon the revision.

## PRD / Execution Logic

Intended files: `src/interactions/i-revise-node/` (`handlers.ts`, `tools.ts`).

- **open_next** validates Rule 10 and writes `<id>.next.mdx` from the live file in state `draft` (optional title and description) with a fresh list of unticked default Atomic Ops and an empty `next-attachments/`; takes `change` / `change_ref`, written to the next file only (the live file carries no change id)
- **Planned edges.** With a change, open_next is Blocked while any of that change's planned entries on the node is no longer legal (with the `unlink_nodes` fix); otherwise it applies them to the next slot and returns `applied_planned` (and the `rules` they bring)
- **Hotspot warning.** When the node is a hotspot counting the revision it opens (`openClosedWarning`, `f-compiler-rules`), the result carries `warnings` and `decision_prompt`, the `record_decision` call naming a new node that depends on it as the alternative. It never Blocks
- **discard_next** deletes `<id>.next.mdx` and `next-attachments/`, leaves the live file untouched, and drops its change's planned edges when it was the change's last revision (`withChangeCleanup`, `f-plan-writes`)
- Orientation gate on `node_id`

Depends on: `f-plan-writes`, `f-compiler-rules`, `f-territory-store`, `f-source-index`, `f-orientation-ledger`, `f-domain-model`, `f-tool-kit`.

- **Open revisions (0.18.0).** `open_next` requires `change` and opens `revisions/<change>/` from live (with that change's planned edges as add deltas and base hashes of live); it is Blocked only when that change is already open on the node, so several changes can revise one node at once. `discard_next` takes `change` (optional when only one is open). New tool `resolve_conflict({ node_id, change, section | field | claim, take: "mine" | "live" | "text", text? })` settles one rebase conflict and refreshes its base hash

## Cleanup (0.18)

`open_next` reads structured planned-edge problems (`PlannedEdgeIssue`) and keeps the ones whose source is the node; a leftover next file is a version-gate upgrade, not a per-tool Blocked.

## Discard guard

`discard_next` is Blocked when a stable or unstable dependent's files import a file that only the discarded revision claims, naming the dependents and the files; any other discard goes ahead.

## Rebase on demand

`rebase_revision({ node_id, change })` rebases one open revision onto current live with the same section-hash rule ship uses (untouched sections carry, both-edited ones become conflicts), for the case where live changed without a ship of a sibling, such as after a git merge brought another branch's ship. It reports `{ conflicts, readiness_reset? }`.

`resolve_conflict` names a section conflict by its level-2 heading (a bare heading gets `## `) or by `"_preamble"` for the text above the first heading, which is kept as given. Taking `live` or `text` for a section the revision lacks inserts it where a rebase would put it: a `_preamble` at the top. `take: "text"` holding a level-2 heading outside fences (any for `_preamble`, any beyond the section's own) is Blocked. A resolution that changes the revision's text, scalars, or claims is a contract write: a ready revision goes back to draft (`readiness_reset`), and an in-review one stays in review, and the relied-on build-item guard runs on the resolved body.

## Acceptance Criteria

- `open_next` creates `<id>.next.mdx` with unticked default ops; `discard_next` deletes it and `next-attachments/` and lists each deleted path; no write creates a `state: mirror` file
- `open_next` with a change writes it to the next file only; the result has no `replaced_change`
- `open_next` with a change adds its planned edges to the next slot and returns `applied_planned`; a planned edge whose target was cancelled Blocks `open_next` with the `unlink_nodes` fix
- `open_next` on a node shipping far above the graph's median returns `warnings` and `decision_prompt`; on a node at the graph's pace it returns neither
- Verified via `npm test`

## Attachments

_None._

## Cycles across changes

`open_next` is Blocked when applying the change's planned `depends_on` edges to the node would close a dependency cycle across changes, naming the changes and the path.
