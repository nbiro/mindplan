# Shape the graph

## Purpose

Creates nodes and adds or removes the edges between them, so the graph's structure only changes through calls that validate taxonomy, Interaction Independence, and cycles, and so a new edge's rules reach the agent in the same result.

## Actor & Trigger

Agent calls `create_node` when reuse found no node, and `link_nodes` / `unlink_nodes` when two nodes should be connected or disconnected (with `change`: plan the edge on a shipped node).

## PRD / Execution Logic

Intended files: `src/interactions/i-shape-graph/` (`handlers.ts`, `tools.ts`).

- **create_node** scaffolds the folder and `<id>.mdx` (a Foundation requires `role`), takes `change` / `change_ref` and `aliases` (validated before any write), is never orientation-gated, and returns `rules` (the rules that reach the new node, sources past distance 1 as one line) and `shape` (`shapeReport`: each required section `present`, `missing`, or `stub`, and the gates that read them)
- **link_nodes / unlink_nodes** add or remove one edge (`belongs_to`, `depends_on`, `exposes`, `leads_to`, `affects`, `mounts`) after `validateLink` and the cycle check; while the source evolves the edge goes to its next slot; a ready slot goes back to draft (`readiness_reset`); stability and Capability states are recomputed and each node written lists its live path. A link or unlink that changes the rules reaching its source returns `rules` with only the entries it added or changed (a source newly within distance 1 counts as changed) and `removed` naming sources that stopped reaching it, light past distance 1 (`rulesReachingAfterWrite`, `f-plan-writes`). The source counts as oriented after every link or unlink, with or without a `rules` block, so several links from one node sent together never Block one another
- **Planned edges.** With `change`, on a shipped source with no open revision of that change, `link_nodes` writes a planned edge instead (`validatePlannedLink`, then the live `planned:` list; result `planned`); the live graph, the map, and the search cache do not change, and readiness never resets. A duplicate planned entry is Blocked. `unlink_nodes` with `change` removes that change's planned entries from source to target and is Blocked when there are none. A planned link orients its source itself (`gateWriteOrOrient`, `f-plan-writes`): on a source never oriented on in this session it returns `oriented: true` with the source's rules, because a planned edge changes neither the live graph nor the rules that reach anything until `open_next` applies it, and that call returns the rules it brings. A live link and a link into a revision keep the plain gate
- **`change` on a pre-ship source.** A Foundation, Interaction, or Interface that has not shipped holds no planned edges: its edges are its own plan. When such a node carries a change id and `link_nodes` passes a different `change`, the call is Blocked instead of writing a live edge under the wrong plan: `"<id>" has not shipped, so the edge would join its own plan (change "<its change>"), not "<change>"`, with both ways out (drop `change` to add it now, which makes the node wait for the target; or plan it once the node has shipped). A pre-ship node with no change id, a Bug, and a source whose own change is the one passed are linked live as before: `change` names no other plan there, so one batch can pass `change` for all of its edges
- **Batch.** `link_nodes({ edges: [{ source_id, target_id, edge_type }], change? })` adds 1 to 100 edges in one call, in place of the three single-edge fields (passing both forms is Blocked). Each edge lands where a single call would put it: live on a pre-ship source, a delta on the source's open revision, a planned entry on a shipped source with no revision of `change`. The whole list is checked on one in-memory graph before the first write, each edge against the graph the earlier ones leave, so two edges of one batch that close a cycle together (within a change or across changes) are caught, and a duplicate inside the batch is Blocked like a duplicate of an existing edge. One Blocked edge Blocks the call: the message lists each failing edge by its position counted from 1 (`edge 3 of 31: …`) with its reason, and nothing is written. The reply is `{ edges: [{ source_id, target_id, edge_type, planned? }], rules?, readiness_reset?, changed_files }`: one `rules` block for the batch (every rule source the edges brought, once, naming the batch sources it now reaches, light past distance 1), the ids whose ready slot went back to draft, and each written file once; every source is recorded as oriented. `unlink_nodes` stays one pair per call
- Orientation gate on the source, or on every source of a batch in one message (`gateWrite`, `f-plan-writes`); the sources of a batch's planned edges orient themselves as in a single planned link, their rules riding on the batch reply; `create_node` is never gated

Depends on: `f-plan-writes`, `f-compiler-rules`, `f-territory-store`, `f-orientation-ledger`, `f-domain-model`, `f-tool-kit`.

- **Open revisions (0.18.0).** `link_nodes` and `unlink_nodes` on a node with open revisions write an add or remove delta to the revision `change` picks (optional with one open); a planned edge on a shipped node with no revision of that change stays planned

## Cleanup (0.18)

A revision's readiness reset comes from `revisionReadinessResult` (`f-plan-writes`); no legacy-next path remains.

## Cycles across changes

`link_nodes` with `depends_on` (live, revision, or planned) is Blocked when the edge closes a dependency cycle across changes (`assertNoChangeCycle`), naming the changes and the path, and `run_check` reports existing ones (see `i-check-integrity`).

## Tool descriptions

Each tool's description says when to call it, what it does, and its key parameters, and ends with `Details: get_spec({ topic: "<tool>" })`; the full contract is the tool's SPEC §8 entry.

## Acceptance Criteria

- `create_node` returns `shape` listing every required section of its type as `stub` or `missing`; a Capability's result has none; `aliases` are written and searchable on the next call
- `link_nodes` with `change` on a shipped Interface writes a planned `exposes`: the live `exposes` list and `graph.edges` are unchanged; an illegal or cyclic planned edge is Blocked; `unlink_nodes` with `change` removes it
- A link on a `ready` next slot returns `next_state: "draft"` and `readiness_reset`
- An Interaction → Interaction `depends_on` is Blocked
- `link_nodes` with `edges` holding one `exposes` from each of 31 Interfaces writes all 31 in one call; a batch of `depends_on` edges from three new Interactions to Foundations that carry rules returns one `rules` block that holds each rule source once; a batch whose third edge is illegal is Blocked naming edge 3 and writes nothing; two `depends_on` edges that close a cycle only together are Blocked; `edges` together with `source_id` is Blocked
- Six `link_nodes` calls from one new node, sent together, all succeed, also when a later edge only brings an inherited rule source closer
- A planned link on a shipped source never oriented on in this session succeeds with `oriented: true`; a live link on one is still `Blocked: Orientation`
- `link_nodes` with `change: "b"` on a draft node of change `a` is Blocked naming both ways out and writes nothing; with `change: "a"`, or none, it writes the live edge; a Bug's `affects` and a draft node with no change id are linked live whatever `change` is passed
- Verified via `npm test`
