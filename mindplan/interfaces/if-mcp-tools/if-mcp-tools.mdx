# MCP tools

## Purpose

MCP stdio Interface that registers twenty-seven tools. Each description leads with when to call the tool. A write returns a small result by default (`{ node_id, state, next_state, changed_files }` plus the tool's own fields) and the record, neighborhood, and drift only with `verbose: true`, so a long session of writes does not drown in repeated context. Read results attach a drift report scoped to the node they are about via `withDrift` from `f-mcp-runtime`, except `get_project`, `get_rules`, and `run_check`: `get_rules` runs before every action and would repeat the same report next to `orient_for_work`. `run_check` is the agent's door to the integrity check. `patch_node_rules` is the only way to write a node's rules, and its description must say when to prefer it over `patch_project_rules`, otherwise area-specific rules keep piling into the global list that `get_rules` returns before every action. Without the when-hints, a long session would treat tools as one-shot session-start helpers. `record_decision` and `list_decisions` lead with their when-clauses too: record when you choose between viable designs; list before reshaping a design someone else chose. The descriptions of the tools that touch shipped nodes say when a write lands in place (an additive claim in a dominated folder, a neighbor label) and when it needs `open_next`, so an agent does not open a revision it does not need or claim a file in the wrong folder to avoid one.

Every tool carries MCP annotations, because the host decides from them which calls need a per-call confirmation: without `readOnlyHint`, `get_rules` and `orient_for_work` (called before every action) prompt like writes, and without `destructiveHint` a `discard_next` prompts like a `patch`. The annotations come from the same `read` / `write` / `destructive` kind that already drives the drift and verbose behavior, so a tool cannot be registered with a kind and no hint. Results are compact JSON text plus a `structuredContent` mirror: pretty-printing cost about a third more tokens on every result and bought nothing a client parses. Per-tool descriptions describe the tool; the routing to the plan-project skill lives once in the server `instructions` (owned by `f-mcp-runtime`), not in fourteen descriptions, which is also what the Claude connector review criteria require.

## Kind

MCP tool surface (stdio).

## Exposed Interactions

## Spec

Intended files: `src/interfaces/if-mcp-tools/`

- Register `get_rules`
- Register `patch_node_rules` with `node_id` (slug) and `rules` (string, required; empty clears). Description starts with the when-clause: call when a rule applies to one node and the work that inherits from it, rather than everywhere (use `patch_project_rules` for everywhere)
- `run_check` takes `merge` (`true` or `"strict"`) and passes it to `runCheckHandler`; its description says the merge gate Blocks work still in review (strict: in-progress work whose claimed files changed against the base) and to run it before telling the user a PR is ready
- Register `run_check` with optional `base`; it calls `runCheckHandler` and returns `{ ok, output, failures, warnings }`; no drift
- The `get_rules` description says it returns global rules only and that node rules arrive through `orient_for_work`; the `orient_for_work` description says it returns a `rules` block and takes `depth`
- Lead every tool description with a when-clause
- Write tools take `verbose`. Without it the result is the handler's small result and carries no `drift`; with it the handler also returns `anchor` and `withDrift` attaches drift scoped to the touched node
- `patch_node_territory` takes `section` + `text` and `replace { find, with, all? }` besides `body`; `update_node_status` takes `scope` and `dry_run`; `link_nodes` accepts the `mounts` edge type
- Read results attach a non-empty drift report (`paths` with `class`, `unowned`, `expected`, `other_count`, `reminder`) scoped to the node; `get_project`, `get_rules`, and `run_check` never carry `drift`
- App Router / MCP mounts Interaction packages; Interface does not own core domain logic
- **Schemas for the honesty fixes.** `create_node`, `open_next`, and `patch_node_territory` take `change` / `change_ref`; `toggle_checkboxes` items take `all`, `note`, and `not_applicable`; `update_node_status` takes `scope: "change"` with `change`, and `skip_review`; `get_blast_radius` takes `node_id` or `change`; `run_check` takes `change`. Hints name which writes send a `ready` revision back to `draft`.
- **Decision tools.** Register `record_decision` (a write tool: `verbose`, no default drift) with `node_id`, `decision`, `alternatives` (non-empty array), `why`, and optional `consequences`, `supersedes`, `change`, `id`; register `list_decisions` (a read tool, drift attached) with optional `node_id`, `change`, and `include_superseded`. `record_decision`'s description leads with: call when you choose between viable designs (a data shape, an ordering guarantee, which system owns a fact). `export_mindplan_view` takes `decisions`; `patch_config` takes `decisions: { blast_radius?, schema_files? }` as a strict object (an unknown key is rejected, not stripped); the `record_decision` id schema uses `DECISION_ID_PATTERN`. `orient_for_work` and `get_node_context` take `include_superseded` (the same flag as `list_decisions`) and their descriptions name the `decisions` block; `get_blast_radius` names `decisions`, and `update_node_status` names `Blocked: Decision` at in-review. Twenty-seven tools
- **Async handlers.** `guarded` accepts a handler that returns a promise (`find_related_nodes` and `orient_for_work` await the query embedding): a resolved value takes the same success envelope, and a rejection or a throw takes the same error envelope as a synchronous handler. The legacy files the handler's graph load removed (before its first await) are drained right away and put back when it settles, so a call that runs meanwhile reports only its own. `find_related_nodes` describes hybrid ranking (keyword plus semantic; an exact id first). `patch_config` takes `search: { enabled?, model? }` as a strict object
- **Aliases.** `create_node` and `patch_node_territory` take `aliases` (one shared schema: up to 20 strings of 1–60 characters, with examples in the description); `patch_node_territory` describes it
- **Areas.** Registers `list_areas` (a read tool, no input; twenty-nine tools) and one shared `area` schema (a Journey id) on `orient_for_work` and `find_related_nodes`
- **Summary-first orient.** `orient_for_work` describes the rows, `auto_focus`, the full reply for `node_id`, and the write gate (`Blocked: Orientation`, `create_node` never blocked); its `limit` defaults to 8 for a query alone
- **Rules versions.** `get_rules` takes `known_version` and describes `rules_version` and the `unchanged: true` reply; `get_project` names `rules_version`; `orient_for_work` takes `known_rules_versions` (a string record) and describes the entry `version`
- **Slot and section reads.** `orient_for_work` and `get_node_context` take `slot` (`"current" | "next"`, one shared schema) and `section` (a level-2 heading such as `"## Spec"`, one shared schema) and pass them to their handlers. The `orient_for_work` description says the body is the active slot's by default (the open next while a revision is open), that `section` returns one section, and that the decisions block is the reply's only copy; the `get_node_context` description says both slots come back unless `slot` names one; the `slot` schema says decisions per slot come back from `get_node_context` only
- **No twin in the descriptions.** `open_next` says it writes `<id>.next.mdx` from the live file with a fresh Atomic Ops list; `discard_next` says it deletes the next file and `next-attachments/`; `update_node_status` says ship promotes and deletes the next file; `force_unship` says it deletes any next file; `run_check` names leftover mirror twins among its warnings, not its Blocks; `patch_node_territory` drops the twin wording
- **Decision defaults.** `orient_for_work` and `get_node_context` take `include_inherited_decisions` (one shared schema) and describe the own-decisions default and `inherited_decisions`; `get_blast_radius` takes `include_dependent_decisions` and describes `dependent_decisions`
- **Tool kinds and annotations.** One registration helper takes `kind: "read" | "write" | "destructive"` and derives both the `guarded` options (`drift` / `write`) and the MCP `annotations`: `read` → `{ readOnlyHint: true, destructiveHint: false, idempotentHint: true, openWorldHint: false }`; `write` → `{ readOnlyHint: false, destructiveHint: false, openWorldHint: false }`; `destructive` → `{ readOnlyHint: false, destructiveHint: true, openWorldHint: false }`. `openWorldHint` is always `false`: every tool acts on the local `mindplan/` tree and the repo, never on an external system. Read tools: `run_check`, `get_mindplan_graph`, `export_mindplan_view`, `find_related_nodes`, `get_node_implementation`, `get_node_context`, `orient_for_work`, `get_project`, `get_rules`, `list_decisions`, `get_blast_radius`. Destructive tools (they remove data or edges that no undo restores): `unlink_nodes`, `remove_attachment`, `discard_next`, `force_unship`. Every other tool is `write`. `run_check` keeps `drift: false` on top of `read`. Every tool keeps its `title`
- **Result envelope.** `ok(payload)` returns `content: [{ type: "text", text: JSON.stringify(payload) }]` (compact, no indentation) and, when the payload is a plain object, `structuredContent: payload` as well. String payloads stay text-only. Error results are unchanged (`isError: true`, message text). No `outputSchema` is declared: twenty-seven schemas would double the tool list the host loads, and `structuredContent` is useful without one
- **Descriptions describe the tool.** No per-tool description names the plan-project skill or tells the agent to follow a skill; the routing sentence stays in `SERVER_INSTRUCTIONS` (`f-mcp-runtime`). `force_unship` keeps the `confirm` token contract and the sentence "Do not invent the confirm token", and drops the DANGEROUS / ask-the-user prose: `destructiveHint` tells the host to prompt
- Register `get_mindplan_graph` with `offset` and `limit` (integers, `limit` 1..500, default 200) and a description that names paging and the `next_offset` field; register `export_mindplan_view` with `output` (repo-relative path) and a description that says a diagram over the size budget is refused with the fix (pass `focus` or `output`)
- **Shipped claims and neighbors.** `set_implementation_files` takes `change` (a slug, or `""` to clear) and passes it to the handler; its description names the slot it writes (pre-ship current, open next, or live in place on a shipped node with no open next, additive only in a folder the node dominates, never a migration or schema file; anything else Blocked with `open_next`), `added_in_place`, the body-mention warning, and `folder_claims`. The `change` descriptions of `patch_node_territory`, `record_decision`, and `set_implementation_files` say that on a shipped node with no open next it labels a neighbor (`neighbor_of`, `replaced_change`), and `patch_node_territory` says `change_ref` is Blocked there. `run_check` and `get_blast_radius` say a change's members are its open revisions and its neighbors, each with `kind`; `open_next` says a neighbor label is inherited unless `change` names another (`replaced_change`); `discard_next`, `update_node_status`, and `patch_node_territory` say when `cleared_neighbors` appears and that `scope: "change"` walks revisions only; `force_unship` says it clears the label (`cleared_change`) and `added_claims`. Still twenty-seven tools

## Decisions

### d-annotations-from-tool-kind

- Decision: MCP annotations are derived from one read / write / destructive kind per tool, the same kind that drives drift and verbose, and openWorldHint is always false.
- Alternatives:
  - Hand-write an annotations object on each of the twenty-seven registrations (a new tool can be added with a kind and no hint, and two tables drift)
  - Mark every write destructiveHint: true to be safe (every patch would prompt like a delete, and the host could not tell discard_next from patch_node_territory)
- Why: The host decides from the hints which calls need a per-call confirmation; one kind keeps the hint and the envelope behavior in one place so they cannot disagree.
- Consequences: A destructive tool is one that removes data or edges no undo restores (unlink_nodes, remove_attachment, discard_next, force_unship); a replace-with-empty write stays write. Adding a tool means naming its kind.
- Change: mcp-audit-fixes
- Date: 2026-10-20

### d-compact-json-with-structured-content

- Decision: Successful object results are compact JSON text plus a structuredContent mirror, with no outputSchema declared.
- Alternatives:
  - Keep pretty-printed text only (about a third more tokens on every result, and a client has to parse prose)
  - Declare an outputSchema per tool as well (twenty-seven more schemas in tools/list, which the host loads into context, for validation no client asked for)
- Why: structuredContent lets a client read the result without parsing and costs nothing, while the text copy stays for hosts that ignore it; the schema would cost context on every session.
- Consequences: A test that compares result text byte for byte must parse it instead; string payloads and error results stay text-only.
- Change: mcp-audit-fixes
- Date: 2026-10-20

### d-skill-routing-in-instructions-only

- Decision: Tool descriptions describe their tool only; the routing to the plan-project skill lives once in the server instructions.
- Alternatives:
  - Keep 'Follow the plan-project skill' in each graph-write description (fourteen copies of one sentence, and a pattern the connector review criteria reject as pulling behavior from an external source)
- Why: The instructions pointer already carries the routing and is read on initialize; repeating it per tool adds context on every session and fails directory review for no gain.
- Consequences: The instructions sentence must name the graph writes the skill covers, since no description will.
- Change: mcp-audit-fixes
- Date: 2026-10-20
