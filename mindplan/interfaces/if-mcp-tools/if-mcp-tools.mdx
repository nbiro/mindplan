# MCP tools

## Purpose

MCP stdio Interface that mounts the thirty-three tools its exposed actions define, behind the version gate (a tool on a graph that needs setup or upgrade could misread it, so it is Blocked with the call that fixes it), so a tool change revises the action it belongs to and not this entry point, which used to hold every definition and changed for every tool. Each description leads with when to call the tool. A write returns a small result by default (`{ node_id, state, next_state, changed_files }` plus the tool's own fields) and the record, neighborhood, and drift only with `verbose: true`, so a long session of writes does not drown in repeated context. Read results attach a drift report scoped to the node they are about via `withDrift` from `f-mcp-runtime`, except `get_project`, `get_rules`, and `run_check`: `get_rules` runs before every action and would repeat the same report next to `orient_for_work`. `run_check` is the agent's door to the integrity check. `patch_node_rules` is the only way to write a node's rules, and its description must say when to prefer it over `patch_project_rules`, otherwise area-specific rules keep piling into the global list that `get_rules` returns before every action. Without the when-hints, a long session would treat tools as one-shot session-start helpers. `record_decision` and `list_decisions` lead with their when-clauses too: record when you choose between viable designs; list before reshaping a design someone else chose. The descriptions of the tools that touch shipped nodes say when a write lands in place (an additive claim in a dominated folder, a neighbor label) and when it needs `open_next`, so an agent does not open a revision it does not need or claim a file in the wrong folder to avoid one.

Every tool carries MCP annotations, because the host decides from them which calls need a per-call confirmation: without `readOnlyHint`, `get_rules` and `orient_for_work` (called before every action) prompt like writes, and without `destructiveHint` a `discard_next` prompts like a `patch`. The annotations come from the same `read` / `write` / `destructive` kind that already drives the drift and verbose behavior, so a tool cannot be registered with a kind and no hint. Results are compact JSON text plus a `structuredContent` mirror: pretty-printing cost about a third more tokens on every result and bought nothing a client parses. Per-tool descriptions describe the tool; the routing to the plan-project skill lives once in the server `instructions` (owned by `f-mcp-runtime`), not in fourteen descriptions, which is also what the Claude connector review criteria require.

## Spec

Intended files: `src/interfaces/if-mcp-tools/` (`register.ts`).

The entry point mounts; it defines no tool. Each exposed action owns its tools in its own `tools.ts` (`TOOLS: ToolDef[]`, built with `defineTool` from `f-tool-kit`): the name, title, kind, when-to-call description, input schema, and handler. So a new or changed tool revises the action it belongs to, not this Interface.

- **Mounting.** `registerMindPlanTools(server)` collects every exposed action's `TOOLS` (`i-orient-plan`, `i-assess-impact`, `i-read-brief`, `i-browse-graph`, `i-change-status`, `i-shape-graph`, `i-edit-territory`, `i-revise-node`, `i-claim-files`, `i-record-decision`, `i-edit-brief`, `i-check-integrity`, `i-export-map`, `i-setup-project`, `i-upgrade-graph`) and registers them in `TOOL_ORDER`: the order `tools/list` has always shown, with `get_skill` after `get_spec` and `setup_project`, `upgrade_project` last. Two actions defining one tool name, or a name missing from the order, throws at startup. Thirty-three tools
- **Version gate.** `mount` calls `versionGate()` (`f-graph-migrations`) inside the guarded envelope before the handler of every tool whose config does not say `gate: false`, so its `Blocked: Version` returns as an ordinary error result. The ungated tools are `get_project`, `get_rules`, `get_spec`, `get_skill`, `run_check` (which reports the same failure itself), `setup_project`, and `upgrade_project`
- **Tool kinds and annotations.** `mount` derives both the `guarded` options (`drift` / `write`) and the MCP `annotations` from the tool's `kind` (`ToolKind`, `f-tool-kit`): `read` → `{ readOnlyHint: true, destructiveHint: false, idempotentHint: true, openWorldHint: false }`; `write` → `{ readOnlyHint: false, destructiveHint: false, openWorldHint: false }`; `destructive` → `{ readOnlyHint: false, destructiveHint: true, openWorldHint: false }`. `openWorldHint` is always `false`. A tool with `drift: false` (`run_check`, `get_project`, `get_rules`, `get_spec`, `get_skill`, `setup_project`, `upgrade_project`) never carries drift
- **Result envelope.** `ok(payload)` returns compact JSON text and, for a plain object, `structuredContent: payload`; string payloads stay text-only; errors are `isError: true` with the message; no `outputSchema`
- **Drift and verbose.** Read results attach a non-empty drift report scoped to the node (`withDrift`, `f-mcp-runtime`); a write carries it only with `verbose: true`, so a default write stays small
- **Async handlers.** `guarded` accepts a handler that returns a promise: the same success and error envelopes, and the legacy files its graph load removed before its first await are drained at once and put back when it settles
- **Descriptions describe the tool.** Each action's tool descriptions lead with when to call it and never name the plan-project skill; the routing stays in the server instructions (`f-mcp-runtime`). `force_unship` keeps the `confirm` token contract
- App Router / MCP mounts Interaction packages; the Interface owns no domain logic

Depends on: `f-mcp-runtime`, `f-tool-kit`, `f-territory-store`.

## Acceptance Criteria

- The server registers thirty-three tools in `TOOL_ORDER`, each defined in its action's `tools.ts`; `register.ts` holds no tool schema
- On a graph with no stamp every gated tool returns `Blocked: Version` naming `upgrade_project` and the seven ungated tools answer; without `mindplan/` the Block names `setup_project`; with a current stamp nothing is Blocked
- Two actions defining the same tool name, or a tool missing from `TOOL_ORDER`, fails at startup
- `tools/list` shows `annotations` on all thirty-three tools: read tools carry `readOnlyHint: true`, the four destructive tools (`unlink_nodes`, `remove_attachment`, `discard_next`, `force_unship`) carry `destructiveHint: true`, no tool carries `openWorldHint: true`, and every tool has a `title`
- Every tool description starts with when to call it; none contains `plan-project`, `skill`, or `DANGEROUS`; `force_unship` still names the `confirm` token format
- A successful object result carries `structuredContent` equal to the parsed compact `content[0].text`; an error result carries `isError: true` and no `structuredContent`
- An async handler's `Blocked:` comes back as the same error envelope as a synchronous one
- A default write result has no `anchor` and no `drift`; `verbose: true` adds both; non-empty scoped drift attaches to read results except `get_project`, `get_rules`, `get_spec`, and `run_check`
- Every input field each tool's schema declares reaches its handler (smoke, and the suites of each action)
- Verified via `npm test`

## Decisions

### d-annotations-from-tool-kind

- Decision: MCP annotations are derived from one read / write / destructive kind per tool, the same kind that drives drift and verbose, and openWorldHint is always false.
- Alternatives:
  - Hand-write an annotations object on each of the twenty-seven registrations (a new tool can be added with a kind and no hint, and two tables drift)
  - Mark every write destructiveHint: true to be safe (every patch would prompt like a delete, and the host could not tell discard_next from patch_node_territory)
- Why: The host decides from the hints which calls need a per-call confirmation; one kind keeps the hint and the envelope behavior in one place so they cannot disagree.
- Consequences: A destructive tool is one that removes data or edges no undo restores (unlink_nodes, remove_attachment, discard_next, force_unship); a replace-with-empty write stays write. Adding a tool means naming its kind.
- Change: mcp-audit-fixes
- Date: 2026-10-20

### d-compact-json-with-structured-content

- Decision: Successful object results are compact JSON text plus a structuredContent mirror, with no outputSchema declared.
- Alternatives:
  - Keep pretty-printed text only (about a third more tokens on every result, and a client has to parse prose)
  - Declare an outputSchema per tool as well (twenty-seven more schemas in tools/list, which the host loads into context, for validation no client asked for)
- Why: structuredContent lets a client read the result without parsing and costs nothing, while the text copy stays for hosts that ignore it; the schema would cost context on every session.
- Consequences: A test that compares result text byte for byte must parse it instead; string payloads and error results stay text-only.
- Change: mcp-audit-fixes
- Date: 2026-10-20

### d-skill-routing-in-instructions-only

- Decision: Tool descriptions describe their tool only; the routing to the plan-project skill lives once in the server instructions.
- Alternatives:
  - Keep 'Follow the plan-project skill' in each graph-write description (fourteen copies of one sentence, and a pattern the connector review criteria reject as pulling behavior from an external source)
- Why: The instructions pointer already carries the routing and is read on initialize; repeating it per tool adds context on every session and fails directory review for no gain.
- Consequences: The instructions sentence must name the graph writes the skill covers, since no description will.
- Change: mcp-audit-fixes
- Date: 2026-10-20
