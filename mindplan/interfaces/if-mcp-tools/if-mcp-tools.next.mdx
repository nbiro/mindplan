# MCP tools

## Purpose

MCP stdio Interface that registers twenty-five tools. Each description leads with when to call the tool. A write returns a small result by default (`{ node_id, state, next_state, changed_files }` plus the tool's own fields) and the record, neighborhood, and drift only with `verbose: true`, so a long session of writes does not drown in repeated context. Read results attach a drift report scoped to the node they are about via `withDrift` from `f-mcp-runtime`, except `get_project`, `get_rules`, and `run_check`: `get_rules` runs before every action and would repeat the same report next to `orient_for_work`. `run_check` is the agent's door to the integrity check. `patch_node_rules` is the only way to write a node's rules, and its description must say when to prefer it over `patch_project_rules`, otherwise area-specific rules keep piling into the global list that `get_rules` returns before every action. Without the when-hints, a long session would treat tools as one-shot session-start helpers.

## Kind

MCP tool surface (stdio).

## Exposed Interactions

- `i-orient-plan` — read/orient tools including `get_project` and `get_rules`
- `i-steer-plan` — mutate tools including territory, node rules, project description, project rules, config, attachments
- `i-export-map` — `export_mindplan_view`
- `i-check-integrity` — `run_check`

## Spec

Intended files: `src/interfaces/if-mcp-tools/`

- Register `get_rules`
- Register `patch_node_rules` with `node_id` (slug) and `rules` (string, required; empty clears). Description starts with the when-clause: call when a rule applies to one node and the work that inherits from it, rather than everywhere (use `patch_project_rules` for everywhere)
- Register `run_check` with optional `base`; it calls `runCheckHandler` and returns `{ ok, output, failures, warnings }`; no drift
- The `get_rules` description says it returns global rules only and that node rules arrive through `orient_for_work`; the `orient_for_work` description says it returns a `rules` block and takes `depth`
- Lead every tool description with a when-clause
- Write tools take `verbose`. Without it the result is the handler's small result and carries no `drift`; with it the handler also returns `anchor` and `withDrift` attaches drift scoped to the touched node
- `patch_node_territory` takes `section` + `text` and `replace { find, with, all? }` besides `body`; `update_node_status` takes `scope` and `dry_run`; `link_nodes` accepts the `mounts` edge type
- Read results attach a non-empty drift report (`paths` with `class`, `unowned`, `expected`, `other_count`, `reminder`) scoped to the node; `get_project`, `get_rules`, and `run_check` never carry `drift`
- App Router / MCP mounts Interaction packages; Interface does not own core domain logic

Depends on: `f-mcp-runtime`, `f-domain-model`, `f-graph-search`, `f-view-projection`.

## Acceptance Criteria

- Twenty-five tools registered, including `patch_node_rules` and `run_check`
- Every tool description starts with when to call it
- `patch_node_rules` rejects a missing `rules` and a non-slug `node_id` at the zod layer
- A default write result has no `anchor` and no `drift`; `verbose: true` adds both
- Non-empty scoped drift attached on read results except `get_project`, `get_rules`, and `run_check`; clean tree omits `drift`
- `run_check` output equals the CLI check output
- Verified via `npm test`
