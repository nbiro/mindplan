# Changelog

## 0.17.0 — Capability, and the established terms behind each type

- **Renamed: Journey is now Capability.** The top-level type answers "What does the product do?", which is what a business capability names. "Journey" read as a UX user journey, a sequence of steps, which the type has not meant for a while. The type is `Capability` everywhere a type is named: the `create_node`, `orient_for_work`, and `get_mindplan_graph` `type` inputs, node records, `Blocked:` messages (`belongs_to edges must go Interaction -> Capability`), the map, the scaffold, SPEC, the playbook, the skills, the guides, and the README. Capabilities live in `mindplan/capabilities/<id>/`. Result fields follow: `capabilities_at_risk` and `containing_capabilities` in `get_blast_radius`, and `capabilities_recomputed` in `link_nodes`, `unlink_nodes`, `update_node_status`, and `force_unship`. `Journey` is not accepted as a type name. The recommended id prefix is `c-`; existing ids keep theirs. `list_areas` and `area` keep their names. [§1.1, §2, §4, §5, §8]
- **Established equivalents.** SPEC §2.0.0 gains a non-normative table that names, for each type and edge, its closest established architecture term (business capability or bounded context, use case, driving adapter or C4 container, driven adapter or infrastructure by Foundation role, defect) and where MindPlan differs from it. The playbook's Taxonomy table and the README type table carry the same term in a column. They are an anchor for agents and people who know those terms, not synonyms: the type names stay the only vocabulary. [§2.0.0]
- **Migration level 3: Capabilities move.** `upgrade_project` moves every `mindplan/journeys/<id>/` node folder, attachments included, to `mindplan/capabilities/<id>/`, rewrites `type: Journey` to `type: Capability` in its live file and replaces the scaffold stubs `create_node` used to write (on every run, for every Capability, so a folder moved by hand is repaired), removes `journeys/` once nothing but `.gitkeep` is left, and lists the moved ids in `migrations.capabilitiesMoved`. Ids and other body text are left as they are. An id present in both folders is `Blocked:` naming both paths. A graph at level 3 whose `journeys/` holds a node folder again (a branch from before the upgrade merged one in) is `Blocked: Version` naming `upgrade_project`, which moves it. [§1.1.2, §8.2]
- **Pointer.** The `MINDPLAN.md` pointer says Capability; `upgrade_project` reports `pointer_outdated` until it is refreshed. [§1.1.1]

**Upgrading an existing project:** update `mindplan-mcp` to 0.17.0, reload the MCP server, and ask the agent to call `upgrade_project` (graph tools are `Blocked: Version` until it does). Commit the upgrade on its own.

## 0.16.0 — type names only

- **Removed: the plain-word layer over the type names.** Journey, Interaction, Interface, Foundation, and Bug are the vocabulary everywhere: SPEC §2.0.0 is now a type glossary (question and example per type, no "area", "action", "entry point", or "building block" column), and the playbook, the `plan-project` and `define-entities` skills with their examples, the setup guide, and the README use the type names in prose and in the wording agents use with the user (the playbook's "Talking to the user" says so). The map (`mindplan/map.md`) drops its plain-word legend line. The route-family warning labels an Interface owner `(Interface)` instead of `(entry point)`, the split hints say Interface and Journeys, and the `list_areas` and `area` descriptions say Journey. Tool names, parameters, result fields, ids, states, edges, and `Blocked:` codes do not change: `list_areas` and `area` keep their names. [§2.0.0, §1.2.3, §9.6]

## 0.15.0 — lighter graph reads and no neighbor labels

- **`get_mindplan_graph` `edges`.** A new optional input: `true` (default, unchanged output), `false` (the reply carries neither `edges` nor `total_edges`), or an array of edge types (`["depends_on"]`; values combine with OR) that keeps only those edges whose source is in the page, with `total_edges` counting them over the filtered set. An unknown type is `Blocked: get_mindplan_graph edges: unknown edge type "<name>". Valid edge types: <list>.` before any node is read. Node filtering, sorting, and paging do not change. The tool description's "planned but not built" example now passes `edges: false`: on a real graph the edges were most of that reply. [§8.1]
- **Removed: neighbor labels.** A shipped node with no open next no longer carries a change id. `change` or `change_ref` on such a node in `patch_node_territory`, `set_implementation_files`, or `set_test_files` is now `Blocked: "<id>" is shipped with no open next: edit its files in place; it needs no change id (open_next if its contract changes).` (the same writes without `change` still pass in place). A change's members are its open revisions and planned sources: `run_check({ change })`, `get_blast_radius({ change })`, `get_mindplan_graph({ change })`, and `scope: "change"` walks no longer list neighbors, the `neighbor` kind and additivity's `neighbors` are gone, and no result carries `neighbor_of`, `replaced_change`, `cleared_neighbors`, or `cleared_change`. `record_decision`'s `change` tags the decision only and defaults to the node's open revision's change; `open_next` neither inherits nor clears a label; retiring or unshipping a node touches no change id. A change that closes still drops its planned edges (`cleared_planned`). Labels were stored state that every write path had to set, replace, and clear, and a change that only recorded decisions left them behind; editing a shipped node's files was already legal and checked without them. [§3.7, §8.1, §8.2]
- **Shipped nodes edited in place get the full stale-text pass.** The plain check gives a shipped node with no open next every stale-text signal (not only the missing-path one) when one of its claimed files changed against the default-branch merge base (or `--base`), using the probe dirty-src and the strict merge gate already share. Outside git, or with no base, nothing changes and nothing is reported. This replaces what a neighbor label bought in `run_check({ change })`. [§9.6]
- **`orient_for_work({ change })` includes decision holders.** Active nodes holding an active decision recorded under the change, and not already a revision or planned source, are listed as members with `kind: "decision"` and recorded as oriented, so after a reconnect one change-wide call still covers them. A change whose only trace is its decisions now orients on those holders instead of being `Blocked:`. They do not join the change for `run_check`, `get_blast_radius`, or scoped walks. [§8.1]
- **Migration level 2: change labels stripped.** `upgrade_project` removes the `change` and `change_ref` scalars from the live file of every shipped node (a revision's own change stays on its next file) and lists each in `migrations.staleChangeLabelsCleared` (`{ node_id, change }`). It runs on every upgrade, so a label a branch from an older release brings back is stripped by the next one. [§1.1.2, §8.2]

**Upgrading an existing project:** update `mindplan-mcp` to 0.15.0, reload the MCP server, and ask the agent to call `upgrade_project` (graph tools are `Blocked: Version` until it does). Commit the upgrade on its own.

## 0.14.0 — filtered graph reads and fan-out

- **`get_mindplan_graph` filters.** Four new optional inputs: `state` (one state or an array, any build-pipeline or Bug state, matched against the record's `state`), `type` (one node type or an array), `change` (matches an open revision's `next.change`, else the record's `change`, so a change's new nodes, revisions, and neighbors all match), and `fields` (the node record fields to return; `id` is always kept, and projection never changes which nodes or edges come back). Filters combine with AND, values inside one array with OR. Filtering runs before sorting and paging, so `total_nodes`, `offset`, `limit`, and `next_offset` describe the filtered set; `total_edges` counts edges whose source is in it. An unknown field is `Blocked: get_mindplan_graph fields: unknown field "<name>". Valid fields: <list>.` before any node is read. With no filter the output is unchanged. Agents filter and project for a question about part of the graph instead of reading all of it, and use `orient_for_work` for one piece of work. [§8.1]
- **Fan-out warnings.** A node that must know every feature of a kind (erase a site, export an account, index for search, check a permission) grows one `depends_on` per feature, so every feature reopens it. For each pre-ship Foundation, Interaction, or Interface, the check counts the distinct other unshipped changes among its `depends_on` targets (its own change, shipped, retired, and unlabeled targets do not count). At config `fan_out.warn_at` (default 3) it warns `fan-out: <id> depends on <N> other changes (<a>, <b>, …). It may need to know every feature of a kind. Consider inverting: …`, highest count first. `run_check({ change })` adds a member's line to the change's warnings. Warnings only: `ok` and the exit code do not change. [§5.15, §9.6]
- **Keep whole covers fan-out.** A decision recorded with `keep_whole: true` silences the fan-out warning as it does the hotspot warning; superseding it brings the warning back. [§5.15, §8.2]
- **`stability.fan_out` in orientation.** A full `orient_for_work` reply on a pre-ship Foundation, Interaction, or Interface carries `stability.fan_out: { count, changes }`, even at count 0 and when kept whole; shipped nodes have none. [§8.1]
- **`fan_out` config.** `mindplan/config.json` may carry `fan_out: { warn_at? }` (a positive integer; unknown keys are `Blocked:` like `decisions` and `hotspots`). `patch_config({ fan_out: { warn_at } })` writes it; a field not passed keeps its stored value. [§1.2.1, §8.2]
- **Invert nodes that must know every feature.** The playbook's Breaking down work, the `plan-project` skill (Classify scope), and the `define-entities` skill (Step 0, Common mistakes) tell agents to define the contract once on the Foundation those features already use (a schema convention, or a record they react to), state it as a node rule there, link the test that enforces it with `set_test_files`, and depend only on that Foundation.
- **Why the pointer forbids reading `mindplan/**`.** The `MINDPLAN.md` pointer (`templates/agent/agents-stub.md`) now says why reads go through MCP too: a raw node file lacks inherited rules, decision status, the active slot, and the orientation that unlocks writes. SPEC §1.1.1 matches it (it said only "never edit"). Run `upgrade_project` to see the new pointer (`pointer_outdated`). [§1.1.1]

## 0.13.0 — setup and upgrade from the agent

- **Breaking: `mindplan-mcp init` is removed.** It exits 1 and points at the MCP tools. There is no CLI setup step: register the MCP server with your agent (`claude mcp add mindplan -- npx mindplan-mcp`, or `.mcp.json` / `.cursor/mcp.json` from `templates/agent/mcp.json.example`), then ask the agent to set up MindPlan. [§1.1, §8.2]
- **`setup_project({ ci? })`.** A new write tool creates the graph in a repository that has none: the `mindplan/` tree, a default `config.json` (`{ sources: ["src/**"], exclude: [] }`), an empty `project.md` from the template, and the version stamp. It returns `{ created, changed_files, ci?, pointer, guide }`: `pointer` is the text the agent writes to `MINDPLAN.md` at the repository root, `guide` the steps the agent follows with you (wire `MINDPLAN.md` into `CLAUDE.md` / `AGENTS.md` / the host's rules file, ignores, move standing rules into the brief with your approval, the description, the merge gate). The server writes none of your files (`CLAUDE.md`, `AGENTS.md`, `MINDPLAN.md`, `.gitignore`, `.cursorignore`); the agent does, and shows you the diff. `ci: "github"` writes `.github/workflows/mindplan-merge-gate.yml`, as `init --ci github` did (an existing file is kept). On a current graph it writes nothing and returns the guide again. [§8.2, §9.6]
- **`upgrade_project()`.** A new write tool runs every graph migration (all idempotent: legacy `current.mdx` / `next.mdx` names, a legacy `implementation_packages` config, Atomic Ops left on shipped nodes, leftover `state: mirror` twins, the `revisions` / `churn` / split backfill from git, and deleting `mindplan/agent/`) and stamps the server's migration level. It returns `{ from_level, to_level, changed_files, migrations, leftovers, pointer_outdated, pointer, guide }`; `leftovers` lists the old host copies (`.claude/skills/mindplan-*`, `.cursor/skills/mindplan-*`, `.cursor/rules/mindplan.mdc`), which it reports but does not delete. [§1.1.2, §8.2]
- **`get_skill({ name?, file? })`.** A new read tool serves the bundled skills (`plan-project`, `define-entities`): no name lists them, `name` returns SKILL.md without frontmatter, `name` + `file` one supporting file. Skills are no longer copied into `.claude/skills/`, `.cursor/skills/`, or `mindplan/agent/`; the playbook and server instructions say to load them with `get_skill`. Thirty-three tools: `get_skill` follows `get_spec` in `tools/list`, `setup_project` and `upgrade_project` come last. [§8.1]
- **Breaking: version gate.** `mindplan/version.json` is now `{ package, graph, migrations }`, and the server migrates graphs to `MIGRATION_LEVEL` 1. Every tool except `get_project`, `get_rules`, `get_spec`, `get_skill`, `run_check`, `setup_project`, and `upgrade_project` answers `Blocked: Version — …` while the repository has no `mindplan/` (call `setup_project`), the stamp is missing, unreadable, or below the level (call `upgrade_project`; stamps written by `init` read as level 0), or the stamp or graph is newer than the server (upgrade `mindplan-mcp`). `get_project`'s `version` carries the same sentence. A release that adds no migration needs no upgrade. `MINDPLAN_VERSION_GATE=off` turns the gate off for one process (test fixtures). [§1.1.2]
- **Breaking: the check fails on an outdated graph.** `run_check` and `mindplan-mcp check` fail with `Blocked: Version — …` in those states and run nothing else; before, they printed a non-failing `Warning: version:`. [§9.6]
- **The server no longer creates `mindplan/` at boot.** `setup_project` creates it. [§1.1]
- **Messages name the tools.** The leftover-mirror-twin warning, the `discard_next` Blocked, the legacy `implementation_packages` Blocked, and failed territory renames say "call upgrade_project" instead of "run mindplan-mcp init". Server instructions say to use the plan-project skill "(load it with get_skill)". [§9.6, Appendix A]
- **Removed templates:** `templates/agent/cursorignore` and `templates/agent/permissions.json` (the Cursor MCP permissions allowlist is no longer installed). New: `templates/agent/setup-guide.md` and `templates/agent/upgrade-guide.md`; `templates/agent/agents-stub.md` is now the `MINDPLAN.md` pointer.

**Upgrading an existing project:**

1. Update `mindplan-mcp` to 0.13.0 and reload the MCP server.
2. Ask the agent to upgrade MindPlan: it calls `upgrade_project` (graph tools are `Blocked: Version` until it does, and `check` fails, including in CI).
3. Delete the paths it reports in `leftovers` (old skill and rule copies), and remove `.cursor/permissions.json` if you do not need it for other servers.
4. Wire the pointer: write `MINDPLAN.md` from the returned `pointer`, add `@MINDPLAN.md` to `CLAUDE.md` and a "Read and follow MINDPLAN.md" line to `AGENTS.md`, and remove the old MindPlan stub section from them. The upgrade guide walks the agent through it.
5. Commit the upgrade on its own, before other work. Teammates must update `mindplan-mcp` before they can use the graph.

## 0.12.0 — splits from moved files only

- **`init` infers a split only when files move.** The git backfill recorded a split whenever a Foundation gained `depends_on` on a newly shipped Foundation, so starting to use a new building block counted as a split and reset the node's hotspot rate (10 false splits on one project). Now a split is inferred only when one of the new Foundation's claims was covered by the node's claims before that ship and no longer is after it. [§5.15]
- **Clear a wrong split record.** `patch_node_territory({ node_id, split_into: [] })` on a shipped node with no open revision removes `split_at` and `split_into`, keeps `revisions`, and replays `churn` from git without the reset. Graphs backfilled by 0.10 or 0.11 keep the splits init wrote then; clear each false one this way. [§5.15, §8.1]

## 0.11.0 — splits for actions and entry points

- **`split_into` for Interactions and Interfaces.** A split was recordable only for a Foundation, so an action or entry point whose behavior moved out kept its hotspot rate. Now an Interaction marks the Interactions it splits into (they must share one of its Journeys when it ships), and an Interface marks the Interactions it moves behavior into (it must expose them). Shipping the revision records the split and resets the rate, as for a Foundation. Marking a part whose edge is not in place yet returns a warning naming the edge. [§5.15, §8.1]
- **Hotspot advice** for an Interaction or Interface tells the agent to mark the parts with `split_into`. [§5.15]
- **The median counts established nodes only.** Nodes shipped once and roots that just split no longer count toward the graph's median rate, so a refactor that adds many nodes no longer flags every established node as a hotspot. [§5.15]
- **Tool definitions live with their actions.** Each action's `tools.ts` now defines its MCP tools (name, description, schema, handler); the MCP entry point only mounts them. `tools/list` is unchanged: the same thirty tools, in the same order, with the same descriptions and annotations.

## 0.10.0 — keep shipped nodes closed

- **Hotspot warnings.** A shipped node that changes for several reasons makes every feature queue on its one next slot. The check now warns `hotspot: "<id>" ships far more often than the rest of the graph lately (rate X against a median of Y), and N nodes depend on it directly; …`, listing its recent changes with the decisions recorded under them as the candidate cuts and a split that fits the node's type. A node is a hotspot when its recent ship rate is an outlier against the project's own median, not past a fixed count: changing often is normal on a long project, and a node everything depends on (auth) is fine at the project's pace. Fan-in only ranks hotspots. Settings are config `hotspots: { half_life_days, outlier_ratio, min_rate }` (default 30, 3, 2), written with `patch_config`. Warnings only. [§5.15, §1.2.1]
- **Revision count, recent rate, and split record.** A shipped node's live file now carries `revisions: N` (first ship writes 1, each promotion adds one) and `churn: X`, a ship count that halves every `half_life_days`. A Foundation that split parts out of itself carries `split_at` and `split_into`: mark the parts on the open revision with `patch_node_territory({ split_into })`, and shipping it records the split and resets `churn`, so a root is not flagged again after the split that fixed it. [§5.15, §6.1]
- **Keep a node whole.** `record_decision({ ..., keep_whole: true })` records that a node stays one node on purpose; hotspot detection skips it until a later decision supersedes that one. [§5.15, §8.2]
- **`init` backfills them from git.** For every shipped node without them, init counts the distinct `shipped_at` values in its live file's git history, replays those ship times through the decay, and infers past splits (a Foundation that gained a newly shipped Foundation in `depends_on`; best-effort); outside git it writes 1. Expect a one-time diff adding `revisions:` and `churn:` (and `split_at` / `split_into` on split roots) to every shipped node on the first init with 0.10.0. [§5.15]
- **`stability` in orientation.** A full `orient_for_work` reply on a Foundation, Interaction, or Interface carries `stability: { fan_in, rate, median_rate, revisions?, split_at?, split_into?, hotspot? }`. [§8.1]
- **Additivity of a change.** `get_blast_radius({ change })` returns `additivity` and `run_check({ change })` prints `Info: additivity: change "x": 5 new nodes, 1 revised shipped node (f-payload, fan-in 43), 3 neighbors`, ending `; purely additive` when nothing shipped is reopened. [§5.15]
- **`open_next` warns on a hotspot.** Reopening a hotspot returns `warnings` and a `decision_prompt` (the `record_decision` call naming a new node that `depends_on` it as the alternative). The revision still opens. [§8.2]
- **The decision gate names the additive option.** `Blocked: Decision` for a shipped Foundation's revision or a wide blast radius adds `An additive alternative leaves "<id>" closed: a new node that depends_on it, or a split of it; …`. [§5.13]
- **`get_spec` topic `open-closed`**, and the `plan-project` skill asks agents to read `stability` and hotspots before choosing `open_next`. [§8.1]

## 0.9.0 — agents learn the rules before they hit them

- **Required sections up front.** The Minimum Territory Shape was enforced only on transitions, so agents found the required sections one `Blocked:` at a time. `create_node`, every full `orient_for_work` reply, and `get_node_context` now return `shape`: the sections the node's next move checks, each `present`, `missing`, or `stub`, with the gates that read them (and `role: "missing"` for a Foundation without one). [§6.5]
- **One Blocked lists every gap.** A move blocked on shape names every missing or stub section in one `Blocked: Minimum Territory Shape. "<id>"/<file> has N problems: …` message; a single gap keeps its old wording. [§6.5, Appendix A]
- **`shape:` warnings.** The check warns once per draft (and per Bug before in-review) that misses a required section, naming each one and the gate it is required before. It never fails the check. [§9.6]
- **One table, generated.** The required sections live in one constant; SPEC §6.5 and the `define-entities` skill embed the table generated from it, and the test suite fails when they drift. The skill's section guidance now lists `Purpose` and `Acceptance Criteria` for every type that needs them; the playbook points to `shape` and the table. [§6.5]
- **`get_spec`.** A new read tool returns one section of the running server's own SPEC.md by stable topic id (`territory-shape`, `lifecycle`, `bugs`, `atomic-ops`, `versioning`, `change-ids`, `neighbors`, `decisions`, `imports`, `ownership`, `orientation`, `rules`, `checks`, `errors`) or by tool name; without a topic it lists them. Thirty tools. [§8.1]
- **Change-wide orientation.** After a reconnect, every node needed its own `orient_for_work` before a scoped walk would run. `orient_for_work({ change })` returns every member of a change (open revisions and neighbors) with the nodes whose rules reach it, each source's rules once (`known_rules_versions` leaves known text out), and the members that hold decisions, and records them all, so one call clears the write gate. The ledger stays in memory: a new session still has to read the rules once. [§8.1, §8.1.2]
- **One orientation Block per call.** A write over several unoriented nodes (a batch or a scoped walk) names all of them in one `Blocked: Orientation`; a `scope: "change"` walk names `orient_for_work({ change })`. [§8.1.2]
- **Planned edges.** A plan that needs wiring on shipped nodes (many features exposed by one shipped Interface) no longer has to open a revision on each or keep the wiring as prose. `link_nodes({ ..., change })` on a shipped node with no open revision of that change plans the edge: it is checked like a link (shape, cycles counting the change's other planned edges, an active target) and kept on the live file under the change, outside the live graph. `run_check({ change })` lists the node as a `planned` member, fails on a planned edge that is no longer legal, and notes the planned edges as info; `get_blast_radius({ change })` returns `planned_edges`; `orient_for_work({ change })` covers the node. `open_next` with that change applies them (`applied_planned`); shipping that revision makes them live, a discard leaves them planned, and a change that closes first drops them (`cleared_planned`). `unlink_nodes({ ..., change })` removes one. [§3.7]
- **Attributed files.** A schema node's revision can now own the migration it adds in a composition root's single migrations folder: `set_implementation_files({ node_id, attributed: [...] })` (with `files` optional) names exact files another node claims. The decision gate counts a new attributed migration or schema file for the revision, the blast radius lists it under the revision, the check requires it on disk once the revision is in review, and ship drops the list. Ownership does not move. [§3.7, §5.13]
- **`get_spec` topic `planned-wiring`.** [§8.1]
- **Planned paths are info, not stale.** `run_check({ change })` on a plan-only change warned `stale:` for every path the plan had not built yet. A slot in `draft` or `ready` with none of its claimed files on disk now reports its missing paths as one `planned: "<id>" names N path(s) not on disk yet (…)` line per node, and a path on a line that says "at build time" is planned on any node. These lines go to the new `info` list of `run_check` and print as `Info:` after the warnings; they never change `ok`. [§9.6]

## 0.8.1 — zod 4.6.6 or later

- **`zod` floor raised to `^4.6.6`.** zod before 4.6.6 could exhaust memory while validating oversized constrained collections ([GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5)), and `^4.4.3` still allowed it. No behavior changes.

## 0.8.0 — a shipped node is one file

- **No standing twin.** Every shipped Foundation, Interaction, and Interface used to keep `<id>.next.mdx` as a `state: mirror` byte copy of `<id>.mdx`, rewritten on every live write. A shipped node is now `<id>.mdx` alone: `open_next` writes `<id>.next.mdx` from the live file (with a fresh Atomic Ops list), and ship, `discard_next`, `force_unship`, and retiring delete it with `next-attachments/`. Live writes touch one file, `changed_files` no longer lists twins, and a pull request shows a node's change once, as the diff of `<id>.mdx` (the merge gate ships every change before it merges). While a revision is open, compare `<id>.next.mdx` with `<id>.mdx` to see it. [§3.6, §5.11]
- **`discard_next`** no longer returns `restored_mirror`; its `changed_files` list each deleted path. [§8.2]
- **The check no longer Blocks on a missing or drifted twin.** A `state: mirror` file left by an earlier release is not a revision: it warns `legacy: "<id>" has a leftover mirror twin (<path>); run mindplan-mcp init to remove it.`, and `open_next` replaces it. [§9.6]
- **`init` removes the twins.** It deletes every leftover `state: mirror` next file (and its `next-attachments/` when that holds only `.gitkeep`) and prints how many; an open revision is never touched. The report's `mirrorTwins` is now `mirrorTwinsRemoved` (paths). Expect a one-time diff deleting the twins under `mindplan/` on the first init with 0.8.0. [§3.6]

## 0.7.0 — leaner node reads; a shipped node keeps no Atomic Ops

- **A shipped node keeps no Atomic Ops.** `open_next` copied the shipped, fully ticked checklist into the revision, so every release piled more ticked items into the body, and a revision could pass the Completion Check without one op of its own. Now every `ship` (first ship and promotion) removes the Atomic Ops section (a Foundation's `## Checklist` too) from the shipped node before the mirror twin is written, and `open_next` starts the revision with the unticked `create_node` defaults, to be rewritten into this revision's ops. `force_unship` gives the live file the same fresh list. Rules, Decisions, and every other section stay; a Bug's Fix Checklist is untouched. Git keeps the shipped ledgers. [§5.6, §6.3]
- **`init` drops the ledgers older releases left.** Each shipped Foundation, Interaction, or Interface loses its live Atomic Ops (an open revision keeps its own), its twin is rewritten, and the CLI prints how many nodes changed. Expect a one-time diff across `mindplan/` on the first init with 0.7.0. [§5.6]
- **`orient_for_work` returns the focus's decisions once.** They came back in the `decisions` block and again in `context.decisions` (and `context.next.decisions`); the context no longer carries them. `get_node_context` is unchanged. [§8.1]
- **One slot by default in `orient_for_work`.** With a revision open, `depth: "body"` and `"full"` returned both the live and the next body, which are mostly the same text. The context now carries the active slot's body (the open revision's while one is open, else the live one) and the other slot's record only; `slot: "current" | "next"` picks one. `get_node_context` takes `slot` too and still returns both by default. `slot: "next"` without an open revision is `Blocked:`. [§8.1]
- **Read one section.** `orient_for_work` and `get_node_context` take `section` (a level-2 heading such as `"## Spec"`) and return only that section of each body, naming it in `section`; a missing heading is `Blocked:` and lists the sections. A node too large for one tool result can be read a section at a time. [§8.1]

## 0.6.0 — merge gate; a brief file lock is waited out

- **`check --merge`.** Plain `check` ignores lifecycle state, so a PR could merge to `main` with its change still `in-review`: finished code the graph called unreviewed. The new opt-in merge gate fails with one `Blocked: Merge: "<id>" (<type>, [next ]<state>, change "<change>" | no change): …` line per Foundation, Interaction, or Interface whose live or open next slot is `in-review`, and per Bug in `in-review`. Each line names the fix: `update_node_status({ scope: "change", change, new_status: "ship" })` (a node with no change: `{ node_id, new_status: "ship" }`; a Bug: `"resolved"`), or move it back to `in-progress` (a Bug: `fixing`) if the work is unfinished. Lines are grouped by change id. `draft`, `ready`, `in-progress`, shipped nodes, mirror twins, and retired nodes pass, so planning and incremental PRs still merge. [§9.6]
- **`--merge=strict`.** Also fails an `in-progress` node whose claimed files changed against the base (`--base <ref>`, default the merge base with the newer of `main` and `origin/main`, else `master`; `base...HEAD` plus the working tree), listing up to five paths: a finished feature left at `in-progress`. Opt-in, because it blocks the incremental PRs of a large feature. With no resolvable base it fails with the `--base` fix. [§9.6]
- **`run_check({ merge })`.** `merge: true` or `"strict"` runs the same gate for agents, adds the same `Blocked: Merge` lines to `failures`, and returns `merge: { level, base?, changes: [{ change, nodes: [{ id, type, state, slot, files? }] }] }`, one group per change. [§8.1]
- **`init --ci github`.** Installs `.github/workflows/mindplan-merge-gate.yml` at the repository top, with its steps running in the project root, so a project in a subfolder gets a workflow GitHub runs, which runs `npx -y mindplan-mcp@<major.minor> check --merge` on pull requests to the repository's default branch. Make its `mindplan merge gate` job a required status check, or a red gate does not stop a merge. The workflow is repo-owned: init keeps an existing one unless `--force`. Nothing is installed without `--ci`. [§9.6]
- **Playbook and skill.** Rule 7 says a PR is merged only after its change is shipped (or moved back to `in-progress`), with `check --merge` as the gate; the plan-project skill names the gate where it talks about shipping.
- **Plan-file I/O retries a transient lock.** On Windows, antivirus, the search indexer, or a file watcher often opens a file for a moment right after it is created, and a tool call that read or wrote it then failed with `UNKNOWN: unknown error, open '…'` (for example `record_decision` right after `open_next` created `<id>.next.mdx`). Every read, write, copy, and removal of a file under `mindplan/` (node files, attachments, the ship copy of `next-attachments/`, `project.md`, `version.json`, and the graph cache's hashing) now retries `EBUSY` and `UNKNOWN`, and on Windows `EPERM` and `EACCES`, up to five times over about 0.3 s, before failing with that error. Any other error still fails at once, and no result changes shape. [§1.1]
- **Changed paths in a subfolder project.** `check --base` (dirty-src) and `check --merge=strict` compared claims, relative to the project root, with `git status` and `git diff` paths relative to the repository top, so in a project below the top nothing matched and both silently passed. Changed paths are now project-relative, and paths outside the project are ignored. [§9.6]
- **The default base ignores a stale local `main`.** The default base was the merge base with local `main` when it existed, so a clone that fetched but never pulled counted already-merged commits as this branch's (dirty-src, new-file detection for the decision gate, strict merge gate). It is now the newer of the merge bases with `main` and `origin/main` (likewise `master`). [§9.6]
- **One git probe per check.** `--merge=strict --base` ran the dirty-src git probe twice and reported a failure twice; it now runs once. `--merge` and `--merge=strict` together are `Blocked:` instead of the last one winning. [§9.6]

## 0.5.3 — a note ticks without checked

- **`note` implies `checked: true`.** A `toggle_checkboxes` entry with `note` and no `checked` was `Blocked:` asking for `checked`, though a note always ticks the item and `not_applicable` already ticked without it. `checked` may now be omitted with either; `checked: false` with a note or reason stays `Blocked:`. [§8.1]

## 0.5.2 — ticked checklist lines are history

- **Closed checklist items no longer warn as stale.** The missing-path stale signal scanned every line of a node body, ticked checklist items included. A ticked item that named a path a later change moved warned forever, because the playbook forbids rewording a closed item. Closed items are now skipped by that signal, with their continuation lines: an item is closed when the Completion Check counts it as done (`- [x] …`, with `— note:` or with `— n/a: <reason>`), so an `— n/a:` with no reason is still scanned. Prose and open items still count. [§9.6]

## 0.5.1 — one blank line below the frontmatter

- **Blank-line runs collapse.** Releases before 0.2.0 added a blank line below a node file's frontmatter on every patch and ship. 0.2.0 stopped adding them but kept a file's layout as it found it, and `get_node_context` returned the body with the run on top, so affected files kept dozens of blank lines above the heading. Every write of a node file (body and section patches, rules, decisions, claims, tests, aliases, status moves, `open_next`, ship, and the mirror twin) now leaves exactly one blank line between the closing `---` and the body, in the file's own line endings, so old files clean up on their next write. `get_node_context` returns the body from its first text. The mirror-twin check ignores the blank lines below the frontmatter, so a twin rewritten from a live file that still has its run is not drift. [§3.6, §6.1]

## 0.5.0 — cached graph loads

Every behavior change in this release. SPEC sections in brackets.

- **Graph cache.** Every tool call loads the graph, and parsing every `.mdx` file cost about 1 ms per node (about 10 s per call at 10,000 nodes on Windows). Parsed node records are now kept in memory and in `.mindplan-cache/graph.db`, and a load re-parses only node folders that may have changed. A load returns exactly what parsing every file would. [§1.1.3]
- **Freshness from git.** In a git repository with 1,000 or more node folders, a record parsed while its folder was clean and committed is reused without touching its files as long as git status lists nothing under the folder and the folder is unchanged between that tree and `HEAD:mindplan`. So a `git pull`, checkout, or merge re-parses exactly the folders that differ. [§1.1.3]
- **Freshness from file stamps.** Outside git, in smaller plans, and wherever git ignores a plan file, each folder is checked by its files' size and modification time; a file modified within two seconds of being stamped is compared by content hash until it settles. [§1.1.3]
- **Timings (10,000 nodes, Windows).** A warm load takes 0.4 s with git and 1.1 s by stamps, against 9.4 s uncached. The first load after an upgrade, which drops the cache, takes about 30% longer than an uncached load. At 1,500 nodes: 0.17 s warm against 1.5 s uncached.
- **Safe to delete.** The cache is derived, gitignored with the search cache, never in `changed_files`, and rebuilt when its file is corrupt. Each record carries the parser that made it (the package version plus a hash of the built parser, so a rebuilt checkout counts as new), and a server reads only its own parser's records. `MINDPLAN_GRAPH_CACHE=off` turns it off for one process; `git` or `stamps` forces one mode. [§1.1.3]
- **Search reads fewer files.** Search keys each node's section headings on the graph cache's content key, so a search no longer stats every territory file. [§8.1.1]

## 0.4.0 — semantic search and leaner orientation

Every behavior change in this release. SPEC sections in brackets.

**Search**

- **Hybrid ranking.** `find_related_nodes` and `orient_for_work` rank with keyword search (SQLite FTS5 `bm25`, porter stemming) and semantic search (cosine over local embeddings). The two are merged by reciprocal rank fusion, plus a one-rank-step boost for nodes linked to the top 3. An exact id always ranks first, and a file path ranks the node that claims it. Each node is indexed by its type, title, description, area (Journey titles), entry points (exposing Interfaces), aliases, and section headings, taken from the open `next` slot while a revision is open; ids and claimed paths are indexed as words. `score` is now the fused score, comparable only within one reply. [§8.1, §8.1.1]
- **Results.** On the repo's search test set (48 English queries over a 63-node site-builder graph and this repo's graph), the top hit is right 83% of the time (was 46%), the right node is in the top five 96% of the time (was 73%), and MRR is 0.89 (was 0.58). Keyword-only search scores 0.71 / 0.90 / 0.79. CI fails if a later change drops below these numbers.
- **Search cache.** A derived cache in `.mindplan-cache/index.db` (Node's built-in `node:sqlite`) holds node rows, the FTS5 index, one vector per node, and edges. The `.mdx` files stay the only source of truth. Every search re-syncs the cache from the loaded graph, so a `git pull` or branch switch is searchable on the next call; writes re-sync it and embed only what changed. It is gitignored (by its own `.gitignore`, and `init` now adds `.mindplan-cache/` to the repo's `.gitignore`), never in `changed_files`, never in the coverage universe, and safe to delete. [§1.1, §8.1.1]
- **Local embedding model.** `Xenova/bge-small-en-v1.5` runs through `@huggingface/transformers`, an optional dependency. It downloads once per machine (about 30 MB) into `~/.cache/mindplan/models` and loads in the background at server start; a tool call never waits for it. Until it is ready, or when it cannot load, search is keyword-only and never fails. `MINDPLAN_SEARCH=keyword`, `MINDPLAN_SEARCH_OFFLINE=1`, and `MINDPLAN_MODEL_CACHE` tune it per process. [§8.1.1]
- **No FTS5 needed.** Where SQLite has no FTS5 (Node 22.13's bundled build), the keyword half is the same BM25 in plain JS, with FTS5's formula, Unicode words, folded diacritics, and light stemming. It scores the test set as FTS5 does. [§8.1.1]
- **`search` settings.** `mindplan/config.json` takes `search: { enabled?, model? }`, written by `patch_config({ search })`. `enabled: false` turns semantic ranking off, and a new `model` rebuilds the cache. [§1.2.1, §8.2]
- **`aliases` on any node.** A new optional frontmatter list holds synonyms, the words users will say, and other languages, such as `quote`, `request a quote`, or `ofertă` on an enquiry form. `create_node` and `patch_node_territory` take `aliases`: up to 20, each up to 60 characters, deduplicated ignoring case, stored as JSON strings; `[]` clears them. The list is slot-independent like `tests`: writing it never needs `open_next` or resets readiness, and promotion keeps it. Queries split on letters of any script and diacritics are folded, so `ofertă` and `oferta` both match. [§6.1, §8.2, §8.1.1]
- **`list_areas` and `area`.** `list_areas` is a new read tool (twenty-nine in all). It returns every Journey as one row of a compact table, `{ columns, rows, count }`, with columns `[id, title, description (60 characters), interactions, interfaces, foundations, open_bugs]`; 30 areas fit in about 3.2 KB. `orient_for_work` and `find_related_nodes` take `area`, a Journey id, and rank only that area's active members: the Journey, its Interactions, the Interfaces exposing them, and the Foundations they depend on transitively. A non-Journey id is Blocked. On a 331-node, 30-area graph, a search with `area` took 2.6 ms against 3.3 ms without. [§8.1]

**Orientation**

- **Summaries first.** `orient_for_work` with only a query returns ranked rows: `{ id, type, state, title, description (70 characters), area?, score }`, 8 by default, with no body, neighborhood, blast radius, rules, or decisions; 10 rows stay under 2 KB. When the top row is a clear winner (the query is its exact id, it is the only match, or it scores at least twice the next row), the full node comes back with the rows, marked `auto_focus: true`. `orient_for_work({ node_id })` returns the full node: record, body, rules, own decisions, owned files (`files`), and the blast radius at `depth: "full"`. **Breaking:** a client that read `context`, `rules`, or `blast_radius` from a query-only reply must pass `node_id` or check `auto_focus`. [§8.1]
- **Write gate.** A write that acts on a node is `Blocked: Orientation` until that node got a full reply in this MCP session, and again after the rules that reach it change. A full reply comes from `orient_for_work` with `node_id` or `auto_focus`, `get_node_context` (which now returns `resolved_rules`, every rule that reaches the node), the node's own `create_node`, or a link that changed its rules. The block names the fixing call. Gated tools: `set_implementation_files`, `set_test_files`, `update_node_status`, `patch_node_territory`, `patch_node_rules`, `open_next`, `record_decision`, `put_attachment`, `remove_attachment`, `force_unship`, and `link_nodes` / `unlink_nodes` (on the source). `create_node` is never blocked, and while the gate is on its result carries `rules`. The rules shown and fingerprinted include those an open revision's proposed edges bring. The CLI is never gated, and `MINDPLAN_ORIENT_GATE=off` turns the gate off for a server process. A new Foundation, `f-orientation-ledger`, holds the per-session record. [§8.1.2]
- **Own decisions by default.** `orient_for_work`'s `decisions.entries` holds only the decisions recorded on the focus (a Bug: those of the nodes it affects directly). `decisions.inherited_decisions: { count, nodes }` names the Journeys and Foundations whose decisions also reach it. `include_inherited_decisions: true` adds their entries: whole records at distance 1 (compact at `depth: "rules"`), one line `{ id, node_id, distance, decision }` beyond. On a node shaped like a real 54-node graph's contact form, the default reply carries one decision instead of thirteen. `get_node_context` adds the same summary and flag. `get_blast_radius` returns the focus's own decisions plus `dependent_decisions: { count, nodes }`; `include_dependent_decisions: true` adds the dependents' rows. **Breaking:** a client that read inherited decisions from `decisions.entries` must pass the flag. The decision gate, `list_decisions`, and supersession are unchanged. [§8.1]
- **Rules version tags.** `get_rules` and `get_project` return `rules_version`, the first 12 hex characters of the SHA-256 of the rules. Passing the last tag back as `known_version` returns `{ path, rules_version, unchanged: true }` with no text (78 bytes) while the rules are unchanged; any other value, or none, returns the full text. Each `orient_for_work` rules entry carries `version`, and `known_rules_versions` (node id → version) leaves out text the caller already holds. Agents pass a tag only while they still hold the text it tags. [§8.1]
- **`find_related_nodes`** matches gain an `area` field (Journey titles).

**Check**

- **Description warnings.** `run_check` prints `Warning: description: …` when a description is empty, repeats the title, runs over 300 characters, belongs to an Interaction that names no actor, or uses revision wording ("now", "no longer", "was changed to", "used to be", …; not checked on Bugs). These never fail the check. [§9.6]

**Fixes**

- **`$` in free text.** A title, description, `change_ref`, `tests` entry, or alias containing `$&`, `$$`, `` $` `` or `$'` was read as a `String.replace` pattern and could garble the frontmatter. It is now written as is.

**Requirements and docs**

- **Node 22.13 or later.** `engines.node` is now `>=22.13`, the first 22.x release where `node:sqlite` needs no flag. Node 18 and 20 are no longer supported; CI runs 22.13, 22, and 24. In MCP mode every console method writes to stderr, so no dependency can write to the stdio channel.
- **Docs.** The playbook's step 1 is now orient with a query, pick a row, `orient_for_work({ node_id })`, act, with the area-first path and the write gate. Rule 1 covers the short `get_rules` form, rule 10 covers inherited decisions, and breakdown rule 4 covers descriptions and aliases. The plan-project and define-entities skills, the `AGENTS.md` stub, SPEC, and README match; README has a Search section, and the `npx` examples use `mindplan-mcp@0.4`.

## 0.2.0 — shipped claims and change neighbors

Every behavior change in this release. SPEC sections in brackets.

- **Additive claims on shipped nodes.** `set_implementation_files` on a shipped node with no open `next` (with or without `slot: "current"`) now writes the live list in place when the change is additive: every old entry is kept or covered by a new directory entry, and each new entry is a file whose parent folder the node dominates (it already claims a file there and no other non-retired node claims or covers anything under it) or a directory over such a folder. Removing, moving, globs, and claims outside a dominated folder still need `open_next`, and so does any migration or schema file (config `decisions.schema_files`): an exact file that matches, or a folder entry over a schema folder or holding a matching file. Such a claim is decision-worthy, and only a revision reaches the decision gate. The write re-syncs the mirror twin and returns `added_in_place` and a `hint`. A new file that belongs beside a neighbor's own files no longer has to go into some other folder the node claims as a directory. The Coverage fix for a file in a folder its shipped owner dominates is the claim alone, without `open_next`, unless the file is a migration or schema file. [§1.2, §1.2.1, §3.7, §8.2]
- **`added_claims`.** Entries added in place are listed in the live file's `added_claims` frontmatter. `run_check` warns `stale:` for each one the body does not name as a whole path (`src/a.ts` is not named by `src/a.tsx`, and `src/a/` is not named by `src/a/b.ts`), a territory patch that names it removes it, and promotion of a `next` drops the list. [§6.1, §6.2, §9.6]
- **Folder-claim hint.** Any `set_implementation_files` result may carry `folder_claims: [{ folder, files, note }]` when every file under a folder is already one of the node's per-file claims and nobody else claims under it. [§8.2]
- **Neighbors join a change.** On a shipped node with no open `next`, `patch_node_territory`, `record_decision`, and `set_implementation_files` (new `change` param) accept `change` and write it as the node's neighbor label on the live file; results report `neighbor_of`, and `replaced_change` when the label replaces another (`""` clears). `change_ref` on a neighbor is Blocked; title, description, and role on a shipped live slot stay Blocked. On an open revision or pre-ship node, `set_implementation_files`'s `change` sets the slot's change id. `open_next` on a labeled node inherits the label as the revision's change unless it passes another, which clears the live label, and so does moving the open revision's change id later (`patch_node_territory` or `set_implementation_files` on the next slot; result reports `replaced_change`); `force_unship` and deprecation clear it too. `record_decision` on a neighbor without `change` records the decision under the neighbor's label. [§3.7, §6.2, §8.1, §8.2]
- **Members include neighbors.** A change's members are its revisions plus its labeled neighbors. `run_check({ change })` runs the import, ownership, and stale-text rules on neighbors too and lists members with `kind: "revision" | "neighbor"`; decision warnings stay revision-only. `get_blast_radius({ change })` merges neighbors' radius and files. `update_node_status` `scope: "change"` walks revisions only. A neighbor-only change has members, so it is no longer Blocked as empty. [§3.7, §8.1, §8.2]
- **Labels clear with the change.** When a write leaves a change with no revisions that had one before it (its last revision ships, is cancelled, or is discarded with `discard_next`, or has its change id moved or cleared), the server clears that change's neighbor labels once, after the write, and reports `cleared_neighbors`. A batch or scoped walk does this once for the whole call. A neighbor-only change is closed by a `scope: "change"` walk to `ship`. [§3.7, §8.2]
- **Docs.** The playbook tells agents to pass `change` on a neighbor's in-place writes and that a new file beside a node's own, in a folder nobody else claims into, is claimed in place; the `plan-project` and `define-entities` skills and the README tool table say the same. [§3.7]

## 0.1.0 — decision records

Every behavior change in this release. SPEC sections in brackets.

- **Decision records.** A node carries decisions in a `## Decisions` section: id, the decision, the alternatives considered, why, optional consequences and `supersedes`, and the change id and date. `record_decision` is the only writer and only appends; body writes keep the section and Block a body that contains one. Decisions belong to a slot: while a shipped node evolves they go to its next file, ship with it, and are dropped by `discard_next`. Recording never resets readiness. [§6.1.2, §8.1]
- **Superseding, not editing.** A new decision with `supersedes` replaces an active one held by the same node, its Journeys, or its Foundations. Status is computed, not written into the old entry, so discarding the superseding revision makes the old decision active again; deprecating the superseding node does not. An id that a `supersedes` still names stays taken. `list_decisions` returns a node's, a change's, or the graph's decisions; superseded ones with `include_superseded`. [§6.1.2, §8.1]
- **Decisions reach the agent.** `orient_for_work` returns a `decisions` block next to `rules`, at every depth, inherited like rules and labeled by source; `get_node_context` returns `decisions` (and `next.decisions`) and its `body` no longer contains the section; `get_blast_radius` lists the active decisions of the focus and its dependents; `export_mindplan_view` takes `decisions: true` for per-node counts. [§8.1]
- **Decision gate (Rule 12).** An open revision is decision-worthy when it changes a shipped Foundation's contract, claims a new migration or schema file (including one the branch adds inside an already-claimed folder), has more dependents than `decisions.blast_radius`, or adds or removes a `depends_on` edge of a shipped node. Without a decision under its change id (recorded since the revision opened; `open_next` now writes `opened_at`) or on the node, `run_check` warns from draft on and a move to `in-review` is `Blocked: Decision` with the `record_decision` call. One decision under a change clears every member. A first build's initial edges are never gated, and inside git a first build's schema file counts only when the branch adds it. **Breaking:** a shipped Foundation's revision, or a first build that claims a schema file, now needs a recorded decision before `in-review`. [§5.13, §9.6]
- **Gate settings.** `mindplan/config.json` takes an optional `decisions: { blast_radius, schema_files }` (defaults `5` and database migration/schema globs); `patch_config` writes it and rejects an unknown key. [§1.2.1, §8.2]
- **Shared branch base.** The dirty-src check and the decision gate measure "this branch" from the same merge base (`main`, `origin/main`, `master`, `origin/master`). [§9.6]
- **Twenty-seven tools.** `record_decision` and `list_decisions` are new. The playbook gains one line on recording decisions. [§8]

## 0.1.0 — graph honesty

Every behavior change in this release. SPEC sections in brackets.

### The graph no longer says "fine" when it does not match the code

- **Readiness reset.** A contract write to a revision in `ready` moves it back to `draft`: `patch_node_territory` (title, description, role, body, section, replace, toggle_checkboxes), `set_implementation_files` (when the list changes), and `link_nodes` / `unlink_nodes` on the source. The reset lives in the territory store's contract writers, so `mindplan-mcp init`'s legacy claim migration also sends a `ready` node whose claims it rewrites back to `draft`. The result carries the new `state` / `next_state` and `readiness_reset: { slot, from, to, note }`. `patch_node_rules`, change-id writes, attachments, and writes to `draft` / `in-progress` / `in-review` slots never reset. [§3.1]
- **Coverage names the fix.** An unclaimed file inside the configured `sources` is `Blocked: Coverage: …` with the probable owner (longest shared claim prefix) and the exact `set_implementation_files` call, preceded by `open_next` for a shipped owner. A file two or more folders deep needs at least two shared folders before a probable owner is named. A retired node's claim no longer counts as coverage; such a file is still reported once, by the leftovers rule, so no graph gains a failure. [§1.2.1, §9.6]
- **Imports over next-slot and released claims.** The import matrix now scans every claimant of a file (live, next slot, released) and resolves targets through released claims. Violations only this wider scan finds print as `Warning: imports (next slot): …` in this release and **will Block in the next release**. [§9.6]
- **Scoped walks do not skip review.** `update_node_status` with `scope` to `ship` is Blocked when a selected node is not yet `in-review`, unless `skip_review: true`; with it the node still walks through `in-review` (gate included) and the result lists `skipped_review`. `dry_run` now lists every transition (one `id: from -> to` line per step), not one line per node. **Breaking:** callers that walked `in-progress` nodes straight to `ship` must walk to `in-review` first or pass `skip_review: true`. [§3.7, §8.2]

### Tool usability

- **Unambiguous checkbox toggles.** A `toggle_checkboxes` `contains` that matches several checkbox lines is Blocked and lists them, unless `all: true`. Matching still uses the whole line, marker included. The result returns `toggled`, the lines as written. **Breaking:** an ambiguous `contains` used to tick the first match silently. [§8.1]
- **Honest closing of an item.** `toggle_checkboxes` takes `note` (ticks and appends ` — note: …`) and `not_applicable` (ticks and appends ` — n/a: <reason>`). Both pass the Completion Check; an `— n/a:` with no reason counts as unchecked. Unticking strips the annotation. [§3.3, §5.6]

### Modeling

- **Change ids.** `create_node` and `open_next` take `change` / `change_ref`; `patch_node_territory` sets or clears them. `update_node_status` gains `scope: "change"`, `get_blast_radius` takes `change` (merged radius), and `run_check` takes `change` (in-review gate on every member; violations the global check already reports are not repeated). Shipping ends membership. Node records show `change` / `change_ref`. [§3.7]
- **Glob claims.** `implements` entries may use `*`, `**`, and `?` (`[` `]` stay literal). Globs expand to concrete files in the check, `get_node_implementation`, and path lookup; exclusivity stays per file. Glob expansions are cached for the length of one call. Directory and glob expansion now skip `.git/` and `node_modules/`. [§1.2]
- **Shared app routes.** SPEC defines route ownership in multi-template apps: the Assembler owns routes that dispatch to the active template; a template's entry point owns only its own routes. The check warns (`Warning: routes: …`) when one route family has more than one owner. Only `app/` folders with a root layout count as routers. [§1.2.3, §9.6]
